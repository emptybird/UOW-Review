1. Diffie–Hellman 密钥协商

1.1 问题：在人人都能偷听的信道上商量出一把钥匙 (S2)

老师用一个场景引出这一节。假设你要设计一个聊天软件，你能给老师发消息，老师也能回复。消息如果不加密，路径上的任何人都能读到整段对话。要加密，最自然的选择是第 4 周 §3.2 的对称加密（比如 AES）：速度快，适合大量数据。可是对称加密卡在一个老问题上：双方必须先有同一把钥匙。老师的原话是：我用一把 AES 密钥加密了消息，可我还得把这把密钥给你，不然你解不开；要是把它从同一条信道发过去，偷听的人也拿到了。

第 4 周 §3.4 给过一个答案：用对方的公钥把 AES 密钥加密以后再送过去，这叫密钥传输 (key transport)。这一节讲另一种思路：钥匙根本不在网络上传。双方各自准备一份秘密，只交换由秘密算出来的公开值，再各自在本地算出同一把钥匙。这叫密钥协商 (key agreement)，也叫密钥交换 (key exchange)，slides 两个说法都用（S2 的标题是 agreement，S3 的第一句说 key exchange）。老师说，没有它就没有今天的 HTTPS；SSH 和 SSL/TLS 用的都是它。

📎 拓展(超出 slides)：名字的来历 — 1976 年，Whitfield Diffie 和 Martin Hellman 在论文 New Directions in Cryptography 里公开发表了这个想法，这也是公钥密码学的起点。原始版本在模 pp 的整数上做幂运算：公开 gg 和 pp，Alice 发出 gamodpg^a \bmod p，Bob 发出 gbmodpg^b \bmod p，两人都能算出 gabmodpg^{ab} \bmod p。S3 第一句 "can do key exchange analogous to D-H" 说的就是：在椭圆曲线上，可以做一个和原始 DH 类似的密钥交换。这个椭圆曲线版本叫 ECDH（Elliptic Curve Diffie–Hellman），也是本课和 Lab 4 用的版本。

📎 拓展(超出 slides)：一个常用的比喻 — 把密钥协商想成调颜料。双方先公开约定一种底色，比如黄色。Alice 往黄色里加一点只有她知道的红色，Bob 加一点只有他知道的蓝色，然后把各自调好的颜料寄给对方。Alice 收到"黄 + 蓝"，再加入自己的红；Bob 收到"黄 + 红"，再加入自己的蓝。两人最后都得到"黄 + 红 + 蓝"，是同一种颜色。偷看邮包的人手里有黄、"黄 + 红"、"黄 + 蓝"，可是把调好的颜料分离回原色很难；把两罐直接倒在一起，得到的是"黄 + 黄 + 红 + 蓝"，多了一份底色，颜色不对。下面会看到，椭圆曲线上的情形和这个比喻一模一样：混色容易、分离困难，就是"标量乘法容易、离散对数困难"。

1.2 先回顾椭圆曲线：曲线、基点和阶 (S3)

S3 的前两条是在搭舞台：选一条合适的曲线 Ep(a,b)E_p(a, b)；选一个基点 G=(x1,y1)G = (x_1, y_1)，它的阶 nn 很大，满足 nG=OnG = O（原文 with large order n s.t. nG=O，s.t. 是 such that 的缩写）。这里的每个符号都值得说清楚。

曲线 Ep(a,b)E_p(a, b)。 它是满足方程

y2≡x3+ax+b(modp)y^2 \equiv x^3 + ax + b \pmod p

的所有点 (x,y)(x, y)，再加上一个特殊的点 OO。pp 是一个大素数；xx、yy 都取 00 到 p−1p-1 的整数，等式两边除以 pp 的余数相等；aa、bb 是决定曲线的两个参数。第 3 周的 secp256k1 就是 Ep(0,7)E_p(0, 7)，即 y2=x3+7y^2 = x^3 + 7，其中 pp 是一个 256 位的素数。

点的"加法"和标量乘法。 曲线上的两个点可以按一套固定规则"相加"，结果仍是曲线上的点。特殊点 OO 叫无穷远点 (point at infinity)，它在这套加法里相当于普通加法里的 0：P+O=PP + O = P。把同一个点 GG 加自己 kk 次，记作 kGkG，叫标量乘法 (scalar multiplication)，第 3 周叫它"椭圆曲线乘法"。

📎 拓展(超出 slides)：加法规则和"快速乘" — 两个不同的点 P=(x1,y1)P = (x_1, y_1)、Q=(x2,y2)Q = (x_2, y_2) 相加，先算过两点的直线斜率 λ=y2−y1x2−x1\lambda = \frac{y_2 - y_1}{x_2 - x_1}；一个点自己加自己（叫倍点），改用切线斜率 λ=3x12+a2y1\lambda = \frac{3x_1^2 + a}{2y_1}。然后

x3=λ2−x1−x2,y3=λ(x1−x3)−y1x_3 = \lambda^2 - x_1 - x_2, \qquad y_3 = \lambda(x_1 - x_3) - y_1

所有运算都对 pp 取余，除法换成乘以模 pp 的逆元。在实数上画出来，这条规则就是"过两点连一条线，找它和曲线的第三个交点，再关于 x 轴翻转"。

算 kGkG 不需要真的加 kk 次。100 的二进制是 1100100，从最高位起逐位处理，"先倍点，这一位是 1 就再加一次 GG"：G→3G→6G→12G→25G→50G→100GG \to 3G \to 6G \to 12G \to 25G \to 50G \to 100G，一共 6 次倍点、2 次加法，而不是加 99 次。这叫倍点–加法 (double-and-add)。256 位的 kk 只需要大约 256 次倍点和不到 256 次加法，所以第 3 周老师说，正着算"不到一秒"。

基点 GG。 所有参与者都知道的一个固定起点。老师说：如果教室里我们四个人约定用这条曲线，那我们四个人都知道 GG。实践中基点和曲线一起由标准规定（secp256k1 的 GG 就写在标准里），所以"选曲线"和"选基点"常常是同一件事。

阶 nn。 从 GG 出发，一次次加 GG：G,2G,3G,…G, 2G, 3G, \dots，迟早会走到 OO。第一次走到 OO 所用的步数 nn 叫 GG 的阶 (order)，即 nG=OnG = O。之后序列开始重复：(n+1)G=G(n+1)G = G，(n+2)G=2G(n+2)G = 2G……所以乘数只在除以 nn 的余数意义下起作用：kG=(kmodn)GkG = (k \bmod n)\,G。这就是 S3 要求私钥 xA<nx_A < n、xB<nx_B < n 的原因：比 nn 大的数和它除以 nn 的余数给出同一个公钥，选大了并不更安全。至于 nn 为什么必须很大，要看下面这个难题。

难题：椭圆曲线离散对数。 已知 GG 和 Y=xGY = xG，求 xx，这叫椭圆曲线离散对数问题 (ECDLP)。第 3 周用"钟面上跳格子"打过比方：知道跳几步，很快就能跳到终点；只告诉你终点，问跳了几步，就只能一步步试。老师在课上又讲了一遍：我选一个数，比如 8，算出 8G8G，它是曲线上的一个点；我把这个点的横纵坐标告诉你，你也知道 GG，可你不可能算出我选的是 8。nn 很大，就是为了让"一步步试"永远试不完：secp256k1 的 nn 大约是 22562^{256}。

再算 2G2G（倍点）：λ=3⋅52+22⋅1=772\lambda = \frac{3 \cdot 5^2 + 2}{2 \cdot 1} = \frac{77}{2}。模 17 下 77≡977 \equiv 9；2 的逆元是 9，因为 2×9=18≡12 \times 9 = 18 \equiv 1。所以 λ=9×9=81≡13\lambda = 9 \times 9 = 81 \equiv 13，x3=132−5−5=159≡6x_3 = 13^2 - 5 - 5 = 159 \equiv 6，y3=13×(5−6)−1=−14≡3y_3 = 13 \times (5 - 6) - 1 = -14 \equiv 3。于是 2G=(6,3)2G = (6, 3)。

自测：在 §1.2 的玩具曲线上，有人说"我的私钥选 22，比 3 大，所以更安全"。对吗？

不对。GG 的阶 n=19n = 19，22G=19G+3G=O+3G=3G22G = 19G + 3G = O + 3G = 3G，私钥 22 和私钥 3 给出同一个公钥 (10,6)(10, 6)，攻击者找到 3 就等于找到了 22。这正是 S3 要求 xA<nx_A < n 的原因：乘数只在除以 nn 的余数意义下起作用。真正的安全来自 nn 本身足够大（约 22562^{256}），而不是私钥"数字大"。

1.3 ECDH：交换两个点，各自算出同一把钥匙 (S3, S4)

舞台搭好了，S3 后三条和 S4 给出协议本身：

  1. 双方约定曲线 Ep(a,b)E_p(a, b) 和基点 GG（阶为 nn），这些都是公开的；
  2. Alice 和 Bob 各选一个私钥 xA<nx_A < n、xB<nx_B < n，各自保密；
  3. 各自算出公钥：YA=xAGY_A = x_A G，YB=xBGY_B = x_B G；
  4. 交换公钥（S4）：① A → B：YA=xAGY_A = x_A G；② B → A：YB=xBGY_B = x_B G；
  5. 各自算出共享密钥：Alice 算 K=xAYBK = x_A Y_B，Bob 算 K=xBYAK = x_B Y_A。

两人用的是不同的私钥、不同的公钥，为什么算出同一个点？S3 的最后一句给了答案：两者相同，因为都等于 xAxBGx_A x_B G (same since K=xAxBGK = x_A x_B G)。展开写：

xAYB=xA(xBG)=(xAxB)G=xB(xAG)=xBYAx_A Y_B = x_A (x_B G) = (x_A x_B)\, G = x_B (x_A G) = x_B Y_A

中间那一步只用到"标量乘法就是重复相加"：先把 GG 加 xBx_B 次得到 YBY_B，再把 YBY_B 加 xAx_A 次，等于一共把 GG 加了 xAxBx_A x_B 次；反过来先加 xAx_A 次、再加 xBx_B 次，也是 xAxBx_A x_B 次。次数一样，落点就一样。

S4 把每一方画成一个 "DH" 盒子：私钥 xx 从外面放进盒子，GG、nn 是盒子的参数，公钥 YY 从盒子之间传过去，共享密钥 KK 从盒子里出来。整张图里，私钥从来没离开过自己的盒子，在线路上走的只有两个公钥。图 2 把同一件事画成了时序图。

课上有同学被"谁选哪个数"绕晕了，老师这样解释：比如你和我，我选我的私钥，你选你的；我不知道你的，你也不知道我的。我把我的公钥给你，你把你的公钥给我，GG 是公开的。然后我用我的私钥乘你的公钥，你用你的私钥乘我的公钥，"左边等于右边"。

图 1 里的两个蓝点是公钥，绿点是共享密钥 KK。

KK 拿来做什么？ 有同学问"K 到底是什么"。老师说，KK 是 A 和 B 之间的共享密钥 (shared key)，可以把它看成一颗种子 (seed)，由它得到 AES 密钥；为了好理解，"你可以把 K 想成就是 AES 密钥"。在发出第一句真正的消息（比如 "hello"）之前，双方先协商出 KK，之后的消息都用由 KK 得到的 AES 密钥加解密。实际系统通常取 KK 的横坐标，再做一次哈希或密钥派生 (key derivation)，得到需要的对称密钥。

multiply 那一行就是 S3 的 K=xAYBK = x_A Y_B；sha256 那一行把点的横坐标哈希成 32 字节，就是老师说的"从种子得到 AES 密钥"。Quiz 3 的聊天程序沿用了同样的握手：双方先交换 {"name", "pk"}，再各自算出同一把 AES 密钥。

偷听的人能算出 KK 吗？ 老师在课上专门问了这个问题。假设有个人坐在中间，能听到所有消息，但不改任何消息。他能拿到 YAY_A 和 YBY_B，曲线和 GG 本来就公开。学生回答：算不出 KK，因为他只有公钥，没有私钥。老师追问："GG 也是公开的，他还是算不出吗？"学生说：还是不行，算 KK 需要私钥。老师说对：只要他只听、不改消息，就不可能解密后面的通信。想算出 KK，他得先从 YAY_A 求出 xAx_A（或从 YBY_B 求出 xBx_B），这就是 §1.2 的 ECDLP。

这里有一条容易想歪的边界：攻击者能不能把手里的公开值"组合"一下？比如把两个公钥加起来：YA+YB=(xA+xB)GY_A + Y_B = (x_A + x_B)\,G。在例子里是 3G+7G=10G=(7,11)3G + 7G = 10G = (7, 11)，而真正的 K=21G=(6,3)K = 21G = (6, 3)。加法得到的是私钥之和，KK 需要的是私钥之积，这和颜料比喻里"两罐直接倒在一起，多了一份底色"是同一回事。

📎 拓展(超出 slides)：CDH 问题 — "已知 GG、xAGx_A G、xBGx_B G，求 xAxBGx_A x_B G"有一个专门的名字：计算 Diffie–Hellman 问题 (computational Diffie–Hellman problem, CDH)。ECDH 的安全性直接依赖它。能解 ECDLP 就能解 CDH（先求出 xAx_A，再算 xAYBx_A Y_B）；对设计良好的曲线，目前也没有比解 ECDLP 更快的办法。

最后，把这一节放回前几周的脉络里：

  • 第 5 周 §2.3：SSH 日志里的 Curve25519 就是 ECDH。每次连接，客户端和服务器各临时生成一对密钥，交换公钥，各自算出 KK，再由 KK 派生出加密和 MAC 用的会话密钥。
  • 第 4 周 §3.4 的拓展：TLS 1.3 用临时的 (EC)DH 协商会话密钥。私钥每次新生成、用完即删，所以长期私钥日后泄露，也解不开以前录下的流量，这叫前向保密 (forward secrecy)。
  • DH 本身不加密任何东西，它只产出一把钥匙，加密靠后面的 AES。它也不告诉你对面是谁，下一节就会看到这一点有多致命。

1.4 中间人攻击：会改消息的 Eve (S5)

§1.3 的结论有一个前提：攻击者只听不改。安全分析里把攻击者分成两类：

  • 被动攻击者 (passive adversary)：只偷听，也叫窃听者 (eavesdropper)；
  • 主动攻击者 (active adversary)：能拦截、修改、丢弃、伪造消息。

老师说，假设这个 Eve 就是网络运营商里的人，所有消息都要经过她。她不再满足于偷听，而是改消息。S5 画出了她的做法：

  1. A → E：YAY_A。Alice 以为自己把公钥发给了 Bob，其实被 Eve 截住了；
  2. E → B：YEY_E。Eve 选了自己的私钥 xEx_E，把自己的公钥 YE=xEGY_E = x_E G 冒充成 Alice 的发给 Bob；
  3. B → E：YBY_B。Bob 回复自己的公钥，同样被截住；
  4. E → A：YEY_E。Eve 把自己的公钥冒充成 Bob 的发给 Alice。

结果出现了两把密钥（S5 图里的记号）：

  • Alice 算 K′=xaYEK' = x_a Y_E，Eve 算 K′=xeYAK' = x_e Y_A，两者相等。Alice 和 Eve 共享 K′K'；
  • Bob 算 K″=xbYEK'' = x_b Y_E，Eve 算 K″=xeYBK'' = x_e Y_B，两者相等。Eve 和 Bob 共享 K″K''。

Alice 和 Bob 都以为自己和对方建立了一把密钥，其实各自都在和 Eve 通信。之后 Alice 用 K′K' 加密的每条消息，Eve 都能解开、阅读、随意修改，再用 K″K'' 加密后转给 Bob；反方向也一样。两个人都察觉不到。图 3 画出了整个过程。

老师用"带名字的消息"把它讲得更直白。本来的第一条消息是"嗨，我是 Alice，我的公钥是 YAY_A"。Eve 把它改成"嗨，我是 Alice，我的公钥是 YEY_E"。Bob 没有办法验证，只能说"好的，收到"，然后回复"我是 Bob，YBY_B 是我的公钥"；Eve 再如法炮制，改成"YEY_E 是我的公钥"。老师问：现在 Eve 能读消息吗？能。

🔑 例：把中间人放进玩具曲线 — 沿用 §1.3 的 xA=3x_A = 3、xB=7x_B = 7。Eve 选 xE=5x_E = 5，YE=5G=(9,16)Y_E = 5G = (9, 16)。

  • Alice 收到的"Bob 的公钥"其实是 YEY_E，她算 K′=3⋅YE=15G=(3,16)K' = 3 \cdot Y_E = 15G = (3, 16)；Eve 算 5⋅YA=5⋅3G=15G5 \cdot Y_A = 5 \cdot 3G = 15G，同一个点。
  • Bob 收到的"Alice 的公钥"也是 YEY_E，他算 K″=7⋅YE=35G=16G=(10,11)K'' = 7 \cdot Y_E = 35G = 16G = (10, 11)；Eve 算 5⋅YB=35G5 \cdot Y_B = 35G，也是它。
  • 没有中间人时，两人本该得到 (6,3)(6, 3)。现在 Alice 手里是 (3,16)(3, 16)，Bob 手里是 (10,11)(10, 11)，这两个值 Eve 都有。

为什么 DH 挡不住她？ 一个公开值只是曲线上的一个点，它不带任何"这是谁生成的"证据。YEY_E 和 YAY_A 看上去毫无区别。DH 保证的只是：和我算出同一个 KK 的那个人，一定掌握对应的私钥；它不保证那个人是谁。偷听者没有私钥，所以输了；中间人自己生成了私钥，所以赢了。

怎么解决？ S5 的提示是一个词：认证 (authentication)。老师把问题说得很具体：第一条消息"我是 Alice，YAY_A 是我的公钥"太容易被换成 YEY_E，所以真正的问题是怎样证明 YAY_A（或 YEY_E）就是你的公钥。如果我们面对面，你把公钥交给我，我当场接受，没有人能在中间动手脚；可如果你托别人带话，或者消息要经过运营商、经过 Telstra，再到我的手机和电脑，带话的人就有能力换掉它。下周要讲的证书能解决这个问题，但老师先打了个预防针：只要用证书，我们就得信任某个第三方。

📎 拓展(超出 slides)：认证怎样补上 DH 的缺口 — 思路是给公开值"签名"。Alice 除了临时的 DH 私钥 xAx_A，还有一把长期的签名私钥；她发送 YAY_A 时附上对 YAY_A 的签名，Bob 用 Alice 的长期公钥验证。Eve 能换掉 YAY_A，却伪造不出 Alice 对 YEY_E 的签名。于是问题变成：Bob 怎样确认手里那把长期公钥真是 Alice 的？这就是证书要回答的。你已经见过这个组合：第 5 周 §2.3–§2.4 里，SSH 服务器用主机私钥对密钥交换的摘要签名，客户端核对主机密钥指纹，防的正是这里的中间人；HTTPS 则由服务器证书来证明身份。另一种办法是带外核对 (out-of-band verification)：双方通过另一条可信的渠道（当面、电话里认得出声音）比对 KK 或公钥的指纹，Signal 的"安全码"就是这样设计的。

还有一条边界要记住：在中间人攻击下，消息"确实被加密了"。Alice 的聊天软件会显示"已加密"，密文也确实只有持有 K′K' 的一方能解开，只不过那一方是 Eve。加密保护的是"和谁共享密钥"这件事已经确定之后的通信；对象错了，加密得再好也没用。Lab 4 和 Quiz 3 的程序都没有任何认证，它们的握手正好暴露在这种攻击之下。

自测 1：在下面两种情况下，Eve 能不能读到 Alice 和 Bob 后面的加密消息？① 她能看到线路上的所有消息，但不能改；② 她能截下并替换任何消息。

① 不能：她只有 YAY_A、YBY_B 和公开参数，算 K=xAxBGK = x_A x_B G 需要私钥（ECDLP / CDH）。② 能：她按 S5 的四步换掉两个公钥，和双方各建一把密钥（K′K'、K″K''），之后解密、阅读、修改、再加密转发。DH 防得住被动攻击者，防不住主动攻击者。

自测 2：Alice 和 Bob 怀疑被中间人攻击了。他们打了个电话（互相认得出声音），各自念出自己算出的 K 的前几位。这能发现攻击吗？为什么？

能。有中间人时，Alice 的密钥是 K′K'、Bob 的是 K″K''，两者几乎不可能相等（例子里一个是 (3,16)(3, 16)，一个是 (10,11)(10, 11)），一对比就露馅。这正是 S5 提示的"认证"：电话这条渠道让双方确认了"和我共享密钥的是对方本人"。Eve 要想不被发现，就得同时控制这通电话，而认得出声音让这一点很难做到。

2. 身份识别协议：从明文口令到挑战–应答

2.1 访问控制的第一步：确认对方是谁 (S6)

S6 的标题是访问控制 (Access Control)。第 4 周 §5.1 讲过，访问控制有两道关：认证 (authentication) 回答"你是谁"，授权 (authorization) 回答"你能做什么"。这一部分只看第一道关，而且看得很细：客户端怎样通过一串消息向服务器证明自己的身份。完成这件事的协议叫识别协议 (identification protocol)，slides 说的 identification 就是第 4 周说的（对实体的）认证。

老师先交代了为什么要从头设计：设计协议时，不能一上来就说"反正一切都用 HTTPS 加密"，有时 HTTPS、SSL 根本用不了。所以这一部分的场景是：Alice 是客户端，Bob 是服务器，Alice 想登录；两人之间的线路没有任何保护，攻击者能看到每一条消息。

先认识 slides 里的记号。每个协议都画成两栏，上方写着双方各自事先持有什么：

  • Alice : (Alice, pw)：Alice 知道自己的用户名 Alice 和口令 pw；
  • Bob : (Alice, pw)：Bob 的数据库里有一条记录，用户 Alice、口令 pw（后面的协议会改变 Bob 存的东西）；
  • pw′：Alice 这一次输入的口令。课上有同学问 pw′ 是不是加密后的口令，老师解释：不是，它就是你这次敲进去的东西，可能输错（真口令是 12345，你手滑敲成 1234），所以要和数据库里的 pw 比一比；
  • H(⋅)H(\cdot)：密码学哈希函数（第 2 周 §1.4）：正着算很快，倒着推不可行，同样的输入永远得到同样的输出。H(r,pw)H(r, pw) 表示把 rr 和 pwpw 放在一起算一个哈希，比如先拼接再哈希；
  • r∈{0,1}nr \in \{0,1\}^n：一个随机选出的 nn 位比特串。

这些协议要防的头号攻击，S8 给了定义：冒充攻击 (impersonation attack) 是指攻击者成功顶替了系统或通信协议中某个合法参与方的身份 (an attack in which an adversary successfully assumes the identity of one of the legitimate parties in a system or in a communications protocol)。S8 括号里的解释最直白：攻击者以 Alice 的身份登录。标准的攻击套路是：先偷听 Alice 的一次正常登录，把消息录下来，再拿录到的东西去冒充她。

后面每看一个协议，都问同样几个问题。它们是一步步加进来的：

角度 问题 从哪个协议开始问
冒充 偷听者录下消息后，能不能以 Alice 的身份登录？ 协议 1
口令泄露 偷听者能不能从消息里得到、或者猜出 Alice 的口令？ 协议 2
数据库泄露 服务器的数据库被偷了，攻击者能得到什么？ 协议 5
匿名 偷听者能不能知道是谁在登录？ 协议 7
效率 服务器认出一个用户，要做多少计算？ 协议 7

2.2 协议 1：直接发送口令 (S7, S8)

S7 是 slides 里"最简单的识别协议"（The simplest Identification Protocol）：

Alice : (Alice, pw) 消息 Bob : (Alice, pw)
(Alice,pw′)(Alice, pw') →
1. 若 pw′=pwpw' = pw，Alice 通过验证

S7 的问题：解释这个协议为什么不好。S8 给出三点：

  1. 冒充攻击（定义见 §2.1）；
  2. 敏感信息以明文传输，没有任何保护 (Sensitive information is transmitted in plaintext without protection)；
  3. 攻击者能拿到用户名和口令，然后发起冒充攻击 (The adversary can obtain the username and pw, and then launch the impersonation attack)。

老师的讲法是：坐在中间的人看到 Alice 和口令，下一次就能自己用。这里攻击者甚至不需要"重放"什么，他拿到的就是口令本身，想登录几次就登录几次。

课上有同学先指出了另一个问题，老师说这是第一点：服务器存的是明文口令。Bob 的数据库一旦泄露，所有用户的口令一起泄露。而很多人在不同网站用同一个口令，泄露的危害会扩散到别的网站去。记住这一点，协议 5 会专门处理"服务器该存什么"。

2.3 协议 2：发送口令的哈希 (S9–S12)

协议 1 的毛病是口令在线路上裸奔。最直接的修补是：不发口令，发口令的哈希。

Alice : (Alice, pw) 消息 Bob : (Alice, pw)
1. 计算 H=H(pw)H = H(pw)
(Alice,H)(Alice, H) →
2. 若 H=H(pw)H = H(pw)，Alice 通过验证

老师问：现在线路上还有敏感信息吗？没有了，中间人只能拿到用户名和口令的哈希值。S9 接着问了三个问题：这个协议在识别上安全吗？它比协议 1 更安全吗？它比协议 1 好在哪里？

问题 1：安全吗？不安全。S10 的答案是：攻击者拿到 (Alice, H(pw)) 之后，仍然可以发起冒充攻击 (the adversary can still launch the impersonation attack after obtaining (Alice, H(pw)))。原因在 Bob 的检查方式：他只核对收到的值是不是等于 H(pw)H(pw)，至于发送方是敲了口令再算出哈希，还是直接贴上一段录来的哈希，他分辨不出。哈希变成了新的口令：谁手里有 H(pw)H(pw)，谁就能登录。

课上有同学不同意：攻击者知道哈希，却不知道口令；他把哈希填进登录框，系统会把它再哈希一次，结果就不对了。老师说，这要看攻击者走哪条路。服务器需要收到的只是"用户名 + 哈希"，它并不在乎这两个值是怎么来的。攻击者完全可以绕过登录页面，把这两个值直接发给服务器。

🔑 例：绕过登录页面（老师的课堂演示） — 假设一个网站这样实现协议 2：你在登录页敲入口令，点"登录"，浏览器里的脚本先把口令算成哈希，再把用户名和哈希发出去。老师打开浏览器的开发者工具（按 F12），在网络面板里找到了这条发出去的 POST 请求，大致长这样：

POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=alice&hash=ef797c8118f02dfb…a898a64f

攻击者偷听到这一条，就可以用开发者工具或任何能发 HTTP 请求的命令行工具，原样再发一次，根本不经过登录框，自然也不会被"再哈希一次"。服务器核对通过，回复"登录成功"，把他带到 Alice 的个人主页。

问题 2：比协议 1 更安全吗？不。S10：它挡不住冒充攻击，所以和协议 1 一样不安全 (Since it cannot withstand the impersonation attack, this protocol is as insecure as the first one)。只看"能不能被冒充"，两者没有区别。

问题 3：好在哪里？S11 的答案是：攻击者能从偷听中拿到 H(pw)H(pw)，但要从 H(pw)H(pw) 破解出 pw 需要时间；换句话说，攻击者不能靠偷听立刻得到 Alice 的口令 (the adversary cannot immediately get Alice's pw from the eavesdropping)。这一点有实际意义：协议 2 被攻破，丢的是 Alice 在 Bob 这里的登录；而口令本身没有直接暴露，Alice 在别的网站用的同一个口令，暂时还是安全的。

S11 的措辞很谨慎："需要时间"，"不能立刻得到"。哈希明明是单向的，为什么只是"需要时间"，而不是"永远得不到"？S11 的最后一个词给了答案：字典攻击 (dictionary attack)。

S12 的定义：字典攻击是一种暴力破解技术，它通过尝试成百上千、有时上百万个可能的口令，来确定真正的口令 (a form of brute force attack technique by trying to determine its passwords by trying hundreds or sometimes millions of likely possibilities)。具体到协议 2：攻击者可以为所有可能的口令预先算好一个 (pw, H(pw)) 的数据库，也就是字典；有了它，就能很快破解口令。S12 把这叫作离线字典攻击 (offline dictionary attack)。

关键在于，字典攻击根本不去逆转哈希。哈希正着算很快，攻击者就挑可能的口令一个个正着算，再看哪个结果对得上。单向性只保护难猜的输入；人类选的口令偏偏很好猜。

🔑 例：一本小字典 — 攻击者事先算好一批常见口令的 SHA-256（笔记作者实际运行的结果，只列前 16 位）：

口令 pw H(pw)H(pw) = SHA-256(pw)

某天她偷听到 Alice 的登录消息：(Alice, ef797c8118f02dfb649607dd5d3f8c7623048c9c063d532cc95c5ed7a898a64f)。一查表，第二行：Alice 的口令是 12345678。整个过程没有"倒推"哈希，只查了一张正着算好的表。

老师坦白说，他自己的一些口令就很简单，比如 12345678，因为好记。他接着指出这样做的另一个后果：同样的输入一定得到同样的输出。如果我用 12345678，你也用 12345678，数据库里我们俩的哈希值一模一样；很多人都用 12345，所以这些哈希很容易被反查出来。

课上有同学说：公司数据泄露以后，常常发公告说"放心，你的口令是哈希（加密）过的"，看来这其实还是个问题？老师说：还是个问题。即使公司存的是哈希值，攻击者仍然有办法找出口令，字典攻击就是一种。

老师还讲了字典从哪里来、有多好用：

  • 现成的字典：有人把历次数据泄露中的真实口令整理成字典，在暗网之类的地方就能下载到。老师说，他的有些口令其实挺复杂，不知为什么还是被收进了字典，只好又改了一遍。
  • 他自己的经历：大约 2013、2014 年，不是家家都有 Wi-Fi，想蹭邻居的网就得攻击。攻击之后能拿到的是 Wi-Fi 口令的哈希。他手里有一本"弱口令字典"，大约 10 GB，第一步先用它试；不行再换基于真实案例整理的字典，还收集过生日、手机号这类口令。当时很多人就用 12345678 这样的口令，命中的可能性很高。他特别指出 Wi-Fi 和协议 2 的不同：光有哈希连不上 Wi-Fi，必须找到真正的口令；而在协议 2 里，哈希本身就能用来登录。
  • 为什么这么快：在网站登录框上一个个试，大概每次要两秒，输错五次账户就被锁 30 分钟或一小时；可一旦拿到了哈希，就能在自己的电脑上用 GPU 试，老师估计每秒能试上万次。

有同学问：如果口令熵很高、非常复杂，预先算字典还有用吗？老师说，他的做法是先下载现成的字典，口令不在里面，他就放弃了。理论上可以为一个很复杂的口令构造一本包含它的字典，但那本字典可能有几十、上百 TB，他的电脑根本放不下。所以他的建议是：真正重要的东西，用随机生成的口令；缺点是根本记不住。（第 7 周的录音里他接着讲了解决办法：口令管理器，见 §2.7。）

📎 拓展(超出 slides)：攻击者怎么知道用的是哪种哈希 — 课上有同学问了这个问题。摘要的长度能缩小范围：SHA-1 是 160 位（40 个十六进制字符），SHA-256 是 256 位（64 个）。但长度相同的不一定是同一种算法，同学自己举了反例：SHA-256 和 SHA3-256 都输出 256 位。办法也是同学想到的：拿一个已知口令（比如在这个网站注册时自己设的），用几种候选算法各算一遍，看哪个对得上。正规的系统都用标准算法，所以候选并不多。课上顺带说到 SHA-1"已经不太安全"：被攻破的是它的抗碰撞性，人们能找到两个不同的输入得到同一个摘要（第 2 周 §1.4）；至于从摘要倒推出原来的输入，至今仍然做不到。老师用 7-Zip 算了一遍这周 PPT 文件的各种哈希来演示：别人能找到另一个摘要相同的文件，却恢复不出他的 PPT。对口令来说，真正的威胁一直是"猜"，不是碰撞。

自测：Eve 偷听到协议 2 的一条消息 (Alice, 5e884898da28047151d0e56f8dc6292773603d0d6aabbdd62a11ef721d1542d8)。她能做哪两件事？哪一件需要字典？

第一，原样重放这条消息，以 Alice 的身份登录 Bob（冒充攻击，S10），不需要知道口令，也不需要字典。第二，用字典查这个哈希：上面的例子里它对应 password，于是她得到了口令本身，可以去试 Alice 的其他账户。第二件事需要字典，而且只在 Alice 的口令足够常见、收在字典里时才成功（S11–S12）。

2.4 协议 3：加一个随机数（盐）(S13–S15)

协议 2 的字典之所以好用，是因为同一个口令永远对应同一个哈希，一本字典可以提前算好、反复使用。协议 3 往哈希里掺进一个随机数，打破这种对应：

Alice : (Alice, pw) 消息 Bob : (Alice, pw)
1. 随机选 r∈{0,1}nr \in \{0,1\}^n
2. 计算 H=H(r,pw)H = H(r, pw)
(Alice,r,H)(Alice, r, H) →
3. 若 H=H(r,pw)H = H(r, pw)，Alice 通过验证

S13 的图题说这个随机数是一个盐 (salt)：混进哈希输入里的一段随机值，让同一个口令每次算出不同的哈希。rr 本身不保密，它和哈希一起发给了 Bob，因为 Bob 也要用它重算一遍。S13 问了和协议 2 一样的三个问题，这次是和协议 2 比。

问题 1：安全吗？不安全。S14：攻击者拿到 (Alice, H(r, pw)) 之后，仍然可以发起冒充攻击 (the adversary can still launch the impersonation attack after obtaining (Alice, H(r,pw)))。S14 括号里有一句 "The adversary cannot change r here"，意思是：攻击者不知道口令，没法为一个新的 rr 算出对应的哈希，他只能沿用录到的那个 rr；可是沿用就够了，因为 rr 是 Alice 选的，Bob 对收到哪个 rr 照单全收。把录到的 (Alice,r,H)(Alice, r, H) 原样重放，Bob 重算 H(r,pw)H(r, pw)，结果对得上。课上同学一眼就看出来了："这不就和上一个一样吗？攻击者知道 r 啊。"老师说：对。

问题 2：比协议 2 更安全吗？不。S14：它挡不住冒充攻击，所以和协议 2 一样不安全 (as insecure as the protocol 2)。

到这里可以把协议 1、2、3 放在一起看了。它们的消息内容不同，失败的原因却完全相同：Alice 发出的消息不依赖任何"新鲜"的、由 Bob 决定的东西，所以录下来的消息永远有效。图 4 画的是这种重放攻击 (replay attack)。

问题 3：好在哪里？表格最后一列的区别，就是协议 3 相对协议 2 的进步。S15 分两步说：

  • 协议 2 那种 (pw, H(pw)) 的数据库，现在用不上了，因为 H(r,pw)H(r, pw) 里有一个随机的盐。字典里存的是"口令 → 不加盐的哈希"，和录到的值对不上。
  • 假设攻击者偷听到了 (r,H(r,pw))(r, H(r, pw))，他需要的是一个针对 Alice 选定的这个 rr、包含所有可能口令的 (pw, H(r, pw)) 数据库；有了它，才能破解口令。S15 把这叫作在线字典攻击 (online dictionary attack)，并且用红字强调：这个数据库不能用来破解另一个 rr 下的口令 (This database cannot be used to crack pw with a different r)。

老师的说法是：你的字典里只有"口令 → 哈希"，没有随机数；你当然可以再做一本新字典，可你得把那个随机数放进去，而且换一个随机数，就得再做一本。

要小心的是，这和业界的常见用法不一样，老师课上闲聊时用的恰恰是常见用法：在线是对着正在运行的服务器一个个试（会被限速、锁账户），离线是拿到哈希后在自己的电脑上算（不限次数、很快）。按常见用法，协议 3 的攻击者也是"离线"的：他在自己的电脑上为 rr 现算字典，根本不用碰服务器。两种用法说的是两件不同的事：slides 关心"字典能不能提前算、能不能复用"，常见用法关心"要不要和服务器交互"。答题时按 slides 的用法写，同时知道外面的人说这两个词时多半是另一个意思。

盐的边界。盐不会让一个弱口令变强。如果 Alice 的口令是 12345678，攻击者为她的 rr 现算一本字典，试到第二个口令就找到了，花的工夫和协议 2 几乎一样。盐真正消灭的是两样东西：提前计算（必须先看到 rr 才能开工）和一本字典通吃所有人。粗略算一笔账：字典有 10710^7 个候选口令，网站有 10510^5 个用户。不加盐时，算 10710^7 次哈希，就能把所有用了常见口令的人一网打尽，而且可以在偷到数据之前就算好；加了盐，每个用户都要单独算 10710^7 次，一共 101210^{12} 次，而且只能在看到每个人的盐以后开始。攻击者的总工作量乘上了用户数。

📎 拓展(超出 slides)：现实中服务器怎样存口令 — 协议 3 的盐是登录时临时选的；真实系统更常见的用法是在服务器端存储口令时加盐：注册时为每个用户生成一个随机的盐，数据库里存 (盐, H(盐, pw))。盐不保密，就放在哈希旁边，作用和 S15 说的一样，让一本字典没法通吃整个数据库。第二个配套措施是故意慢的哈希：像 SHA-256 这样为速度设计的哈希，一块现代 GPU 每秒能算数十亿次以上，远超老师课上估的"每秒上万次"；所以存口令要用 PBKDF2、bcrypt、scrypt、Argon2 这类可以调节计算量的函数。第 3 周 §3.8 讲过 BIP39 用 PBKDF2 做 2048 轮 HMAC，正是为了让每一次猜测都付出同样的代价。

自测：Alice 用协议 3 登录了两次，分别选了两个不同的随机数，Eve 都录了下来。① 她能重放哪一次？② 想破解 Alice 的口令，她最少要算几本字典？③ 如果 Alice 的口令是一个 20 位的随机字符串呢？

① 两次都能重放：rr 是 Alice 选的，Bob 对任何 rr 都照单全收（S14）。② 一本就够：随便挑一次，比如为第一次的随机数 r1r_1 算一本 (pw,H(r1,pw))(pw, H(r_1, pw)) 的字典；破解出来的口令对两次都适用。盐让她不能用提前算好的字典，但没有阻止她为一个具体的 rr 现算一本（S15 的 online dictionary attack）。③ 那就破解不了：随机口令根本不在任何字典里，可能性多到算不完。可她依然能重放登录，协议 3 的冒充问题和口令强弱无关。

2.5 协议 4：让 Bob 出随机数，挑战–应答 (S16, S17)

图 4 指出了协议 1–3 的病根：消息里没有新鲜的东西。协议 4 只改了一处，随机数改由 Bob 来选（S16 的图题：Using a Random Salt Chosen by Bob）：

Alice : (Alice, pw) 消息 Bob : (Alice, pw)
1. 随机选 r∈{0,1}nr \in \{0,1\}^n
← rr
2. 计算 H=H(r,pw)H = H(r, pw)
(Alice,H)(Alice, H) →
3. 若 H=H(r,pw)H = H(r, pw)，Alice 通过验证

这种结构叫挑战–应答 (challenge–response)：验证方先发一个新鲜的随机数，叫挑战 (challenge)；证明方用挑战和自己的秘密算出应答 (response)。只有知道秘密的人，才能对一个从没见过的挑战给出正确的应答。

S16 问了两个问题。

问题 1：如果攻击者不能从通信中算出口令，这个协议安全吗？安全。S17 的解释是：即使攻击者偷听到了 rr 和 H(r,pw)H(r, pw)，也不能再用一次，因为攻击者冒充 Alice 时，Bob 给的 rr 会不一样；对一个不同的 rr，攻击者必须算出 H(r,pw)H(r, pw)，而不知道口令，他就答不对，冒充攻击也就不成立 (Without knowing pw, the adversary cannot respond correctly and hence the impersonation attack cannot work)。老师的话更短：你没法再登录一次，因为 rr 是 Bob 给的。图 6 是 Eve 的失败尝试。

问题 2：如果 Bob 选的 rr 总是同一个，还安全吗？不安全。S17：一旦攻击者偷听到 rr 和 H(r,pw)H(r, pw)，冒充攻击就能成功。rr 固定不变，应答也就固定不变，协议退回成"协议 2 加一个固定前缀"，录下来就能重放。老师说：rr 不变，就和前面的一样了。所以挑战的价值全在新鲜：每次都不同，攻击者事先也猜不到。S22 后来补了一句"rr 要足够长"，原因在下面的自测里。

📎 拓展(超出 slides)：挑战为什么还要"猜不到" — 这种只用一次的随机数常叫 nonce（number used once）。光"不重复"还不够，还得不可预测。注意协议 4 里只有 Alice 证明自己，Bob 并不证明自己是 Bob：谁给 Alice 发一个 rr，她都会老老实实地算出应答。如果 Eve 能猜到 Bob 下一次的挑战 r*r^*，她就可以先冒充 Bob 去问 Alice，拿到 H(r*,pw)H(r^*, pw)，等 Bob 真的发出 r*r^* 时再交上去。协议 4–7 都是这样的单向认证 (one-way authentication)，§3.3 会看到同样的单向性在 GSM 里造成了什么后果。

问题 1 的前提值得再读一遍：如果攻击者不能从通信中算出口令。偷听者手里仍然有一对 (r,H(r,pw))(r, H(r, pw))。Alice 的口令要是很弱，攻击者就为这个 rr 现算一本字典（S15 的 online dictionary attack），猜出口令以后，对任何新的 rr 都能算出正确应答，冒充又成立了。所以协议 4 防住了重放，没有防住猜口令。另外，Bob 要算 H(r,pw)H(r, pw)，就得知道 pw，他的数据库里存的还是明文口令。剩下的这两个问题，协议 5 和协议 6 各解决一个。

讲完协议 4，老师把前四个协议串成了一段历史：这四个协议就是网站登录安全的演进过程。很久很久以前，网站直接存你的口令，每次登录你把用户名和口令原样交上去；后来发现不安全，就改成哈希；还是不安全，又加了随机数。

自测：Bob 的挑战 r 只有 8 位（只有 256 种可能），但每次都随机选。Eve 能做什么？

Eve 可以长期偷听，把见过的 (r,H(r,pw))(r, H(r, pw)) 都记下来。只有 256 种挑战，用不了多少次，她就攒齐了大部分；以后 Bob 发出的挑战一旦落在她的记录里，她就把对应的旧应答交上去，冒充成功。这就是 S22 要求"rr 足够长"的原因：nn 很大时，同一个挑战几乎不会出现两次，记录攒得再多也用不上。

2.6 协议 5：服务器只存 H(Alice, Bob, pw) (S18–S20)

协议 4 的 Bob 存着明文口令。协议 5 改的正是 Bob 存的东西：

Alice : (Alice, pw) 消息 Bob : (Alice, H(Alice, Bob, pw))
1. 随机选 r∈{0,1}nr \in \{0,1\}^n
← rr
2. 计算 H=H(r,H(Alice,Bob,pw))H = H\big(r, H(Alice, Bob, pw)\big)
(Alice,H)(Alice, H) →
3. 若 H=H(r,H(Alice,Bob,pw))H = H\big(r, H(Alice, Bob, pw)\big)，Alice 通过验证

为了说话方便，记 V=H(Alice,Bob,pw)V = H(Alice, Bob, pw)。Bob 的数据库里只存 VV，不再存 pw。Alice 每次登录时用自己的用户名、服务器的名字和口令，现场算出 VV，再算 H(r,V)H(r, V)。协议的运行方式和协议 4 一模一样，只是 pw 的位置换成了 VV。

S18 问了三个问题：它比协议 4 好在哪？如果 H(Alice,Bob,pw)H(Alice, Bob, pw) 里没有 Alice 呢？没有 Bob 呢？Week 6 的课就停在这里，老师说"有点复杂，想一想，下次回答我"；Week 7 一开课就公布了答案。

好在哪（S19）。① 即使服务器的数据库被攻破，攻击者也不能立刻从中得到用户的口令 (Even the server's database is cracked, the adversary cannot immediately obtain pw of users from the database)；② 攻击者必须为每个用户分别发起 online dictionary attack，因为用户名各不相同 (must launch an online dictionary attack to crack the password for EACH user because the usernames are distinct)。第 ② 条的道理和协议 3 的盐一样：Alice 的 VV 里有 "Alice"，所以猜她的口令要用一本 pw → H(Alice,Bob,pw)H(Alice, Bob, pw) 的字典；这本字典对 Carol 无效，Carol 要另算一本。用户名在这里起到了盐的作用。

去掉 Alice（S20）。V=H(Bob,pw)V = H(Bob, pw)。攻击者可以用 offline dictionary attack 代替 online dictionary attack，一个数据库就足以破解所有口令 (One database is enough to crack all passwords)。Bob 这台服务器上所有用户共用同一个函数 pw → H(Bob,pw)H(Bob, pw)，Bob 的名字又是公开的，攻击者可以提前把字典算好，数据库一到手就整库查表；口令相同的两个用户，存的值也一模一样。

去掉 Bob（S20）。V=H(Alice,pw)V = H(Alice, pw)。如果用户在别的服务器上用了同样的用户名和口令，攻击者就能在那些服务器上冒充这些用户；slides 的注释是 H(Alice,pw)H(Alice, pw) 在所有服务器上都一样。要理解这一条，得先看清协议 5 里应答是怎么算出来的：H(r,V)H(r, V) 只需要 VV，不需要 pw。谁拿到了 VV，谁就能回答任何挑战。如果 VV 里没有服务器的名字，Alice 在每个网站上存的 VV 都相同；攻击者从防护最差的那个网站偷到 VV，不用破解口令，就能在所有她复用了用户名和口令的网站上登录。老师说这种情况非常普遍：我们很多人在各处都用同一套用户名和口令。把 Bob 的名字放进去，VV 就和服务器绑定了，从 Bob 那里偷到的 VV 在 Dave 那里毫无用处。

2.7 协议 6：用对称密钥代替口令 (S21, S22)

协议 4、5 防住了重放，剩下的软肋是口令本身能被猜。协议 6 干脆把口令换掉：

Alice : (Alice, K) 消息 Bob : (Alice, K)
1. 随机选 r∈{0,1}nr \in \{0,1\}^n
← rr
2. 计算 H=H(r,K)H = H(r, K)
(Alice,H)(Alice, H) →
3. 若 H=H(r,K)H = H(r, K)，Alice 通过验证

KK 是 Alice 和 Bob 共享的一把对称密钥。S21 对它的评价很高：这是标准的安全识别协议 (This is the standard secure identification protocol)。它要你解释：为什么它比之前所有的协议都好？S22 的答案：

  1. 用的是对称密钥；不存在能破解这把密钥、再拿去冒充的字典攻击 (There is no dictionary attack, which can crack the secret key for impersonation attack)；
  2. 只要 rr 和 KK 足够长，只要 KK 保密，这个协议就是安全的 (When r and K are long enough, the protocol is secure as long as K is kept secret)。

老师的讲法是：这就像把你的口令换成了一把密钥。对口令版本来说，只要 Bob 每次都选新的随机数、而不是固定的数，协议就是安全的；把口令换成对称密钥，就更安全了。

课上有同学问到了点子上：协议 6 和协议 4 的消息格式一模一样，唯一的区别就是口令换成了密钥，这就更安全了？老师说：对，密钥比口令复杂得多。区别全在"能不能被猜"：人选的口令落在几百万、几千万个常见候选里；一把随机生成的 128 位密钥有 2128≈3.4×10382^{128} \approx 3.4 \times 10^{38} 种可能，没有哪本字典装得下。反过来，老师也提醒：如果 KK 很短，比如 123456，那它和口令没有任何区别。S22 那句"足够长"就是这个意思。

同学接着说：可我记不住密钥啊。老师当场找了一把对称密钥给大家看，一长串毫无规律的字符，问："你记得住吗？"记不住。所以密钥一般不靠人记，而是存在设备里：

  • SIM 卡和银行卡的芯片：老师说，你在超市刷卡时，卡里的芯片藏着一把密钥；§3 的 GSM 用的就是 SIM 卡里的密钥；
  • 口令管理器：老师举了 1Password 和 Google 口令管理器的例子。你存的那些口令，被一把你从没见过的 AES 密钥加密保存；你只需要记住一个主口令，用它打开那把密钥，再由密钥解开其余的口令。他的总结是：对人来说，我们仍然在用口令保护那些复杂的东西。

老师还补充了两点。第一，这把对称密钥只用来做认证；要加密后面的消息，双方会另外协商一把密钥（比如 §1 的 DH）。一把密钥只做一件事，泄露了也只影响一件事。第二，协议 6 里服务器存的就是 KK 本身，不是哈希；一旦服务器被攻破，你的密钥也就泄露了。§2.9 会回到这一点。Google、Facebook 这样的网站登录仍然基于口令；协议 6 这类做法更多用在设备认证上，老师举的例子是：某个服务要认证的不是你这个人，而是你的手机。

📎 拓展(超出 slides)：H(r,K)H(r, K) 就是一个 MAC — 用一把共享密钥对消息 rr 算出一个标签，这正是第 4 周 §3.5 讲的消息认证码 (MAC)。实际系统不会直接把 rr 和 KK 拼起来再哈希，而是用专门为带密钥的哈希设计的 HMAC，比如 HMAC-SHA256(K,r)(K, r)；直接拼接在某些哈希函数上有已知的弱点。协议的逻辑不变：挑战新鲜，密钥保密，应答就无法伪造。

自测：协议 4 和协议 6 在线路上传的消息格式完全相同。为什么 S22 说协议 6"不存在字典攻击"，而协议 4 的偷听者可以做字典攻击？

字典攻击靠的是"秘密落在一个可以列举的小范围里"。协议 4 的秘密是人选的口令，常见的就那么几百万个，攻击者拿偷听到的 (r,H(r,pw))(r, H(r, pw)) 一个个试，弱口令很快就会被试出来。协议 6 的秘密 KK 是随机生成的长密钥（比如 128 位），可能性多到列举不完，没有字典能覆盖它。前提是 KK 真的够长、够随机：如果 KK = 123456，它就和口令一样能被猜出来。

2.8 协议 7：匿名识别 (S23, S24)

协议 6 已经很安全了，协议 7 又改了一处：Alice 不再发送用户名，而是把它放进了哈希。

Alice : (Alice, K) 消息 Bob : (Alice, K)
1. 随机选 r∈{0,1}nr \in \{0,1\}^n
← rr
2. 计算 H=H(r,Alice,K)H = H(r, Alice, K)
HH →
3. 若 H=H(r,Alice,K)H = H(r, Alice, K)，Alice 通过验证

S23 的问题：和协议 6 相比，这个协议的动机是什么？再分析它的缺点。

动机（S24）：匿名识别 (anonymous identification)。偷听通信的攻击者不知道被识别的是谁 (the adversary who is eavesdropping the communication cannot know who is being identified)。老师对比了两个协议里偷听者能看到什么。协议 6 里，线路上有用户名 Alice 和哈希值：攻击者冒充不了你，但他知道你是 Alice，知道你哪天、几点在登录哪个网站（比如微软的服务器）。这也许是你的隐私，也许你不在乎；可对攻击者来说，这是他能拿到的一份私人信息。协议 7 里，线路上只有两样东西：随机数 rr 和哈希值 HH，没有用户名。在攻击者眼里，这两样都像一串随机数，他根本不知道你是谁。

📎 拓展(超出 slides)：连"是不是同一个人"都看不出 — 因为 rr 每次都是新的，同一个 Alice 每次登录发出的 HH 也都不同。偷听者不仅不知道是谁，连"这两次登录是不是同一个人"都判断不了，这叫不可关联性 (unlinkability)。如果 rr 固定，Alice 每次都发出同一个 HH，偷听者虽然不知道她叫什么，却能认出"又是这个人"，长期跟踪下来，名字往往也就猜到了。

缺点（S24）：识别效率低。 Bob 收到 HH 时也不知道对方是谁。不知道身份，服务器只能拿每个用户的密钥逐一试，直到找到对的那个用户；服务器有 nn 个用户，最坏情况下要把第 3 步的哈希算 nn 次，而 nn 可能是 10,000 (The disadvantage is the inefficient identification)。用户名并没有消失，它从明文搬进了哈希：Bob 逐个试的，正是"用户名 + 这个用户的密钥"这一对。图 7 画出了 Bob 的搜索。

🔑 例：搜索要花多少时间 — 笔记作者用 Python 实测，为 10,000 个用户各算一次 SHA-256，一共约 3 毫秒，平均每次约 0.3 微秒。于是：

用户数 nn 每次登录最坏要算的哈希 大约耗时（同一台电脑）
50（老师说的小团队） 50 可以忽略
10,000（S24 的例子） 10,000 约 3 毫秒
1 亿（一个大型网站） 10810^8 约 30 秒

平均情况要试一半用户，也是和 nn 成正比。每一次登录都要付这笔账，同时登录的人越多，服务器越吃不消。协议 6 无论有多少用户，都只算 1 次。

老师的评价是：更安全，但低效。有同学问实际中用不用它，老师说它不能扩展 (not scalable)，不是给实际使用的，只是拿来让我们分析的；不过如果你的服务器只服务一个小团队，比如 50 个人，最坏也就算 50 次哈希，很快，用它没问题。

还有一条边界：协议 7 只对偷听者匿名，对 Bob 不匿名，Bob 搜索结束就知道是谁了，他也必须知道，否则没法授权。网络层的信息（比如 IP 地址、登录时间）也可能暴露身份，那是协议之外的事。§3.5 会看到 GSM 怎样用一个"临时身份"做到对偷听者匿名，同时让服务器一步查到你是谁。

自测：服务器有 n = 10,000 个用户，用户在表里的位置是随机的。用协议 7，平均每次登录要算多少次哈希？为什么协议 7 的匿名性同样依赖"r 每次都新选"？

平均要试一半，约 5,000 次；最坏 10,000 次（S24）。如果 rr 固定，同一个用户每次发出的 H=H(r,Alice,K)H = H(r, Alice, K) 都一样，偷听者虽然不知道她的名字，却能认出"又是这个人"，并持续跟踪；而且固定的 rr 还会让重放重新成立（§2.5）。新鲜的 rr 让每次的 HH 都不同，同时守住了防重放和不可关联两件事。

2.9 协议 8 和 9：用公钥识别 (S25–S27)

协议 6 和 7 都有一个共同的前提：Alice 和 Bob 共享同一把密钥，所以服务器手里也有你的密钥。最后两个协议换用公钥密码学（第 4 周 §3.3）：Alice 持有一对密钥 (pk,sk)(pk, sk)，Bob 只存 Alice 的公钥 pkpk。老师说，Alice 事先把自己的公钥放到了服务器上。

协议 8：基于公钥加密的识别 (Public-Key Encryption Based ID，S25)。

  1. Alice → Bob："Hi, I am Alice"；
  2. Bob 选一个随机数 rr，用 Alice 的公钥加密：C=E(pk,r)C = E(pk, r)，把 CC 发给 Alice；
  3. Alice 用私钥解密 CC，把得到的 r′r' 发回；
  4. Bob 检查 r′=rr' = r。

只有持有私钥 sksk 的人才能把 CC 解回 rr。如果对面真是 Alice，r′r' 当然等于 rr。

协议 9：基于签名的识别 (Signature Based ID，S26)。

  1. Alice → Bob："Hi, I am Alice"；
  2. Bob 选一个随机数 rr，发给 Alice；
  3. Alice 对 rr 签名，得到 Sig_r，发回；
  4. Bob 验证 Sig_r 是不是对 rr 的有效签名。

签名只有私钥持有者做得出来，任何人都能用公钥验证（第 3 周 §1.3）。

两个协议都还是 §2.5 的挑战–应答，只是"应答"的算法换了：协议 8 的应答是解密，协议 9 的应答是签名。随机数仍然由 Bob 来选，所以重放照样不成立。

换成公钥，得到了什么？ 老师说，如果你让他设计一个更安全的系统、又不在乎复杂度，他会选协议 8，而不是 6 或 7。理由是服务器存什么：协议 6、7 里，服务器存着你的对称密钥，服务器一旦被攻破，你的密钥也就泄露了；协议 8 里，你只把公钥交给服务器，黑客就算攻破了服务器，拿到的也只是你的公钥，私钥始终在你自己手里。从这个角度看，协议 8 比 6 和 7 更安全。另外，公钥方案用的是 RSA、ECDSA 这类标准密钥，不可能"短到能猜"，字典攻击无从谈起。第 5 周 §3.2 的 SSH 公钥登录，本质上就是协议 9：客户端用私钥对和本次会话绑定的数据签名，服务器用 authorized_keys 里的公钥验证。

它依赖什么？ 课上有同学问：协议 8 能解决 §1.4 DH 的中间人问题吗？老师说：不能，它只解决认证这一部分，而且这里假设我们已经有一个安全的办法把公钥放到服务器上，比如用 U 盘把公钥拷过去。这个假设正是 §1.4 留下的问题："Bob 怎样确认这把公钥真是 Alice 的？"如果 Eve 能在注册时把 Bob 存的 pkpk 换成自己的，协议 8、9 就会忠实地认证 Eve。下周的证书就是来回答这个问题的。

S27：匿名吗？ S27 把两个协议并排放在一起，问了两个问题：

  1. 攻击者能知道被识别的是谁吗？能。两个协议的第一条消息都是明文的"Hi, I am Alice"，Bob 也需要这个名字来决定用谁的公钥。老师说：这两个都不匿名，因为你得报上用户名。
  2. 怎样改进？老师留给大家自己想，课上没有给答案。

📎 拓展(超出 slides)：S27 第二问的两种思路 — 思路一：学协议 7，把名字藏起来。协议 9 可以不报名字，Bob 收到签名后拿每个注册用户的公钥逐个验证，直到有一个通过。匿名了，代价和协议 7 一样：最坏要做 nn 次验证，而验签比算哈希慢得多。协议 8 就难办了：Bob 加密之前必须先决定用谁的公钥。思路二：先建加密通道，再在里面报名字。先用 §1 的 DH 和对方协商出一把会话密钥（服务器用证书证明自己，防住中间人），再把"Hi, I am Alice"和整个识别过程放进加密通道里。偷听者只看到密文，Bob 却能直接按名字找到公钥，一步完成。现实系统基本都这样做：第 5 周 §2.1 的 SSH，第 ④ 步用户认证发生在加密通道建好之后；TLS 1.3 连客户端证书都加密传输。这样，§1 的密钥协商和 §2 的身份识别就合在了一起。

📎 拓展(超出 slides)：Alice 不该"有求必应" — 协议 8 里，Alice 对收到的任何 CC 都会解密，再把明文交出去；协议 9 里，她对收到的任何 rr 都会签名。攻击者如果冒充 Bob，就能把从别处截获、加密给 Alice 的一段密文当成 CC 发给她，骗她解开；或者把一份合同的哈希当成 rr，骗到她对这份合同的签名。常见的对策有两个：识别用的密钥对不做别的事；只对带固定格式的数据签名，比如"登录 Bob：rr"。第 5 周 §3.2 说过，SSH 签的正是和本次会话绑定的数据。

自测：服务器的数据库被整个偷走了。分别用协议 6 和协议 8 的系统，攻击者能不能用偷到的东西冒充用户？

协议 6：能。数据库里存的就是每个用户的对称密钥 KK，攻击者用 KK 就能回答任何挑战。协议 8：不能。数据库里只有公钥 pkpk，回答挑战需要私钥 sksk 才能解开 CC，而私钥从没交给过服务器。这就是老师更喜欢协议 8 的原因。（攻击者如果还能改数据库，把某个用户的 pkpk 换成自己的，那就另当别论了，这又回到了"公钥属于谁"的问题。）

课上有同学问：9 是不是最新、最安全的版本？老师纠正了这种"升级"的看法。从协议 1 到 7，确实是从不安全到安全、再到"更安全但低效"；从协议 4 开始，口令版本已经算是安全的做法了；从协议 6 开始，不再用口令，协议 6 是标准做法。但 8 和 9 不是 7 的升级，而是另一类协议，没法说哪一个是最好、最安全的：密钥很短时，协议 6、7 并不比口令强；8、9 用的是标准的 RSA 或 ECDSA 密钥。老师说 6、7 已经足够好，8、9 一些大公司也在用。选哪个，取决于你的系统在用户注册时让他们用什么：口令、对称密钥，还是公钥。

自测：下面每种情况各对应哪个协议，又该怎样修补？① 一个网站在浏览器里先把口令哈希再发出去；② 一个物联网设备每次开机都发送同一段认证码；③ 一个服务端数据库存着每个用户的 SHA-256(用户名, 口令)，没有服务器名。

① 是协议 2：哈希成了新口令，偷听者重放即可登录。修补：改成服务器出挑战的协议 4/5，或者先建立加密通道（比如 HTTPS）再传。② 是协议 1–3 那一类：消息不依赖新鲜的东西，录下来就能重放（图 4）。修补：服务器每次发新鲜的随机挑战，设备用密钥算应答（协议 6）。③ 是协议 5 去掉了 Bob：值在所有用同样做法的网站上都一样，用户复用口令时，从这里偷到的值能拿去别的网站冒充（S20）。修补：把服务器名放进哈希，最好再给每个用户配一个随机的盐。

3. 移动通信安全：GSM 的认证与密钥协商

3.1 移动环境：任何人都能收听的无线电 (S28–S30)

讲完识别协议，老师说："基于这部分，我们可以转到移动环境，比如我们的手机。"S29 画出了移动环境 (the mobile environment)：几部移动台 (mobile station, MS)，也就是手机，通过无线电连到运营商的网络；网络在图里是一朵云，里面有基站 (base station)、位置寄存器 (location register) 和交换系统 (switching system)；网络背后还有一台认证服务器 (authentication server, AS)。老师说，我们用 4G、5G 上网时，手机先连到基站，基站再连到后面的各种服务器。

S30 说，从 2G 到 5G 的电信系统，都要面对四个安全问题：认证 (authentication)、机密性 (confidentiality)、完整性 (integrity) 和匿名性 (anonymity)。slides 把最后一个加粗、斜体，特别强调。放到手机上，它们分别是：

  • 认证：网络要确认接入的是一个合法的、付了费的用户，而不是蹭网或冒名顶替的人；
  • 机密性：无线电是广播的，任何人拿一台接收机都能收到你的信号，通话和数据必须加密；
  • 完整性：传输的内容不能被人悄悄改掉；
  • 匿名性：手机走到哪里都要不停地向网络报到。如果它的永久身份在空中明文传输，谁都能知道"这个人现在在这里"，还能一路跟踪他的行踪。这是移动网络特有的隐私问题，S30 加粗它，§3.5 会专门讲它。

这四个问题前面都见过了：认证是 §2 的识别协议，机密性需要 §1 那样的一把会话密钥，匿名性是协议 7 的动机。下面要看的 GSM 协议，就是把这几样东西组装进一个真实系统的例子。

📎 拓展(超出 slides) — GSM 是 Global System for Mobile Communications 的缩写，是 1990 年代起在全球普及的 2G 标准。S31 的标题 "GSM Authentication and Key Agreement" 里的 "Authentication and Key Agreement" 常缩写成 AKA，后来的 3G、4G、5G 都沿用了"认证与密钥协商"这个名字和基本结构，只是越改越强。

3.2 角色和名词：谁手里有什么 (S31, S32)

S31 的图例里列了一串缩写，先把它们理清：

缩写 S31 的解释 是什么
MS mobile station 手机，连同插在里面的 SIM 卡
IMSI International Mobile Subscriber Identity，国际移动用户识别码 用户的永久身份，存在 SIM 卡里
TMSI Temporary Mobile Subscriber Identity，临时移动用户识别码 VLR 分配的临时身份，用来代替 IMSI

📎 拓展(超出 slides) — SRES 是 Signed RESponse 的缩写，Kc 的 c 指 cipher（加密）。按 GSM 标准，Ki 和 RAND 都是 128 位，SRES 是 32 位，Kc 是 64 位。HLR 里负责保管 Ki、生成认证数据的那部分叫认证中心 (Authentication Centre, AuC)，S29 图里的认证服务器 (AS) 在 GSM 里对应的就是这一块。

老师逐个解释了几个关键名词。IMSI 存在你的 SIM 卡里，安卓手机能在设置里查到它；iPhone 只显示 ICCID，老师说两者看起来有点像。Ki 是一把对称密钥：老师说 HLR 就像你的运营商，比如 Telstra 或 Optus；你用的是 Telstra 的 SIM 卡，Telstra 那里就有一把对称密钥，你的卡里有同一把。VLR 和 HLR 的区别，老师用出国来解释：你在新南威尔士州开户、用 Telstra 的卡，平时打交道的是 HLR；可如果你去了新西兰，为你服务的就是当地的"访问位置寄存器"。

📎 拓展(超出 slides)：两处细节 — IMSI 和 ICCID 是两个不同的号码。IMSI 最多 15 位数字，标识的是"用户"：开头 3 位是国家码（MCC，澳大利亚是 505），接着 2–3 位是网络码（MNC，Telstra 是 01），后面是用户编号。ICCID 印在 SIM 卡上，19–20 位，标识的是"这张卡"。VLR 不只用于出国漫游。每个地区的交换中心都配有 VLR，记录当前在这个地区的手机，所以你在家门口也是先和本地的 VLR 打交道；HLR 则固定在你的归属运营商那里。出国只是让"VLR 属于别的运营商"这件事变得显眼。

第 0 步：开户 (Setup，S32)。一切从你办卡那天开始：

  • MS 向一家移动运营商订购服务；
  • 运营商发给 MS 一个硬件令牌 (hardware token)，比如 SIM 卡；
  • 一个唯一的移动身份（即 IMSI）和一把秘密密钥（即 Ki）存进 SIM 卡；
  • 同样的身份和密钥也存进运营商的数据库，即 HLR。

开户之后，三方各自持有：SIM 卡里有 IMSI 和 Ki；HLR 里有所有用户的 IMSI 和 Ki；VLR 此时对你一无所知。S31 底部还标了两个区域：手机和 VLR 之间是无线 (wireless) 的，任何人都能收听；VLR 和 HLR 之间是有线且安全的 (wired & secure)，属于运营商之间的核心网。

3.3 六步走完一次认证与密钥协商 (S31, S33–S38)

图 10 是 S31 的协议图，加上了每一步的本地计算，并按无线和有线分了段。

第 1 步：MS → VLR：IMSI（S33）。手机开机时，把自己的 IMSI 发给 VLR。有了 IMSI，VLR 就能找到这部手机的 HLR：前面拓展里说过，IMSI 开头的国家码和网络码指明了它属于哪家运营商。

第 2 步：VLR → HLR：IMSI（S34）。VLR 把 IMSI 转给 HLR，请它提供一组认证凭据。

第 3 步：HLR → VLR：IMSI, RAND, SRES, Kc（S35）。HLR 收到请求后：

  • 按 IMSI 找到这个用户的秘密密钥 Ki；
  • 生成一个随机数 RAND，计算 SRES = A3(Ki, RAND) 和 Kc = A8(Ki, RAND)；
  • 把 RAND、SRES 和 Kc 发给 VLR。

S35 特别注明：VLR 和 HLR 之间的通信走的是安全信道。这很要紧：SRES 是"标准答案"，Kc 是会话密钥，这一段要是被人偷听，认证和加密就都失去了意义。

第 4 步：VLR → MS：RAND（S36）。VLR 拿到这组凭据后，把 RAND 发给手机，作为挑战。

第 5 步：MS → VLR：SRES（S37）。

  • 手机收到 RAND，用 SIM 卡里存着的 Ki 算出 SRES = A3(Ki, RAND) 和 Kc = A8(Ki, RAND)；
  • 把 SRES 作为对 VLR 挑战的应答发回去；
  • VLR 把它和 HLR 给的 SRES 比对；
  • 手机发来的 SRES 正确，手机就通过了认证。

老师说：现在手上有两个 SRES，一个来自你的手机，一个来自 HLR；两个相等，说明你是合法用户，你的手机就有信号了。

第 6 步：VLR → MS：A5(Kc, TMSI)（S38）。

  • VLR 为手机挑一个临时身份 TMSI，加密后发给它；
  • 手机用 RAND 和 Ki 推出 Kc，解密得到 TMSI，把它当作自己的临时身份；
  • 之后的通信里，手机用 TMSI 表明身份。

这就是协议 6。把 GSM 和 §2.7 对一下，结构完全一样：

协议 6（§2.7） GSM
共享的对称密钥 KK Ki（SIM 卡里一份，HLR 里一份）
Bob 选的随机挑战 rr RAND
应答 H(r,K)H(r, K) SRES = A3(Ki, RAND)
Bob 检查 H=H(r,K)H = H(r, K) VLR 比对两个 SRES
（没有） 额外产出会话密钥 Kc = A8(Ki, RAND)
（没有） 额外分配临时身份 TMSI，保护匿名

只有一处结构上的不同：负责比对的 VLR 手里没有 Ki。HLR 替它出好题、算好答案，交给它的是 (RAND, SRES, Kc) 这样一组"题目、答案和钥匙"，VLR 只负责发题和比对。这样做的好处是，Ki 永远只在 SIM 卡和 HLR 两处，你漫游到别的运营商那里，对方拿到的只是一次性的认证数据。

📎 拓展(超出 slides)：三元组 — (RAND, SRES, Kc) 在 GSM 标准里叫认证三元组 (authentication triplet)。HLR 通常一次给 VLR 发好几组，每组只用一次，用完再要。这样手机在一个地区多次接入时，VLR 不必每次都去问远方的 HLR。

为什么偷听者拿它没办法？把每一方知道什么列出来，答案就清楚了：

值 SIM 卡 VLR HLR 空中的偷听者
Ki ✓ ✗ ✓ ✗
IMSI ✓ ✓ ✓ ✓（第 ① 步是明文）
RAND ✓ ✓ ✓ ✓（第 ④ 步）
SRES ✓ ✓ ✓ ✓（第 ⑤ 步）
Kc ✓ ✓ ✓ ✗
TMSI ✓ ✓ ✗ ✗（第 ⑥ 步加密传输）

偷听者能看到 RAND 和 SRES，但 SRES 只对这一个 RAND 有效；下一次 VLR 发出新的 RAND，旧的 SRES 就作废了，这正是 §2.5 的道理。Ki 从不在空中出现，Kc 由两端各自算出、也从不传输。课上有同学问：这么说，中间人在这里不是问题？老师说：对，不是问题。

密钥协商，但不用 DH。S31 标题里的 "Key Agreement" 指的是 Kc：手机和网络各自用 Ki 和 RAND 算出同一把 Kc，后面的通话用 A5 和 Kc 加密。这和 §1 的 DH 一样达到了"钥匙不在网络上传"，手段却不同。DH 难在双方事先没有任何共同秘密；GSM 在第 0 步就把共同秘密 Ki 装进了 SIM 卡。运营商把 SIM 卡交到你手里，相当于 §1.4 说的"面对面交换钥匙"：认证的难题在开户那天就靠线下手续解决了，所以 GSM 不需要公钥运算。

📎 拓展(超出 slides)：老师说"中间人不是问题"，要加一个限定 — 这句话对偷听者和重放者成立。但 GSM 的认证是单向的：只有手机向网络证明自己，网络从不向手机证明自己（回忆 §2.5 拓展说的协议 4–7 的单向性）。于是攻击者可以架一个伪基站，冒充网络：手机分不出真假，伪基站可以直接要求手机报出 IMSI（这类设备由此得名 IMSI catcher），还可以让手机不加密通信，再把通话转发到真网络，成为真正的中间人。GSM 也没有给数据做完整性保护，早期的 A5/1、A5/2 加密算法也都已被攻破。3G 起的 AKA 加入了双向认证（网络用一个带序列号和 MAC 的认证令牌向 SIM 证明自己）和完整性保护，4G、5G 延续并加强了这些设计。S30 把完整性列为移动系统的安全问题之一，GSM 恰恰在这一项上留了空白。

自测：① 在 GSM 里，什么扮演了协议 6 的挑战 r、密钥 K 和应答 H(r, K)？② HLR 为什么把 SRES 交给 VLR，而不是直接把 Ki 交给它？

① 挑战是 RAND，密钥是 Ki，应答是 SRES = A3(Ki, RAND)；VLR 比对两个 SRES，相当于 Bob 的第 3 步检查。② VLR 可能属于别的地区，甚至别的国家的运营商（漫游）。交出 Ki 等于把用户的长期秘密交给对方，对方从此能冒充这个用户、解密他的所有通话。交出一次性的 (RAND, SRES, Kc)，对方只能完成这一次认证，Ki 始终只在 SIM 卡和 HLR 两处。

3.4 Ki 一旦泄露：SIM 卡复制 (课堂讨论)

GSM 的安全全靠 Ki 保密，而 Ki 存在两个地方：你的 SIM 卡和运营商的 HLR。老师问：有没有可能复制一张 SIM 卡？

从运营商那一端。老师说：如果我在 Telstra 工作，权限很高，能访问服务器，有没有可能拿到你的 Ki？答案是有可能。拿到 Ki，就能复制你的 SIM 卡。复制出来的卡和原卡一模一样。老师描述了一个场景：晚上你关机睡觉，我把复制的卡插进手机，网络把我当成你；如果我已经知道你网上银行的口令，登录时需要的一次性短信验证码 (OTP) 就会发到我这里。他补充说，两张卡不能同时在线，所以攻击要挑你关机的时候。

从卡这一端。老师说，在 2G、3G 的年代，复制 SIM 卡是做得到的，"我们那时候就这么干过"。大约十年前，手机套餐的流量很少，一个月可能只有 300 MB；他当时在中国，有些套餐每月给 2–3 GB 又不贵，于是他把一张卡复制了三份，几个人分着用。因为同一时间只能有一张卡在线，他们还定了规矩，比如"我每天下午 4 点到 6 点用"；两个人同时用，就会有一个人突然掉线，得重新连。

可是 Ki 从卡里读不出来。有同学问过老师：Ki 就在卡里，能不能直接读？老师说不能，这正是复制 SIM 卡很难的原因。那手机又是怎么算出 SRES 的？靠卡上的芯片：手机把 RAND 交给 SIM 卡，SIM 卡在芯片内部用 Ki 算好 SRES，再交还给手机，Ki 从不出卡。老师说银行卡也是这样，所以你把卡借给别人买东西，对方也很难复制它。今天的 4G、5G SIM 卡基本复制不了；不过老师也说，不能说绝对不可能，用专门的设备，SIM 卡和银行卡至今仍有被复制的可能。

📎 拓展(超出 slides)：读不出 Ki，当年又是怎么复制的 — 早期很多 SIM 卡用一个叫 COMP128 的算法同时实现 A3 和 A8。1998 年，研究者（Briceno、Goldberg、Wagner）发现它有缺陷：反复把精心挑选的 RAND 喂给 SIM 卡，收集十几万次 SRES 输出，就能推算出 Ki。卡没有"交出"Ki，是它的输出把 Ki 泄露了出来。这也是为什么后来的卡换了算法，并限制了卡能被询问的次数。另一端的风险也真实发生过：2015 年有报道称，情报机构入侵了 SIM 卡制造商 Gemalto，窃取了大批 SIM 卡的 Ki。

这一节的教训正好呼应 §2.9 老师对协议 6 和协议 8 的比较。对称方案里，同一把密钥存在不止一个地方，SIM 卡和 HLR 任何一处被攻破、任何一个有权限的内部人员，都能让它泄露；公钥方案里，验证方只存公钥，偷走了也没用。

自测：攻击者偷到了某个用户的 Ki，又录下了这个用户过去一个月的无线通信。他能解密这些录音吗？这和 §1.3 讲的"前向保密"有什么关系？

能。每次会话的 Kc = A8(Ki, RAND)，而 RAND 在第 ④ 步是明文发送的，录音里就有。有了 Ki，攻击者对每段录音都能算出当时的 Kc，再解密 A5 加密的内容。这说明 GSM 没有前向保密：会话密钥由长期密钥和公开的随机数决定，长期密钥一旦泄露，过去的会话全部暴露。§1.3 的临时 DH 不一样，每次会话的私钥用完即删，长期密钥只用来签名证明身份，泄露了也解不开以前的录音。

3.5 TMSI：用临时身份保护匿名 (S38, S39)

回到第 6 步。VLR 给手机分配一个临时身份 TMSI，用 Kc 加密后发给它；之后手机都用 TMSI 表明身份。在空中偷听的人看到的只是一个临时号码，只有 VLR 知道它对应哪个 IMSI；TMSI 定期更换，偷听者就没法长期跟踪一个人。老师说：这是为了保护你的身份；我们之后不再用 IMSI，而用 TMSI 和 VLR 通信。

TMSI 为什么必须加密发送？如果第 ⑥ 步明文发出 TMSI，偷听者刚在第 ① 步看到了 IMSI，紧接着又看到了分配给它的 TMSI，两者一对，临时身份就白换了。

和 §2.8 的协议 7 比一比，TMSI 用一种开销小得多的办法实现了匿名：

协议 7 GSM 的 TMSI

协议 7 把开销花在计算上，TMSI 把开销花在存储上：VLR 记下"谁现在叫什么"，就能一步认出你。

S39 的问题："How does TMSI provide anonymity protection when public-key cryptography is available?"（当可以使用公钥密码学时，TMSI 怎样提供匿名保护？）配图在第 ① 步的 IMSI 上画了一个红框，提示我们看那里。课上没有讲这道题。

红框指出了 TMSI 的缺口：TMSI 只在第 ⑥ 步之后才有，而第 ① 步的 IMSI 是明文发送的。这里有一个"先有鸡还是先有蛋"的问题：网络要先知道你是谁，才能找到你的 Ki、生成认证数据；可在认证完成之前，双方还没有 Kc，手机拿什么加密 IMSI 呢？于是手机第一次接入时，或者网络认不出它的 TMSI 时（比如到了一个新地区，或者 VLR 丢了记录），都只能把 IMSI 明文报上去。偷听者只要守在旁边，就能在这些时刻拿到你的永久身份；§3.3 拓展里的伪基站更可以主动要求手机报出 IMSI。

📎 拓展(超出 slides)：S39 的一种解答 — 对称密码学卡在"要先有共享密钥"，公钥密码学正好不需要。让 SIM 卡里预先存一把归属网络的公钥 PKHPK_H（公钥可以公开，不怕被看到），手机在第 ① 步不再发 IMSI，而是发一段用 PKHPK_H 加密过的 IMSI。具体做法就是 §1 的 ECDH：手机临时生成一个私钥 ee，算出 E=eGE = eG 和共享秘密 Z=e⋅PKHZ = e \cdot PK_H，用 ZZ 派生出的密钥加密 IMSI，把 EE 和密文一起发出；归属网络用自己的私钥算出同一个 Z=skH⋅EZ = sk_H \cdot E，解出 IMSI。这种"临时 ECDH + 对称加密"的公钥加密方案叫 ECIES。关键在于 ee 每次都新选：同一个 IMSI 每次加密出来的密文都不一样，偷听者既看不出你是谁，也看不出两次接入是不是同一个人，这正是 §2.8 拓展说的不可关联性。所在地网络（VLR 那一侧）也解不开，它把密文转给你的归属网络，由归属网络确认身份。5G 正是这样做的：永久身份叫 SUPI，加密后的版本叫 SUCI（Subscription Concealed Identifier）。5G 仍然保留了临时身份（叫 5G-GUTI），平时用它，开销小；只在没有可用的临时身份时才发 SUCI，补上的正是 S39 红框里的那个缺口。

自测：Eve 在商场里放了一台接收机，录了一周的无线信号。① 如果手机用 GSM，TMSI 每天更换一次，她能知道什么？② 如果手机用上面拓展里的公钥方案（5G 的 SUCI），她又能知道什么？

① 她能在每部手机首次接入、或网络认不出 TMSI 的时刻，从第 ① 步拿到明文 IMSI，知道这个人这一刻在商场；在同一天里，同一个 TMSI 反复出现，她还能把这一天的活动串起来。只要她在某次换号前后正好录到 IMSI，就能把新旧号码接上。② 永久身份不再明文出现：每次发出的密文都不同，她既不知道是谁，也连不起两次接入。剩下的只有临时身份在换号之间可被关联，以及协议之外的信息（比如信号出现的时间和位置）。

本章小结 (Key takeaways)

本章三部分回答的是同一组问题，只是一次比一次接近真实系统。GSM 把前两部分的工具组装在一起，也暴露出它们各自的边界：

安全目标 §1–§2 的工具 GSM 的做法 留下的问题
认证：你是谁 挑战–应答（协议 4–9） RAND / SRES，相当于协议 6 只有手机证明自己，网络不证明
机密性：会话密钥 ECDH Kc = A8(Ki, RAND)，再用 A5 加密 Ki 一旦泄露，过去的通话全部暴露
匿名：别让人知道是谁 协议 7（最坏 nn 次哈希） TMSI（查表） 第 ① 步的 IMSI 是明文（S39）

本章要带走的八件事：

  • DH 让两个没有共同秘密的人，在公开信道上得到同一把钥匙。ECDH 公开曲线 Ep(a,b)E_p(a, b) 和基点 GG（阶为 nn），双方各选私钥 x<nx < n，交换公钥 Y=xGY = xG，各自算出 K=xAYB=xBYA=xAxBGK = x_A Y_B = x_B Y_A = x_A x_B G。偷听者有 GG、YAY_A、YBY_B，可算 KK 需要私钥（ECDLP）。KK 是一颗种子，由它派生出 AES 密钥；SSH 的 Curve25519、TLS 和 Lab 4 用的都是它。
  • DH 只防偷听，不防改消息。中间人把两个公钥都换成自己的 YEY_E，和 Alice 共享 K′=xAYEK' = x_A Y_E，和 Bob 共享 K″=xBYEK'' = x_B Y_E，之后解密、阅读、修改、再加密。公开值本身不带"是谁生成的"证据，解法是认证：证明 YAY_A 真是 Alice 的。下周的证书做的就是这件事，代价是要信任一个第三方。
  • 识别协议首先要防冒充攻击：偷听一次正常登录，再以 Alice 的身份登录。协议 1 发明文口令；协议 2 发 H(pw)H(pw)，哈希成了新口令，照样能重放，好处只是口令不会立刻暴露；协议 3 加了由 Alice 选的盐，仍能重放。三者的共同病根是：消息不依赖任何新鲜的、由验证方决定的东西。
  • 字典攻击不逆转哈希，而是猜输入。slides 的 offline dictionary attack 用一本提前算好、对所有目标通用的字典（协议 2）；online dictionary attack 的字典要在看到 rr 或用户名之后才能算，只对一个目标有效（协议 3、5）。盐消灭的是"提前计算"和"一本通吃"，不能让弱口令变强。业界说的在线、离线指的是"要不要和服务器交互"，是另一回事。
  • 由验证方出新鲜、足够长的随机挑战，重放就失效（协议 4 的挑战–应答）；rr 固定就退回到协议 2。协议 5 让服务器只存 H(Alice,Bob,pw)H(Alice, Bob, pw)：有 Alice，数据库泄露后每个用户都要单独一本字典；有 Bob，偷到的值不能拿到别的服务器上冒充。
  • 协议 6 是标准的安全识别协议：把口令换成又长又随机的对称密钥 KK，字典攻击无从下手，只要 rr、KK 够长、KK 保密就安全，代价是服务器也存着 KK。协议 7 把用户名藏进哈希，对偷听者匿名，代价是服务器最坏要试 nn 个用户。协议 8、9 用公钥加密或签名做挑战–应答，服务器只存公钥，被攻破也不泄露秘密，前提是 Bob 手里的公钥真属于 Alice。九个协议不是一条升级链，选哪个取决于注册时用口令、对称密钥还是公钥。
  • GSM 的认证与密钥协商 = 协议 6 + 会话密钥 + 临时身份。SIM 卡和 HLR 共享 Ki；HLR 生成 RAND，算出 SRES = A3(Ki, RAND) 和 Kc = A8(Ki, RAND) 交给 VLR；VLR 以 RAND 为挑战，比对手机算出的 SRES；Kc 两端各自算出，用 A5 加密通信；TMSI 加密下发，之后代替 IMSI。Ki 从不离开 SIM 卡和 HLR，VLR 只拿到一次性的认证数据。
  • GSM 留下了三个缺口。Ki 存在两处，任何一处泄露都能复制 SIM 卡、解开过去的通话（没有前向保密）；认证是单向的，伪基站能冒充网络；第 ① 步的 IMSI 明文发送，TMSI 只能保护之后的通信（S39）。公钥密码学补上了最后这一处：用归属网络的公钥加密永久身份，也就是 5G 的 SUCI。

§1.4 和 §2.9 都停在了同一个问题上：我怎么知道这把公钥真是 Alice 的？第 7 周的证书和 PKI 就从这里开始。
