1 · Hashes and MACs

📖 Full notes: Chapter 1 · 哈希与 MAC

Tool Question it answers Secret Who can verify Gives
Hash Did the bytes change? none anyone integrity (expected value must be trusted)
MAC Did a holder of the shared key send this? shared key K key holders integrity + authenticity
Signature Did the private-key holder sign this? private key anyone with the public key integrity + authenticity + non-repudiation
Encryption Can outsiders read it? key — confidentiality

Terms

  • Hash function: maps any input to a fixed-length digest. Deterministic: same input → same digest. Avalanche effect: one changed bit → a completely different digest. One-way (preimage resistant): easy to compute, infeasible to reverse. Collision resistant: infeasible to find two inputs with the same digest (collisions exist, but nobody can find them). Puzzle-friendly: a proof-of-work puzzle has no shortcut. 📖 Ch1 §2
  • MAC: a keyed checksum, tag = MAC(K, m), with K shared by sender and receiver; HMAC builds a MAC from a hash. Authenticated encryption (AES-GCM, ChaCha20-Poly1305): confidentiality and integrity in one step. 📖 Ch1 §7.2 📖 Ch1 §8

Facts

  • SHA-256: Bitcoin, BIP39 checksum, hash before signing (Lab 3). Keccak-256: Ethereum addresses. HMAC-SHA512: BIP32 and the BIP39 seed. MD5 and SHA-1: broken. 📖 Ch1 §2
  • Uses of a hash: file checksum; block linking (change one block and every later link breaks); proof of work, find a nonce with H(nonce∥prev∥tx)<targetH(\text{nonce} \| \text{prev} \| \text{tx}) < \text{target} (smaller target = harder); address derivation; hash-then-sign; password storage with a per-user salt, H(r, pw), so one precomputed dictionary cannot attack every user. 📖 Ch1 §3 📖 Ch1 §4 📖 Ch1 §6.3
  • A MAC gives no confidentiality, no non-repudiation (both sides hold K) and no replay protection on its own. CRC-32 is not a MAC (WEP): it has no key, so an attacker can flip bits and fix the checksum. Use authenticated encryption, check the tag before using the plaintext, and add counters against replay. 📖 Ch1 §7.2 📖 Ch1 §8

Traps: a hash is not encryption · a hash proves the data did not change since it was recorded, not that it is true · a published hash helps only if it comes from a trusted channel, otherwise sign · authenticated encryption does not give freshness · a salt is not secret. 📖 Ch1 ⚠️

Short answers

  • Q: What is the difference between a hash and a MAC? A hash uses no key, so anyone can compute it; it detects changes only if the expected value is trusted. A MAC uses a secret key shared by two parties, so an attacker who changes the message cannot compute a valid tag. So a MAC gives integrity and authenticity against an active attacker; a hash alone does not. 📖 Ch1 §7.1
  • Q: Why is an offline dictionary attack faster and harder to stop than online guessing? The attacker already has the hash and tests guesses on their own machine, thousands per second with a GPU. The server never sees the guesses, so rate limits and account lock-out cannot stop it. Online guessing must send each guess to the server, which is slow and can be limited. 📖 Ch1 §6.2
  • Q: Which tool fits which job? Checking a download: a hash from a trusted channel, or a signature. Two servers that share a key: a MAC or authenticated encryption. Blockchain transactions and public software: a signature, because anyone can verify it but only the signer can make it. Passwords: a per-user salt and a hash. Secret data: authenticated encryption. Replay: a counter or challenge, plus a MAC or signature. 📖 Ch1 §1 📖 Ch1 §9

2 · Diffie–Hellman Key Exchange

📖 Full notes: Chapter 2 · Diffie–Hellman 密钥交换

Terms

  • Diffie–Hellman (DH): two parties with no shared secret agree on one over a public channel. DH does not encrypt; a KDF (e.g. HKDF) turns the secret into symmetric keys. 📖 Ch2 §1 📖 Ch2 §3
  • ECDH: everyone knows the curve and the base point G. Alice sends YA=xAGY_A = x_A G and Bob sends YB=xBGY_B = x_B G; both compute K=xAYB=xBYA=xAxBGK = x_A Y_B = x_B Y_A = x_A x_B G. Getting xAx_A from YAY_A is infeasible, so a passive eavesdropper cannot compute K. 📖 Ch2 §2 📖 Ch2 §4.1
  • Ephemeral key: new for each session and deleted after use (not “short”). Static key: the same every time. Forward secrecy: a long-term key stolen later does not reveal sessions recorded earlier. 📖 Ch2 §6

Facts

  • MITM: Eve sends her YEY_E to Bob instead of YAY_A, and YEY_E to Alice instead of YBY_B → she shares xAYEx_A Y_E with Alice and xBYEx_B Y_E with Bob → she decrypts, reads, changes and re-encrypts every message. Root cause: the public values are not authenticated. 📖 Ch2 §4.2 📖 Ch2 §9
Countermeasure Stops MITM?
Send H(YAY_A) with YAY_A No: Eve sends H(YEY_E)
Encrypt YAY_A with AES first Impossible: no shared key yet
Server signs the handshake; client checks the certificate Yes: Eve lacks the private key
Authenticate only the server Yes: the client proves itself later, inside the channel
Compare fingerprints by phone or in person Yes
Trust on first use (SSH) Not on the first connection; yes later
User clicks through a certificate warning No
  • Key derivation: Lab 4 uses SHA-256(str(k)) of the shared point’s x-coordinate as the AES key; SSH derives encryption keys, MAC keys and IVs; TLS 1.3 derives handshake and traffic keys. 📖 Ch2 §3
  • TLS key roles: the certificate’s long-term signing key authenticates the server · ephemeral key agreement gives a fresh secret · symmetric traffic keys protect the data. TLS 1.3 removed static RSA key transport and static DH (RSA signatures stay), so every connection has forward secrecy. Forward secrecy protects past sessions only: a stolen long-term key still allows impersonation in future. 📖 Ch2 §6
  • Lab 4 / Quiz 3 chat problems: public keys not authenticated (MITM); key pairs reused from files, so every session gets the same AES key and there is no forward secrecy; the AES-CTR counter restarts; no integrity check; random.randint for keys. 📖 Ch2 §8
  • ECIES (Assignment 2): the sender’s ephemeral key and the recipient’s long-term public key do ECDH, then HKDF and AES-GCM. The recipient need not be online. 📖 Ch2 §7

Short answers

  • Q: Why does unauthenticated DH fail against an active attacker? The public values carry no proof of who sent them. An attacker in the middle replaces YAY_A and YBY_B with their own YEY_E, so each victim shares a key with the attacker instead of with each other. The attacker decrypts, reads and re-encrypts all traffic, and nobody notices, because each side completes a normal DH exchange. The fix is to authenticate the public values, e.g. with a signature over the handshake checked with a certificate. 📖 Ch2 §4.2 📖 Ch2 §5
  • Q: Explain forward secrecy and how ephemeral DH provides it. Forward secrecy means that if a long-term key is stolen later, sessions recorded earlier stay secret. With ephemeral DH, each session uses fresh private values that are deleted after the handshake, and the long-term key is used only to sign. So a later key theft cannot recompute the old shared secrets. 📖 Ch2 §6

3 · HTTPS, TLS and Digital Certificates ★★★ (sample question)

📖 Full notes: Chapter 4 · HTTPS、TLS 与证书

Terms

  • Public key substitution problem: a signature shows which private key signed, not who owns the key, so an attacker can swap Alice’s published key for their own. 📖 Ch4 §1
  • Certificate: a CA-signed statement that binds an identity (the domain names in the SAN, Subject Alternative Name) to a public key. It also has the issuer, a serial number, the validity period (not-before, not-after), Basic Constraints (CA or not) and Key Usage / EKU. Certificates are public; anyone can copy one. 📖 Ch4 §2
  • CSR: signed with the applicant’s private key to prove possession; the RA checks identity or domain control; the CA never sees the private key. DV: only domain control is checked; OV / EV: the organisation is checked too. 📖 Ch4 §3
  • Trust anchor: the root where path checking stops. Trust store: the roots a client accepts. CertificateVerify: the server signs the TLS 1.3 handshake with its private key. 📖 Ch4 §4 📖 Ch4 §6

Facts

  • Chain: root CA (self-signed, installed by the vendor or administrator) → intermediate CA → server certificate. The server sends its own certificate and the intermediates. Intermediates keep the root key away from daily use and limit damage. 📖 Ch4 §4
  • Client checks: a path to a trusted anchor → the hostname matches the SAN → validity time, signatures, CA constraints, allowed use → revocation. 📖 Ch4 §5
Failure What the client cannot confirm
Expired certificate that it is valid now
Wrong hostname that this is the service you wanted
Missing intermediate that a complete path exists
Unknown root an approved starting point of trust
Revoked certificate that it is still acceptable
  • TLS 1.3: ClientHello + key share → ServerHello + key share → (EC)DHE secret, handshake keys → encrypted EncryptedExtensions, Certificate, CertificateVerify, Finished → client sends Finished → traffic keys. Only in TLS 1.2: ServerKeyExchange, the old ChangeCipherSpec role, static RSA. 📖 Ch4 §7
  • Expiry is the planned end; revocation is an early withdrawal (key compromise, misissuance, loss of authorisation), and the key must be replaced too. Certificate Transparency (CT): public logs make issuance auditable but revoke nothing. Public TLS certificates issued from 15 March 2026 last at most 200 days, so renewal is automated with ACME. 📖 Ch4 §8
  • Self-signed certificate: strong crypto but no trust. Use it only when it is trusted through an independent channel (e.g. built into the app), with hostname checks still on. Public CA → public sites; private CA → internal managed devices; self-signed → small or development setups. 📖 Ch4 §9
  • DNS poisoning beats HTTP but not HTTPS, because the certificate is checked for the original hostname. HTTPS fails only with another failure: a clicked-through warning, a stolen server key, a misissued certificate or a malicious root on the device. 📖 Ch4 §10.1
  • mTLS: the client also shows a certificate (machine identity); authorisation is still separate. Keep private keys in an HSM. Many outages are operational: a renewed certificate not reloaded, a forgotten endpoint, an incomplete chain. 📖 Ch4 §11

Traps: the padlock means encryption and a checked domain, not an honest site · a root is trusted because it was installed, not because it is signed · revocation does not make a stolen key safe · CT does not revoke · a self-signed certificate lacks trust, not strong crypto. 📖 Ch4 ⚠️

Short answers

  • Q: Why does copying a bank’s certificate not let an attacker impersonate the bank? The certificate is public. In TLS 1.3 the server must sign the handshake (CertificateVerify) with the private key that matches the certificate, and the client checks the signature with the public key in the certificate. The signature covers the fresh handshake, so an old one cannot be replayed. Without the private key, the attacker fails. 📖 Ch4 §6
  • Q: Why does a client trust a self-signed root certificate? A self-signature proves nothing, because anyone can make one. The root is trusted because the OS or browser vendor (root programme) or an administrator put it in the trust store. Adding a root is a security decision, because it widens which identities the client accepts. 📖 Ch4 §4
  • Q: Compare CRL and OCSP. A CRL is a signed list of revoked certificates published by the CA; the client needs a fresh list. With OCSP the client asks a responder about one certificate and gets a signed status, which raises privacy and availability concerns. With OCSP stapling the server supplies the signed status, and the client still checks that it is valid and fresh. 📖 Ch4 §8.2
  • Q: Why can a company proxy read HTTPS traffic without warnings? The administrator installed the company root CA in the laptops’ trust store. The proxy uses it to issue a certificate for each requested hostname, and this certificate passes every check. So the browser’s TLS connection ends at the proxy, which decrypts the traffic and opens a second TLS connection to the real website. 📖 Ch4 §10.2

4 · SSH Security

📖 Full notes: Chapter 5 · SSH

Terms

  • SSH replaces telnet and rsh, which send passwords and commands in cleartext. It gives an encrypted, authenticated channel for remote admin, commands, SFTP/SCP and port forwarding. It does not protect the endpoints and is not a full VPN. 📖 Ch5 §1
  • SSH-2 layers: Transport Layer Protocol (server authentication, key exchange, encryption) → User Authentication Protocol (authenticates the client inside the channel) → Connection Protocol (multiplexes channels: session, x11, direct-tcpip = local forwarding, forwarded-tcpip = remote forwarding). 📖 Ch5 §2 📖 Ch5 §8
  • Host key fingerprint: a hash of the server’s public host key. Trust on first use (TOFU): accept the key the first time, store it in known_hosts, warn if it changes. Passphrase: encrypts the private-key file on the client; it is never sent. 📖 Ch5 §4 📖 Ch5 §5

Facts

  • Steps: the client connects → the server sends its host key → they negotiate and open a secure channel → the user logs in. Transport: ephemeral DH (Curve25519) signed with the host key → encryption keys, MAC keys, IVs. Legacy, do not re-enable: DSS, RC4, 3DES, CBC-only, SHA-1. 📖 Ch5 §2 📖 Ch5 §3
  • TLS trusts a CA-signed certificate checked automatically; SSH trusts a host key checked by the user’s fingerprint check (or host certificates at scale). 📖 Ch5 §4
  • Hardening: no public management ports (use a bastion host, an identity-aware broker or a VPN); no direct root login; disable password login; use keys or short-lived certificates; least privilege (AllowUsers, restricted commands, limited forwarding). Changing port 22 only reduces scanning noise. Agent forwarding lets a compromised middle host use your agent, so prefer ProxyJump. 📖 Ch5 §6
  • Cloud access: direct public SSH (simple; every machine exposed) / VPN (broad network access) / bastion (central policy and logs, but a high-value target) / identity-aware broker (checks cloud IAM, then opens a temporary path). 📖 Ch5 §7
Command Listener on Who connects to the target
ssh -L 8080:127.0.0.1:80 user@web client the server side; 127.0.0.1 = the server itself
ssh -R 10123:127.0.0.1:123 user@web server the client side; the client’s own port 123
ssh -D 1080 user@bastion client (SOCKS proxy) the server side; any destination

Short answers

  • Q: Why is public-key authentication better than passwords? The private key never leaves the client; the client sends only a signature over session data, which cannot be replayed (Week 6 Protocol 9). The server stores only public keys, so a server breach does not allow impersonation. Keys cannot be guessed, phished or reused like passwords, so password login can be turned off. 📖 Ch5 §5
  • Q: What does TOFU fail to prevent? A man-in-the-middle on the very first connection: the attacker’s key is stored as the real one. TOFU only detects a changed key later. Fix: compare the fingerprint with a trusted source, or use host certificates. 📖 Ch5 §4
  • Q: Only the bastion can reach db.internal:8080. Open it at localhost:9000. ssh -L 9000:db.internal:8080 user@bastion. The listener is on your laptop; the bastion connects to db.internal:8080 for you. 📖 Ch5 §10.1
  • Q: Why can port forwarding bypass network segmentation, and how do you control it? The SSH server can often reach internal hosts that the client cannot. Local or dynamic forwarding lets a user reach them through it, and remote forwarding can publish a laptop service into another network. The firewall sees only encrypted SSH. So disable forwarding for restricted accounts, and grant it as a separate permission with limited destinations. 📖 Ch5 §9 📖 Ch5 §11

5 · Wireless Network Security

📖 Full notes: Chapter 6 · 无线网络安全

Terms

  • Access point (AP): connects wireless clients to the wired LAN (infrastructure mode; ad hoc mode = client to client). Beacon frame: the AP advertises; probe request: the client asks. SSID: a network name that anyone can broadcast, so it proves nothing. 📖 Ch6 §1 📖 Ch6 §2.1
  • Four-way handshake: confirms knowledge of the shared secret and installs fresh session keys; it is not a user login. SAE (WPA3-Personal); 802.1X/EAP (enterprise, one identity per user or device); PMF (Protected Management Frames); AES-CCMP; rogue AP; evil twin (a rogue AP that copies a trusted SSID); jamming; WPS. 📖 Ch6 §2.2 📖 Ch6 §7

Facts

  • Joining: WPA2-Personal open-system authentication → association → four-way handshake with the PSK; WPA3-Personal uses SAE instead of open-system authentication; enterprise adds EAP before the four-way handshake. 📖 Ch6 §2.2
  • Wi-Fi 4 / 5 / 6 / 6E / 7 = 802.11n / ac / ax / ax at 6 GHz / be. A new generation improves performance, not security. 📖 Ch6 §1
  • Threats: confidentiality (eavesdropping, traffic analysis); integrity and identity (evil twin, spoofing, downgrade, frame injection); availability (jamming, deauthentication abuse); operations (insecure defaults, shared credentials, unpatched APs). 📖 Ch6 §3
  • PMF (required by WPA3) reduces forged disconnects on established links. It does not stop jamming and does not verify an SSID. Jamming attacks availability; near the AP, many clients lose service. 📖 Ch6 §5
  • WEP = RC4 + 24-bit IV + one shared key + CRC-32. A reused IV means a reused keystream: C1⊕C2=P1⊕P2C_1 \oplus C_2 = P_1 \oplus P_2. 📖 Ch6 §6
  • Evil twin: forge deauthentication frames → broadcast the same SSID as an open network → show a fake router page that asks for the Wi-Fi password. Do not help: a hidden SSID, PMF, new Wi-Fi hardware. 📖 Ch6 §9.1 📖 Ch6 §9.3
  • WPS: the 8-digit PIN is checked in two halves, so each half can be guessed online; disable WPS. 📖 Ch6 §10
  • Secure configuration: WPA3-SAE or 802.1X, never WEP; transition mode only if needed; require PMF; a long random passphrase; change the default SSID and admin password; patch the firmware; separate guest and IoT networks; disable WPS; monitor for rogue APs. 📖 Ch6 §11

Short answers

  • Q: State WEP’s three design mistakes and the lesson from each. Shared credentials: one key for all users and devices, so a leak exposed the whole WLAN and the key was hard to change; lesson: distinct identities (enterprise authentication or per-device credentials). Weak integrity: CRC-32 allowed controlled bit changes; lesson: authenticated encryption. Nonce reuse: the 24-bit IV space made keystream reuse certain; lesson: large nonces, unique under a key, also after a reboot. 📖 Ch6 §6
  • Q: Why can a weak WPA2-PSK passphrase be guessed offline? What does SAE change? The four-way handshake contains values derived from the passphrase, with the SSID as a salt. An attacker who captures it (often after forging deauthentication frames) tests guesses on their own GPUs, and the AP cannot limit the guesses. SAE resists passive offline guessing: a recorded exchange gives nothing to test against, so every guess needs a live exchange with the AP. Weak passwords and transition mode still matter; use a long random passphrase and separate guest and IoT networks. 📖 Ch6 §8.1 📖 Ch6 §8.5
  • Q: Your laptop uses a café’s WPA2 Wi-Fi. Why should banking still use HTTPS? WPA2 protects only the link from the laptop to the AP. After the AP the traffic is decrypted and visible to the AP owner and the networks beyond; with a shared passphrase, other customers may decrypt it too. HTTPS protects the connection end to end, from the browser to the bank, even on an open or hostile network. 📖 Ch6 §4
  • Q: How does a client avoid an evil twin on an 802.1X network? It must validate the authentication server’s certificate against the expected CA and server name, ideally through a managed connection profile, so users are never asked to trust an unknown certificate. The attacker cannot present a valid certificate for the real server. EAP-TLS avoids sending passwords at all. Do not auto-join unknown networks, and monitor for rogue APs. 📖 Ch6 §9.2

6 · Blockchain and Smart Contracts

📖 Full notes: Chapter 7 · 区块链与智能合约

Terms

  • Blockchain: a shared, append-only ledger kept by many nodes under common validation rules: replicated, linked (each block stores the previous block’s hash) and agreed (consensus picks the history). No single administrator. 📖 Ch7 §1
  • Double-spending: spending the same asset twice. Consensus: agreement, validity, termination. Finality: accepted blocks will not change. 📖 Ch7 §2 📖 Ch7 §4.1
  • EVM: makes every node compute the same new state. Externally owned account (EOA): controlled by a private key; can start transactions. Contract account: controlled by its code; acts only when called. Both use 20-byte addresses. 📖 Ch7 §6
  • Nonce: a per-account sequence number. Gas: a unit of work. Smart contract: code and state at an address. Oracle: brings outside facts on-chain. Bridge: links two chains. 📖 Ch7 §7 📖 Ch7 §8 📖 Ch7 §9

Facts

  • Bitcoin white paper: Satoshi Nakamoto, 2008: a P2P network plus a proof-of-work hash chain; the longest chain wins. Confirmed payments are hard to reverse, and a lost key cannot be recovered. 📖 Ch7 §2
  • Transaction path: the wallet signs → broadcast → nodes check the signature and the funds → a block → consensus. More confirmations mean more confidence. 📖 Ch7 §3
  • Byzantine generals: no consensus if 1/3 or more are traitors. FLP: no protocol guarantees every property. So blockchains assume an honest majority, and security is probabilistic. 📖 Ch7 §4.2 📖 Ch7 §4.3
PoW PoS BFT-style voting
Used by Bitcoin Ethereum permissioned networks
Who adds the block the miner who solves the hash puzzle first validators lock ETH as stake; a proposer suggests, others attest known validators vote
Notes open; costly to make, cheap to verify; energy rewards and penalties; finality fast finality
  • 51% attack: redo the proof of work of a block and all later blocks, and overtake the honest chain (more than half the hash power). It can reverse the attacker’s own payments and censor transactions; it cannot steal other people’s coins. 📖 Ch7 §5
  • Transaction fields: nonce, fee settings, to, value, data, signature. The nonce orders transactions and stops replay. Two pending transactions with the same nonce: at most one is confirmed, probably the one with the higher fee. A simple transfer uses 21,000 gas; fee = gas used × effective gas price; the priority fee is a tip. Out of gas: state is reverted, but the fee is still paid. An empty “to” creates a contract; data holds the function and its arguments. 📖 Ch7 §7.1 📖 Ch7 §7.2
  • A contract runs deterministic if–then rules and can emit events. Deterministic does not mean correct, and whoever controls upgrades can change the rules. Lab 2 ERC-20 transfer: require checks → update balances → emit a Transfer event. 📖 Ch7 §8
  • Garbage in, garbage out: a contract can check the oracle’s format and signature, not the truth. A single price source (one exchange pool) can be manipulated, and bridges concentrate trust. Defences: several independent sources, sanity checks, limits on possible loss. 📖 Ch7 §9.2 📖 Ch7 §9.3
  • Use a blockchain only when several parties need a common state and no single party should control it; otherwise use a database. Five threat layers: user and keys, application, protocol, infrastructure, dependencies. A valid transaction can still be harmful, e.g. a phished signature. Keys authorise; transactions request; contracts execute. 📖 Ch7 §10 📖 Ch7 §11.2

Short answers

  • Q: Why can digital signatures alone not prevent double-spending? A signature proves that the key holder authorised a payment, but not that the money is still unspent. Two conflicting payments can both carry valid signatures. Nodes must agree on one order of transactions, and that is the job of consensus. 📖 Ch7 §2
  • Q: Give two reasons why distributed consensus is hard. Any two: nodes may crash or act maliciously; the P2P network has faults and delays; there is no global clock, so a slow node cannot be told apart from a failed one. 📖 Ch7 §4.2
  • Q: Gas limit vs max fee per gas? The gas limit is the most work the transaction may use. The max fee per gas is the highest price the sender will pay per unit of gas. The real fee is gas used × effective gas price; unused gas is not charged. 📖 Ch7 §7.2
  • Q: Why does a smart contract need an oracle, and what new risk does it bring? Every node must reproduce the same result, so a contract cannot call websites or sensors itself. An oracle submits outside facts as transactions. The contract can check the format and the oracle’s authority, not whether the fact is true, so a hacked or manipulated oracle can make correct code pay out wrongly. 📖 Ch7 §9.1

7 · Cryptocurrency Wallets

📖 Full notes: Chapter 8 · 加密货币钱包

Terms

  • Wallet: manages keys (authority), not coins; the coins stay on the blockchain. Hardware wallet: the key stays in a secure chip and signs there. 📖 Ch8 §1
  • Private key: a random 256-bit number on secp256k1 → public key K=k⋅GK = k \cdot G (64 bytes, x‖y) → address: the last 20 bytes of the Keccak-256 hash of the public key, written with 0x. EIP-55: mixed upper and lower case that catches typing errors. 📖 Ch8 §2
  • Non-deterministic wallet (“just a bunch of keys”), deterministic (seeded) wallet, HD wallet; BIP32, chain code, extended key (xprv, xpub), hardened derivation, BIP44, BIP39 mnemonic, passphrase, RFC 6979. 📖 Ch8 §6 📖 Ch8 §7.1

Facts

  • Each step from private key to address is one-way, so sharing the address is safe. A signature is a tamper-evident seal, not encryption. ECDSA: z=H(m)z = H(m), random kk, r=(kG)xmodNr = (kG)_x \bmod N, s=k−1(z+rd)modNs = k^{-1}(z + rd) \bmod N. 📖 Ch8 §3
  • Reused k: both signatures share r, so k=(z1−z2)/(s1−s2)k = (z_1 - z_2)/(s_1 - s_2) and then the private key d=(s1k−z1)/rmodNd = (s_1 k - z_1)/r \bmod N (the PS3 used a fixed k; Lab 3 used Python’s random). Use RFC 6979. 📖 Ch8 §4
  • Cryptography signs bytes, not intentions: malware can show one action and submit another, so check the address and amount on the hardware wallet’s own screen. Defences: hardware isolation, multisig, verified backups. 📖 Ch8 §5
Non-deterministic Sequential deterministic HD (BIP32)
Keys unrelated, random one seed → a chain one seed → a tree
Backup every key separately the seed once the seed once
Compromise one key = one address seed leak = all keys seed leak = all keys
  • BIP32: seed → HMAC-SHA512 → left 256 bits = master private key, right 256 bits = master chain code. Child keys: parent key + chain code + 32-bit index → HMAC-SHA512 → left half = child key, right half = child chain code. xpub derives only public keys (watch-only wallets). Hardened derivation needs the parent private key: xpub plus one leaked normal child key reveals the parent key; a hardened branch does not. 📖 Ch8 §7.2 📖 Ch8 §7.3 📖 Ch8 §7.5
  • BIP44: m/44'/60'/0'/0/0 = purpose / coin type (60 = Ethereum, 0 = Bitcoin) / account / change / address index; ' = hardened; m = private derivation, M = public. 📖 Ch8 §8
  • BIP39: entropy + checksum (first ENT/32 bits of its SHA-256) → 11-bit groups → words from a 2,048-word list: 128 + 4 bits = 12 words; 256 + 8 bits = 24 words. Words + passphrase → PBKDF2-HMAC-SHA512, 2,048 rounds, salt “mnemonic” + passphrase → 512-bit seed. The checksum only catches typing errors; a different passphrase gives a different wallet. 📖 Ch8 §9

Short answers

  • Q: Why does BIP32 use a chain code? The chain code adds extra random data to each derivation. Without it, anyone who saw a parent public key could derive all its child public keys and link every address in the wallet. With it, deriving child keys also needs the chain code, which protects privacy. So an extended public key is more sensitive than a normal public key. 📖 Ch8 §7.4
  • Q: Why is mnemonic exposure more likely than brute force? A correctly generated 12-word mnemonic has 128 bits of entropy, about 21282^{128} choices, so guessing is infeasible. Attackers target the recovery channel instead: phishing sites and fake support staff, malware reading the screen or clipboard, screenshots, cloud-synced notes and photos, stolen paper backups, and weak self-made phrases. Keep it offline, test recovery, and never type it into a website. 📖 Ch8 §11

8 · Secure Cloud Storage and Data Sharing ★★★ (Assignment 2)

📖 Full notes: Chapter 9 · 安全云存储与共享

Terms

  • Data plane: reads and writes content. Control plane: changes permissions, keys, retention and replication; changing a policy or deleting keys also does damage. 📖 Ch9 §1.1
  • Shared responsibility model: the provider secures the infrastructure; the customer secures data, identities, configuration and use. The customer does the most in IaaS, less in PaaS, least in SaaS, but always stays accountable. 📖 Ch9 §1.3
  • Envelope encryption: a DEK encrypts each object; a KEK held in the KMS wraps the DEK; root keys protect KEKs. BYOK: the customer supplies the key material; HYOK: the key stays outside the cloud. 📖 Ch9 §6 📖 Ch9 §7.6

Facts

  • Data lifecycle: create (classify, assign an owner) → store (encrypt, replicate, log) → use (decrypt only where authorised) → share (keep accountability) → archive or delete (verify deletion). 📖 Ch9 §2
  • Threats are mostly configuration and identity: one bad policy exposes a whole bucket (public links, inherited permissions); a leaked API key works from anywhere; ransomware uses stolen sessions and deletes snapshots, versions or keys. Replicas are not backups: use immutable backups under a separate identity and control plane, and test restores. 📖 Ch9 §3

Short answers

  • Q: “Our cloud data is encrypted, so it is secure.” Why is this incomplete? It does not say which scope. With encryption at rest the service still decrypts for any authorised request, so a misconfigured policy or a stolen credential exposes plaintext, and the provider can read it. Encryption in transit protects only the network path; the server sees plaintext. Data in use is plaintext in memory. Only client-side or end-to-end encryption keeps plaintext from the provider, and even then endpoints and metadata are exposed. The claim also ignores integrity, key management and availability. 📖 Ch9 §5
  • Q: How can a leaked API credential become a data breach in seconds? Give three defences. The key appears in a repository, log, build artifact or endpoint, where scanners find it fast. The attacker calls the provider API from anywhere, and the provider sees a valid credential, so the attacker can list, read, share or delete data. Defences (any three): workload identity and short-lived tokens; a managed secrets service; least-privilege policies; a tested rotation and revocation process; monitoring of unusual API use. 📖 Ch9 §3.2
  • Q: Rotation vs re-wrapping vs full re-encryption. When is full re-encryption needed? Rotation makes a new key version active for future use, while old ciphertext still depends on old versions. Re-wrapping protects an existing DEK under a new KEK without changing the file. Full re-encryption encrypts the data again under a new DEK. It is needed when the DEK itself is exposed, or when a removed user who knows the old DEK must be kept out of future versions. 📖 Ch9 §7.4

9 · Secure Two-Party Computation

📖 Full notes: Chapter 10 · 安全两方计算

Terms

  • Secure multi-party computation (MPC): parties compute an agreed result without giving anyone all the raw inputs; 2PC is the two-party case. Benefit: data minimisation. Costs: complexity and speed. 📖 Ch10 §1
  • Ideal world: a trusted third party takes x and y, returns only the authorised output F(x, y) and forgets everything. Real world: only protocol messages. 📖 Ch10 §2
  • View: a party’s input, random values, received messages and output. Simulator: a thought experiment that rebuilds the view from the party’s own input and output. 📖 Ch10 §3
  • Semi-honest: follows the protocol but analyses everything. Malicious: sends false messages, stops early, biases the result. 📖 Ch10 §5
  • Oblivious transfer (OT), secret sharing with a t-of-n threshold, private set intersection (PSI), homomorphic encryption, trusted execution environment (TEE). 📖 Ch10 §6 📖 Ch10 §7 📖 Ch10 §11

Facts

Function What the output also reveals
Comparison (millionaires) is the other value above or below mine
Sum of two inputs, x + y the other input exactly
Sum of three or more the total of the others only
PSI which of my items the other also has
Size of the intersection how many overlap, not which
  • Repeated queries can binary-search an input (about 7 queries for a value from 0 to 100), so limit and audit queries. MPC does not make inputs true. With more than two parties, privacy holds only while the corrupted or colluding parties stay below the threshold. 📖 Ch10 §4 📖 Ch10 §5
  • OT: the receiver picks one of two values and learns only that one; the sender does not learn the choice. GMW (1987): OT can solve any two-party computation problem. 📖 Ch10 §6
  • Secret sharing: one share reveals nothing useful; with 3-of-4, any 3 holders rebuild the secret, and bribing 2 is not enough. 📖 Ch10 §7
  • MPC distributes trust (communication cost) · homomorphic encryption computes on ciphertext (key ownership, compute cost) · a TEE isolates plaintext in hardware (side channels, trust in the vendor). MPC moves trust assumptions; it does not remove them. 📖 Ch10 §10 📖 Ch10 §11
  • Uses: joint fraud detection, PSI for shared customers, cross-organisation statistics, threshold signing for high-value keys. 📖 Ch10 §9

Short answers

  • Q: What may each participant learn in a secure two-party computation? Why? Each participant learns its own input, its authorised output and whatever follows from these two, and nothing else. The reason is the simulation definition: a simulator given only that party’s input and output can produce a view (random values, received messages, output) that looks the same as the real one. So the real messages carry no extra information about the other party’s input. This holds under the assumed threat model, semi-honest or malicious. 📖 Ch10 §3 📖 Ch10 §12
  • Q: Why can a perfectly secure MPC protocol still reveal a private input? The protocol only promises to leak nothing beyond the output, and the output may reveal a lot. If two parties compute x + y, Alice learns y by subtracting x. Even a one-bit comparison leaks the input if it can be repeated, because the other party can binary-search it. So output controls and query limits are needed. 📖 Ch10 §4
  • Q: Why does secret sharing spread trust only if the shares are really separated? The threshold assumes the holders fail or are corrupted independently. If two shares sit in accounts run by the same administrator, one compromise or one dishonest person gets both. Copying shares into one backup weakens confidentiality the same way, and losing too many destroys availability. 📖 Ch10 §7

Short answers

  • Q: Why is a CI/CD pipeline a security-critical trust boundary? High complexity: many tools, dependencies, scripts and runners create attack surface. Many interactions: it connects developers, OSS, repositories, registries and environments. High privilege: it can read code, publish packages, run commands, deploy services and use secrets. Secrets are injected into the runner at run time, so any code running in a job can use them, and one compromise can reach production and every downstream user. 📖 Ch11 §5.1
  • Q: A vendor posts the SHA-256 of each release on its download page. What is the limit, and what else helps? A hash helps only if the expected value comes from a trusted channel; an attacker who controls the download server can replace both the file and the hash. A signature cannot be forged without the vendor’s private key. Provenance shows which commit and pipeline built the file, and a reproducible build lets others rebuild and compare. A signature alone fails if the build itself is compromised, as in SolarWinds. 📖 Ch11 §7
  • Q: Compare static and dynamic analysis. Static analysis checks code without running it and covers many paths, but it reports possible issues and has false positives (CodeQL, Semgrep). Short answers

  • Q: Compare the isolation models of VMs and containers. A VM runs its own guest OS and kernel, and the hypervisor controls every access to the hardware, so a compromised guest, even with admin rights, should stay inside its VM. It fails only through a VM escape and is weakened by features like shared folders. Containers are processes that share the host kernel, isolated by namespaces, cgroups, capabilities and seccomp. They are lighter and faster, but one kernel bug affects all containers on the host, and settings such as a privileged container, a host root mount or Docker socket access break isolation without any bug. 📖 Ch12 §5 📖 Ch12 §13
  • Q: How can a VM escape happen, and how do you reduce the risk? Guest code sends crafted input to an interface the hypervisor exposes, such as a virtual device, copy/paste or a shared folder. A privileged host-side component reads that input; if it has a bug, the input can corrupt memory or skip a check and run code on the host. Reduce the risk: disable unneeded integration features (they enlarge the attack surface), patch the hypervisor, limit management privileges and monitor. 📖 Ch12 §7
  • Q: Why is a snapshot not a backup? A snapshot freezes the disk state and writes later changes to a separate file, so rollback is fast. But it depends on the original virtual disk and cannot be moved elsewhere on its own. A backup is a complete, independent copy. 📖 Ch12 §1

D1 ★★★ Secure an HTTP chat app (the lecturer’s sample)

You want to send a message to your friend Alice via an application. However, you find that this application uses the HTTP protocol. How will you secure this communication? Describe your method and analyze whether it can resist a man-in-the-middle (MITM) attack. 📖 Ch4 §13 📖 Ch0 §5

Problem. HTTP sends messages in plaintext and does not authenticate the server. Anyone on the path, such as a café Wi-Fi owner, can read, change or inject messages.

Method: use HTTPS, i.e. HTTP over TLS 1.3.

  1. Certificate: the server gets a certificate from a trusted CA. It binds the server’s domain name to its public key and is signed by the CA.
  2. Key exchange: in the handshake, the client and the server send ephemeral (EC)DH key shares and compute a fresh shared secret. The server signs the handshake with the private key of its certificate (CertificateVerify).
  3. Verification: the client checks that the certificate chain leads to a root CA in its trust store, the hostname matches the SAN, and the certificate is in its validity period and not revoked. Then it checks the signature, which proves that the server holds the private key.
  4. Protection: both sides derive symmetric session keys and protect every message with authenticated encryption such as AES-GCM. This gives confidentiality and integrity, and ephemeral keys give forward secrecy.

MITM analysis. An attacker can intercept the handshake, but cannot show a valid certificate for the server’s domain and cannot sign the handshake without the server’s private key. The client detects this and stops the connection, so the attack fails. Plain DH without certificates would not resist MITM, because the attacker could run one DH exchange with each side and relay the messages.

Assumptions and limits. The user does not ignore certificate warnings; no malicious root CA is installed on the device; the server’s private key stays secret. TLS protects only the link from the client to the server. If I do not trust the chat server, Alice and I should add end-to-end encryption, so that only our two devices hold the message keys.

Marking points: HTTP has no confidentiality, integrity or server authentication · TLS with a CA-issued certificate · ephemeral DH + server signature · client checks chain, hostname, validity, revocation · authenticated encryption · MITM fails: no valid certificate or private key · contrast with unauthenticated DH · assumptions · E2EE if the server is untrusted.

D2 ★★★ Secure cloud storage and sharing (Assignment 2)

A team stores confidential files on a cloud storage service that it does not trust. Only the owner of a file may decide who can read it. Any change to a file must be detected, and access must be removable. Design a solution, explain how it gives confidentiality, integrity and access control, and state its limits. 📖 Ch9 §12

Threats. The provider is curious or hacked: it can read, change, delete or roll back files. An unauthorised user tries to read files. An attacker swaps a user’s public key. A removed user keeps old data.

Confidentiality: client-side encryption. Each file is encrypted on the owner’s device before upload, with a fresh random data-encryption key (DEK) and AES-256-GCM. The provider stores only ciphertext.

Sharing: key distribution. When the owner approves a request, the owner wraps the DEK with the requester’s public key using ECIES (per-recipient wrapping). Only that requester can unwrap it. Each user registers their own public key from their own account (or a certificate binds it to the user), so the owner cannot be tricked into wrapping the DEK for an attacker’s key.

Integrity. The GCM tag detects any change to the ciphertext. The owner also signs a manifest (file ID, version, ciphertext hash) with ECDSA, and the hash is recorded on-chain. A reader checks the hash and the signature, so a replaced, rolled-back or forged file is detected.

Access control. A smart contract records the owner of each file. Only the owner can approve, reject or revoke a request; the contract checks the caller (msg.sender). Every action emits an event, which gives a tamper-evident audit trail. On-chain data is public, so the contract gives authorisation, not confidentiality: only wrapped keys are stored on-chain. (Without a blockchain: an owner-controlled authorisation service with RBAC or ABAC and logging.)

Revocation. The owner deletes the wrapped DEK, and the contract blocks new access. For full revocation, the owner re-encrypts the file with a new DEK and wraps it only for the remaining users.

Limits. Revocation cannot recall a DEK or plaintext that was already downloaded. Metadata (who shares with whom, when, file sizes) is public. Endpoints must be trusted: malware on a reader’s computer sees the plaintext. The provider can still delete files; we detect it, but we need backups. Wrapped DEKs have no forward secrecy if a user’s private key leaks later.

Marking points: client-side encryption with a per-file DEK and authenticated encryption · per-recipient key wrapping with authenticated public keys · integrity via the tag and a signed hash · owner-only access control with an audit trail · revocation by re-keying · at least one limitation.

D3 ★★ Design an identification protocol (Week 6)

Design a protocol that lets Alice log in to Bob over an insecure channel. It must resist eavesdropping and replay, and a stolen server database must not let the attacker log in as Alice. Explain why it is secure and how to make it anonymous. 📖 Ch3 §2 📖 Ch3 §10 📖 Ch3 §11

Design: public-key challenge–response (Protocol 9). Alice creates a key pair (pk, sk) on her device; Bob stores only (Alice, pk). Steps: (1) Alice → Bob: “Alice”; (2) Bob → Alice: a fresh, long, unpredictable random challenge r; (3) Alice → Bob: Sig_sk(r, Bob); (4) Bob checks the signature with pk and checks that r is the challenge he just sent.

Why it is secure. Eavesdropping: only r and a signature travel; no password is sent, and sk cannot be computed from them. Replay: r is new for every login, so an old signature fails; r must be unpredictable, not a counter (the lesson of Protocols 3–4). Dictionary attack: there is no low-entropy password to guess (Protocols 2–5). Server compromise: Bob stores only the public key, so a stolen database cannot answer a challenge, unlike Protocol 6, where Bob stores K. 📎 Signing Bob’s name stops a fake server from relaying Bob’s challenge, as passkeys bind the website.

Anonymity and session. “Alice” is sent in clear. To hide it, encrypt the identity with Bob’s public key, send it inside an encrypted channel, or use a temporary pseudonym (like GSM’s TMSI); Protocol 7’s way is anonymous but costs up to n hashes. Identification gives no session key, so combine it with signed ephemeral DH, as TLS does.

Marking points: fresh random challenge from the verifier · signature (or a MAC with a long random key) instead of a password · server stores only the public key · each attack explained · anonymity fix · session key.
