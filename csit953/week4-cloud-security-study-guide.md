老师用学校自己的经历开场。几年前，UOW 的邮件服务还跑在校园机房里，服务器是自己的，机房也是自己的；后来全部搬到了 Microsoft 的云上，学校只管付费，省心得多。可他马上补了一句：省心不等于可以不管，**我们的数据怎么办？** 数据现在放在别人的机器上，经过别人的网络，由别人的软件管理，原来那套"机房门锁好、防火墙配好"的思路就不够用了。

这不只是机构的事。老师提醒，我们每个人都在用云存储，手机尤其如此：不管 Android 还是 iOS，默认设置下都会把照片、通讯录、聊天记录自动同步到云上，除非你专门去关掉。本章的几个问题，和每个人都有关：

1. 数据放进云里以后，安全由谁负责？（§1）
2. 云存储和一块硬盘有什么不同？风险从哪里来？（§2）
3. 密码学能帮上哪些忙，帮不上哪些忙？（§3）
4. 加密的安全最后都落到密钥上，密钥怎么管？（§4）
5. 谁能读写这些数据，这个决定由谁、在哪里做出？（§5）
6. 数据要分享出去，怎样只让对的人读到，又能在需要时收回？（§6）

S5 把本章的路线概括成一句话：**跟着数据走，从存储一直走到安全共享** (*Today follows data from storage to secure sharing*)。S55 再把这一路上的控制措施归成五个**控制平面**：存储、密码学、密钥、访问、共享，正好对应 §2 到 §6。小结里会回到这张表。

## 1. 为什么云安全仍是一个"新兴"话题

云计算已经有二十年历史，大型云服务商的数据中心可能是世界上管理得最好的机房。为什么课程还把云安全放在"新兴话题"里？本节先回答这个问题（§1.1），再看云具体改变了风险的哪些方面（§1.2），最后看安全责任在服务商和客户之间怎么划分（§1.3）。

### 1.1 基础设施成熟了，运维安全未必成熟 (S2)

老师的回答是：**运行环境一直在变**。机构不断接入新的托管服务：SaaS 平台、各种 API、容器、无服务器函数 (serverless functions)，最近又多了云上的 AI 系统。每接入一个服务，就多出一批新的身份、新的配置选项、新的数据流向和新的依赖。数据也不再待在一个地方，而是在 SaaS、多个云 (multi-cloud)、员工的终端设备和合作方之间流动（S2 第 1、2 条）。

更值得注意的是威胁来自哪里。老师引用了**云安全联盟 (Cloud Security Alliance, CSA)** 的研究：排在前面的担忧仍然是**错误配置 (misconfiguration)**、**身份与访问管理 (identity and access management, IAM)** 的失误、不安全的 API、可见性不足和未经认证的共享（S2 第 3 条，§2.6 会展开）。这张清单上没有"加密算法被攻破"，也没有"签名算法有漏洞"。老师强调，失效出在**架构、配置、治理和日常运维**上，不在算法上。他说得很直接：配置一旦出错，攻击者可能拿到你全部的数据，**这时你用的是什么加密算法都无关紧要**。

S2 还提到，法规、**数据主权 (sovereignty)** 和供应链方面的要求也在不断变化（§2.9 会讲数据位置为什么重要）。最后一条是本节的结论：**成熟的基础设施不等于成熟的运维安全** (*Mature infrastructure does not mean mature operational security*)。服务商的机房再坚固，防守方面对的仍然是一个时刻在变的系统，它的规模和变化速度都和传统机房完全不同。下一节具体看这些不同。

### 1.2 云改变了风险的位置、规模和速度 (S3)

老师说，云安全**不是把传统安全原样搬到别人的机房里** (*not simply traditional security hosted somewhere else*)。S3 列出了五个变化，和传统机房对比着看最清楚：

| 维度 | 传统机房 | 云 |
|---|---|---|
| **位置 LOCATION** | 数据和服务器都在自己楼里，"内部"和"外部"有清楚的界线 | 工作负载和数据跨越组织边界：服务商的磁盘、SaaS 厂商的系统、员工的手机、合作方的账号 |
| **规模 SCALE** | 一个管理员账号管几台到几十台服务器 | 一个身份、一条自动化规则或一条策略，可以同时作用于成千上万个资源 |
| **速度 SPEED** | 加一台服务器要采购、上架、布线，以周计 | 调一次 API，几秒钟就能创建、修改或删除基础设施 |
| **可见性 VISIBILITY** | 资产就是机房里那几排机柜，一眼看得到 | 资产散落在许多订阅、账号、区域和 SaaS 应用里，很容易被遗忘 |
| **依赖 DEPENDENCY** | 主要依赖自己的硬件和软件 | 依赖服务商、身份服务、软件库、托管服务、外部 API，还有客户自己的配置 |

这五个变化是叠加起作用的。设想一个管理员写了一条过于宽松的策略：在传统机房，它影响一台服务器，而且要等下次维护窗口才会上线；在云上，它可能在一秒钟内作用到整个账号的每一个存储桶（规模和速度），而如果没有人持续盯着配置，几个月都不会有人发现（可见性）。依赖这一条也值得多想一步：云上的应用除了依赖服务商，还依赖你自己的配置，老师说"你是客户，云要你自己来配"。配置错了，服务商的安全再好也帮不上忙。这就引出了下一个问题：哪些事归服务商管，哪些归你管？

<details>
<summary>自测：一个自动化脚本每晚把所有存储桶的访问策略同步成同一个模板。某天有人往模板里加了一行"允许公开读取"。这件事集中体现了 S3 的哪几个维度？</summary>

**规模**：一份模板同时作用于所有桶。**速度**：一晚上就全部生效，没有人工审批的时间差。**可见性**：如果没有持续的配置检测，没人会注意到这些桶已经公开。如果模板来自第三方工具，还涉及**依赖**。

</details>

### 1.3 责任共担模型：一张边界图，不是免责声明 (S4)

**责任共担模型 (shared responsibility model)** 把安全工作分成两份（S4 前两条）：

- **服务商**保护底层的云基础设施：物理设施、核心基础设施，以及托管服务本身；
- **客户**保护自己的数据、身份、配置，并决定服务被怎样使用 (*permitted use*)。老师具体列了：数据分类、身份、访问策略、应用配置，以及服务的用法。

这条分界线不是固定的，它随服务模型移动（S4 第 3 条）。三种服务模型可以用住处来类比：**IaaS**（基础设施即服务，租虚拟机）像租一套毛坯房，装修、门锁、谁有钥匙都归你管；**PaaS**（平台即服务，租运行环境）像租一套精装公寓，房东负责水电和家具，你只管自己的东西；**SaaS**（软件即服务，直接用软件，比如 OneDrive、Gmail）像住酒店，几乎一切都由酒店负责。可就算住酒店，房卡给谁、门有没有关好、贵重物品放不放在桌上，仍然是你自己的事。老师的原话是：IaaS 把更多操作系统和网络方面的责任留给客户；PaaS 把其中一部分移给服务商；SaaS 移得更多，但客户**仍然要管用户、数据共享和许多安全设置**。图 1 把这个趋势画了出来。

**每个设计都应该写明每项控制、每种失效归谁** (*name who owns each control and each failure*)。老师说，责任共担应该被当作一张**控制地图 (control map)**。S4 的标题说它"不是免责声明 (not a disclaimer)"：这个模型的用处不是让双方出事时互相推责任，而是把边界画清楚，让每项控制都有一个具体的负责人。最危险的地方恰恰在边界上：双方都以为对方会管的事，往往没人管。

## 2. 云存储：风险跟着数据走

S5 的路线从存储开始，老师给的理由是：**几乎每个安全决策都取决于存储模型**。本节先纠正一个直觉（§2.1），比较三种存储（§2.2），看便利背后的依赖（§2.3），然后用生命周期和威胁模型两个工具系统地找风险（§2.4–2.5），再逐个看最常见的几类威胁：错误配置（§2.6）、泄露的凭据（§2.7）、勒索软件（§2.8）和数据位置（§2.9）。

### 2.1 云存储是一道服务边界，不只是远程硬盘 (S7)

很多人对云存储的直觉是"一块放在远处的硬盘"。S7 的标题否定了这个直觉：云存储是一道**服务边界 (service boundary)**。

区别在于你接触到的是什么。用硬盘时，你直接面对物理设备。用云存储时，应用面对的是**逻辑资源**：对象、共享文件或虚拟卷；服务商在背后把它们映射到物理设备、冗余副本和具体的地理位置上（S7 前两条）。以 Google Cloud Storage 为例（S7 的配图）：最外层是**项目 (project)**，管计费和环境；项目里建**桶 (bucket)**，桶名全球唯一；桶里放**对象 (object)**，对象 = 数据 + **元数据 (metadata)**；每个对象有一个**对象名**，长得像路径，比如 `logs/2026/april/access`，但它只是一个键，背后没有真正的目录。你永远看不到你的数据具体躺在哪块磁盘上。

既然看不到磁盘，你能做的一切都要通过 **API** 和管理控制台。S7 第 3、4 条说，API 控制数据的创建、访问、版本、保留和删除；而**身份和策略决定谁可以调用这些 API**。云存储的安全问题，说到底就是"谁能调用哪些 API"的问题。

S7 最后一条把这些 API 分成两类：

- **数据平面 (data plane)**：读写内容本身，比如上传一个对象、下载一个对象；
- **控制平面 (control plane)**：创建存储资源，修改权限、配置、加密设置、保留策略和复制规则，开关日志。

```d2 图 2 · 同一个存储服务有两套 API：数据平面读写内容，控制平面决定"内容怎么存、谁能读"
direction: down
user: 应用 / 普通用户
admin: 管理员 / 部署脚本
svc: 云存储服务 {
  data: "数据平面 data plane\n读、写对象内容"
  ctrl: "控制平面 control plane\n权限·加密·保留·复制·日志" {class: key}
}
store: "项目 → 桶 → 对象\n（数据 + 元数据）" {shape: cylinder}
user -> svc.data: 上传 / 下载
admin -> svc.ctrl: 改配置
svc.data -> store: 读写内容
svc.ctrl -> store: 决定怎么存、谁能读
```

图 2 里绿色的控制平面是本节的重点。老师举了一个例子：**一个读不了文件的用户，照样可以造成破坏**，只要他能改文件的策略或者删掉它，比如关掉日志、删掉备份。反过来想更吓人：能改策略的人，可以先把"读取"权限授予自己，再去读。控制平面的权限往往比数据平面的权限**更危险**。S7 的结论是，安全模型必须同时保护两样东西：**存储的数据**，以及**决定服务如何运作的管理操作**。§2.6 和 §2.8 里的攻击，几乎都走控制平面。

<details>
<summary>自测：运维同事只有"修改存储桶策略"的权限，没有"读取对象"的权限。他能拿到桶里的数据吗？</summary>

能。他可以修改策略，给自己（或者所有人）加上读取权限，然后再读。控制平面的权限可以换成数据平面的访问权限，所以"能改策略"至少要和"能读数据"同等对待，通常还要更严格。

</details>

### 2.2 对象、文件、块：三种存储，三种信任模型 (S8)

"云存储"其实是三类差别很大的服务。它们暴露的 API、共享方式和失效方式都不同（S8 第 4 条），S8 的标题称之为**不同的信任模型**。老师逐个介绍了它们的用途和风险：

| | 对象存储 OBJECT | 文件存储 FILE | 块存储 BLOCK |
|---|---|---|---|
| 怎么访问 | 通过 API 按对象名存取；对象带元数据，放在桶里，规模几乎没有上限 | 共享目录和文件路径，权限模型和本地文件系统相似 | 虚拟磁盘，挂载给操作系统或数据库 |
| 适合 | 备份、媒体、归档、应用数据 | 团队协作、依赖传统文件系统的老应用 | 虚拟机系统盘、数据库 |
| 谁管什么 | 服务管理一切，没有文件系统，只有对象 | 服务管理目录和权限 | 操作系统管文件系统；云管卷和**快照 (snapshot)** |
| 典型风险 | 桶策略和公开链接造成暴露 | 权限继承、同步把错误带到各处 | 快照被复制、共享或删除 |

S8 的最后一条是选择控制措施的原则：**按工作负载选控制，而不是按"存储"这个词** (*Choose controls for the workload—not for the word "storage"*)。老师列出了设计时要问的问题：客户端怎么认证？共享怎么实现？有没有快照？哪些 API 能修改策略？恢复怎么做？同样叫"存储加固"，对一个存放公开网站图片的对象桶，重点是防止策略被误改成可写；对一个跑数据库的块存储卷，重点是谁能创建和共享快照，因为一份快照就是整个数据库的完整拷贝。

<details>
<summary>自测：下面三个需求各适合哪种存储？主要的安全控制点在哪？① 保存 10 年的审计日志归档；② 小组共同编辑的项目文件夹；③ 一台虚拟机上跑的 PostgreSQL 数据库。</summary>

① 对象存储：重点是桶策略（禁止公开）、保留策略和不可变性，防止日志被删改。② 文件存储：重点是目录权限和继承关系，以及同步会不会把误删扩散到每个人的电脑上。③ 块存储：重点是卷加密、快照的创建和共享权限，以及虚拟机操作系统本身的访问控制。

</details>

### 2.3 便利的另一面：每个好处都带来一个新的依赖 (S9)

云存储有五个人人知道的好处，S9 把每一个都翻过来看：

| 好处 | 依赖于 | 出了问题会怎样 |
|---|---|---|
| 随时随地访问 | 强身份认证和可信的终端设备 | 密码被钓走，攻击者也能"随时随地"访问 |
| 自动同步 | 被同步的内容本身是好的 | 误删、损坏和被勒索软件加密的文件，也会被迅速同步到每台设备 |
| 弹性扩展 | 有人盯着用量和暴露面 | 暴露在外的服务能被大规模抓取，泄露的数据量没有上限；被盗的账号也能产生巨额账单 |
| 复制 replication | 每份副本都受到同等保护 | 可用性提高了，但需要保护、需要删除的拷贝也更多 |
| 托管服务 | 服务商的控制措施、服务可用性，以及你的正确配置 | 运维省事了，但你越来越依赖服务商 |

老师把这一页总结成一个普遍规律：**带来便利的东西，往往也带来潜在的风险**。他举了一个身边的例子：用 AI 工具帮你读材料很方便，可为了得到答案，你得先把材料交出去，里面可能就有敏感信息。便利是真实的，代价也是真实的，安全设计要做的是把代价看清楚。

<details>
<summary>自测：对勒索软件来说，网盘的自动同步是"帮凶"还是"解药"？</summary>

两者都可能。同步会把被加密的文件迅速推到每一台设备上，这是帮凶；如果网盘保留了文件的旧版本，又可以把文件恢复到被加密之前，这是解药。关键在于有没有一条**不受同步影响的恢复路径**，§2.8 专门讨论这一点。

</details>

### 2.4 跟着数据走完一生 (S10)

一份文件的风险不是一成不变的，老师说**文件不是靠某一个永久的设置保护的**。S10 把数据的一生分成五个阶段，每个阶段面对的风险和需要的控制都不同：

1. **创建 CREATE：给数据分类，明确归属。** 这份数据有多敏感？谁是负责人？哪些用户可以读、可以写？后面所有阶段的决定都以这一步为依据。
2. **存储 STORE：加密、复制、记录日志、保留。** 老师还提到版本控制。这一阶段的控制最多，也最容易做成"打了勾就算完"。
3. **使用 USE：只在获得授权的处理环境里解密。** 使用时，明文**总要在某个地方出现**，否则没法处理，负责处理的环境和终端设备就成了关键。
4. **共享 SHARE：分发访问权，同时不丢掉问责。** 共享改变了数据的受众，而且常常产生新的副本。老师说，有些网站禁用了右键，不让你另存图片，可最"笨"的办法照样管用：拿手机对着屏幕拍一张。东西一旦分享出去，拿到的人可以复制、转发，再也收不回来（§6.6 会正式讨论这个问题）。
5. **归档 / 删除 ARCHIVE / DELETE：保留证据，并核实处置。** 归档可能把数据移到另一个服务，或者进入法律保留状态。删除比看上去难得多：云上一份文件往往有多份拷贝，老师用小组报告举例，你删了 V5，那 V4、V3、V1 呢？还有副本、缓存和备份。

图 3 把一份文件在一生中"长出"的副本画在一起。

```d2 图 3 · 一份文件会长出很多副本：删除要追到你账号里的每一份，分享出去的那些追不回来
direction: right
f: 小组报告 V5 {class: key}
acct: 账号里的副本：能删 {
  grid-columns: 1
  v: 旧版本 V1–V4
  r: 跨区域副本
  b: 备份与快照
  c: 各设备的同步副本
}
out: 分享出去的：删不掉 {
  grid-columns: 1
  d: 组员下载的副本 {class: warn}
  p: 转发、翻拍的副本 {class: warn}
}
f -> acct: 自动产生
f -> out: 分享
```

图 3 揭示了一个贯穿本章的矛盾：**副本既是保障，也是负担**。对可用性来说，副本越多越好（§2.8）；对保密和删除来说，副本越多，要保护和要清理的地方就越多（§2.9）。橙色的那组副本已经离开了你的控制，删除和撤销都管不到它们。§4.1 会介绍一个对付账号里那组副本的办法：如果所有副本都是用同一把密钥加密的，只要销毁这把密钥，所有副本就同时变成了无法解读的数据。

<details>
<summary>自测：小组把报告 V5 删了，三个月后它却出现在网上。它可能是从哪里流出去的？哪些是你本来可以删掉的？</summary>

可能来自旧版本、跨区域副本、备份或快照、某台设备上的同步副本，也可能是组员下载后转发的。前四类在你的云账号里，只要知道它们存在、又有权限，本来可以清理（备份可能受保留策略约束）；组员下载、转发的副本已经离开了你的控制，删除管不到。

</details>

### 2.5 先画威胁模型，再选控制措施 (S11)

知道了数据的一生，下一步是系统地找出"可能出什么事"。S11 的标题给出了顺序：**先画出资产、参与者和信任边界，再选择控制措施**。这就是**威胁建模 (threat modeling)**。S11 列出五个要素：

- **资产 ASSETS**：数据、密钥、身份、策略、日志、备份。老师强调，最显眼的资产是存储的内容，但密钥、身份、访问策略、审计日志、备份和恢复机制**同样有价值**：攻击者拿到其中任何一样，都可能间接拿到数据，或者让你无法恢复。
- **参与者 ACTORS**：普通用户、管理员、应用和自动化服务、服务商员工、合作方，以及攻击者。
- **边界 BOUNDARIES**：终端、网络、**租户 (tenant)**、服务商、合作方。信任边界就是数据或请求从一个信任区域进入另一个信任区域的地方。
- **动作 ACTIONS**：读、写、共享、删除、配置、恢复。
- **失效 FAILURES**：身份被盗、策略写错、恶意软件、服务中断、内部人员滥用。

> 🔑 **例：给小组的云盘文件夹画一张威胁模型** — 五个同学用一个云盘共享文件夹写课程报告。按 S11 的五个要素逐项填：
>
> | 要素 | 这个场景里 |
> |---|---|
> | 资产 | 报告各版本、共享链接、五个人的云盘账号、账号的恢复邮箱、网盘的版本历史 |
> | 参与者 | 五个组员、看报告的老师、网盘服务商、钓鱼攻击者、一个中途退组的同学 |
> | 边界 | 每个人的电脑和手机（终端）、校园 Wi-Fi（网络）、网盘账号（租户）、服务商 |
> | 动作 | 读、编辑、生成共享链接、删除、修改共享设置、从历史版本恢复 |
> | 失效 | 某个组员被钓鱼，攻击者删光文件夹，同步把删除推到每台电脑；共享链接被设成"任何人可查看"后流传出去；一台电脑中了勒索软件，被加密的文件同步上云；交作业当天服务商出故障 |
>
> 从"失效"一行倒推控制措施：开多因素认证（防钓鱼）、确认版本历史保留足够久（防删除和勒索）、共享链接限定为指定的人并设过期时间（防扩散）、在另一个地方留一份离线拷贝（防服务中断）、退组的同学及时移出（防内部人员）。

这个例子也说明了先建模的意义：如果一上来就想"要不要给文件加密"，很可能花了力气，最大的风险（被钓鱼的账号、一个公开链接）却完全没有覆盖。

<details>
<summary>自测：S11 为什么把"密钥、身份、策略、日志、备份"都列为资产？举一个攻击者没有碰数据本身、却借助其中一样资产造成损失的例子。</summary>

因为拿到它们就等于间接控制了数据或恢复能力。例子：攻击者先删掉备份（资产：备份），再加密数据勒索；或者把桶策略改成公开（资产：策略）；或者删掉审计日志掩盖痕迹（资产：日志）；或者偷走一把能解密的密钥（资产：密钥）。

</details>

### 2.6 威胁集中在配置和身份 (S12, S13)

威胁模型画好了，现实中哪些失效最常见？S12 的标题给出了答案：**当前的云威胁集中在配置和身份上**。它列出五类：

1. 错误配置，以及薄弱的**变更控制 (change control)**；
2. 身份与访问管理的失误；
3. 不安全的 API 和第三方集成；
4. 意外泄露和**未经认证的共享 (unauthenticated sharing)**；
5. 在快速变化的资源中缺乏可见性。

老师解读说，这个规律的意义在于：**服务商的物理安全很少是唯一的问题**。许多事故用的都是**合法的云功能**，只不过是通过一个权限过大、保护不足或配置错误的身份或策略。打个比方：服务商的大门锁得很好，攻击者要么拿着一把有效的钥匙从正门进来，要么从客户自己没关的那扇门进来。

S13 讲的是"没关的门"有多大：**一条策略就能暴露整批数据** (*One policy can expose an entire data collection*)。老师说，存储权限之所以威力大，是因为一条策略可以作用于一大批数据。S13 列出了四种常见的路径：

- **继承宽泛的权限**：权限设在桶、容器或共享目录上，里面的每个文件都继承它，包括以后新放进去的文件。
- **公开访问**：可以直接打开，比如把桶设成公开可读、当成公开网站；也可以**通过一个链接**。老师举了 Google Drive 的例子：把文件设成"知道链接的人可查看"，再把链接发到一个群里，群里每个人都能读、都能下载，而链接还可以被继续转发。
- **跨账号角色 (cross-account roles)**：为了让合作方或另一个账号能访问你的资源，你在自己的账号里建一个允许对方"扮演"的角色。这样会产生意料之外的访问路径。
- **配置漂移 (configuration drift)**：资源一开始符合审批过的**基线 (baseline)**，后来被部署脚本、一次手工修复、一份复制来的模板或一个第三方集成悄悄改掉了。

老师特别提醒：**一条策略单独看可能很合理，和另一条权限组合起来就变得危险**。比如，策略 A 允许合作方的账号扮演角色 R，好让对方上传发票，这很合理；半年后，另一位同事为了一个报表任务，给角色 R 加上了读取 `finance/` 下所有文件的权限，这单独看也合理。两条合在一起，合作方（以及任何攻破了合作方的人）就能读你的全部财务数据，而两次变更的审批人都没看到全貌。

S13 的最后一条给出了预防措施，三样缺一不可：**防护规则 (guardrails)**、**审查 (review)** 和**持续检测 (continuous detection)**。防护规则是在组织层面强制的底线，比如"整个组织不允许出现公开的桶"，单个管理员改不动它；审查管住每一次变更；持续检测则用来发现漂移，因为配置是会变的，上线时检查一次远远不够。

<details>
<summary>自测：一个存储桶上线时通过了安全审查：不公开，只允许财务组读取。半年后它变成了公开可读，却没人记得改过它。S13 用哪个词描述这种情况？哪一类措施最可能及早发现它？哪一类能让它根本发生不了？</summary>

**配置漂移**。**持续检测**（自动、持续地扫描配置，一旦偏离基线就告警）最可能及早发现；组织层面的**防护规则**（比如禁止任何桶公开）能让它根本发生不了。

</details>

### 2.7 API 凭据就是远程权力 (S14–S16)

S12 说威胁集中在身份上。云上最常见的"身份"往往不是一个人，而是一串字符：**API 凭据 (API credential)**。

课上有同学说自己经常用 API，却说不清它到底是什么。**API**（application programming interface，应用程序编程接口）是程序调用服务的入口：你的代码不是在网页上点按钮，而是直接向云服务发请求，比如"列出这个桶里的文件""删除这个对象"。云服务需要知道每个请求是谁发的、有没有权限，于是请求里要带上凭据。S14 的标题点出了凭据的本质：**一个 API 凭据代表一份远程的权力** (*An API credential represents remote authority*)。

S14 逐条拆开了这句话：

- **"API key"这个词含义模糊**：它可能只是一个**标识符**，也可能是一个**秘密**，或者是一对凭据中的一半。老师解释，在有些系统里，key 只用来标识是哪个应用或项目在调用（主要用于计费和限额），不足以做强认证；可在另一些系统里，秘密访问密钥 (secret access key)、**持有者令牌 (bearer token)** 或签名请求用的凭据，可以**直接授权**云上的操作。
- **持有者令牌和访问密钥可以在没有用户参与的情况下授权调用。** "bearer"的意思是"谁持有它，谁就能用"，就像一张不记名的电影票：检票员不问你是谁，只看票。整个过程没有人输入密码，也不会弹出多因素认证。
- **附在凭据上的策略决定它实际能做什么。** 凭据本身只是一串字符，它有多危险，完全取决于它背后的权限。
- **写在代码、文件或设备里的长期秘密很难控制。** 它会被复制到许多地方，你很难说清楚到底有多少份拷贝、都在谁手里。
- **一个泄露的凭据，只有在授予了有用的权限时才危险。** 这一条反过来就是防御思路：凭据难免泄露，那就让它泄露时没多大用处。

老师说得很直白：**我只要能从你那里复制到这把 key，就能访问你的私有数据**。S15 把这件事写成了五步，标题是：**泄露的 API 凭据可以在几秒钟内变成一次数据泄露**。图 4 把这五步画了出来。

```d2 图 4 · 泄露的凭据：在服务商看来，这是一次合法的调用，而不是一次攻击
shape: sequence_diagram
dev: 开发者
repo: 公开仓库
atk: 攻击者
api: 云 API
dev -> repo: "① 推送含密钥的代码"
atk -> repo: "② 扫描、复制密钥"
atk -> api: "② 远程调用"
api -> atk: "③ 凭据有效，照常执行"
api -> atk: "④ 列出、读取、删除"
dev -> api: "⑤ 撤销、调查、换新"
```

几个细节值得展开：

- **第 ① 步**：秘密可能出现在代码仓库、日志、构建产物 (build artifact) 或某台终端设备上。老师说，一旦凭据被提交到公开仓库或者打进构建日志，**自动化的扫描器很快就会发现它**。
- **第 ③ 步是整个攻击的核心**：凭据有效，服务商就把这些请求当作**已认证的活动**，而不是一次破解加密的尝试。没有漏洞利用，没有恶意软件，日志里看到的全是合法的 API 调用。这也说明了为什么 §1.1 说算法很少是问题：攻击者根本不用碰加密。
- **第 ⑤ 步**：控制损失需要三件事。**撤销 (revocation)**，让这把凭据立刻失效；**调查 (investigation)**，查日志弄清它被用来做了什么；**替换 (replacement)**，给合法的应用换发新凭据。只删掉那次提交是不够的：它还留在提交历史和别人的 fork 里，扫描器也早已复制走了。

S16 给出了防御方向，标题是：**通过缩短秘密的寿命和缩小它的权力来保护云 API** (*by reducing secret lifetime and authority*)。五条措施：

1. **优先用工作负载身份 (workload identity) 和短期令牌，而不是静态的 API 秘密。** 老师说这是**最有效的改进**：只要平台能给经过认证的工作负载签发短期凭据，就不要用静态秘密。托管的工作负载身份让虚拟机、容器、函数或应用在运行时向平台证明"我是谁"，换取一份临时的权力，代码里不存任何永久的云秘密。没有永久的秘密，也就没有可以泄露的永久秘密。
2. **实在躲不开的秘密，放进托管的秘密服务 (managed secrets service)，不要写进源代码。** 比如调用第三方服务必须用的 API key。它只在运行时注入给获得授权的那个工作负载。
3. **限制凭据能做的动作、能碰的资源、生效的条件、来源网络和允许调用的服务。** 这就是 §5.2 要讲的最小权限。
4. **通过演练过的响应流程来轮换和撤销凭据。** 第一次撤销凭据不该发生在事故当天。
5. **监控异常的 API 调用地点、调用量、错误和权限变更。** 第 ③ 步说明，被盗的凭据看上去完全合法，能暴露它的只有"异常"：从一个陌生国家调用、半夜突然列出所有桶、大量的权限被拒错误、有人给自己加权限。

老师还提了一个简单的办法：给 key 设**有效期**，比如只能用 7 天，那么即使它丢了，7 天以后也就没用了。S16 标题里的两个旋钮，寿命和权力，可以组合成一张表：

| | 权力大 | 权力小 |
|---|---|---|
| **寿命长** | 最危险：泄露一次，长期、全面失守 | 危害有限，但暴露窗口很长 |
| **寿命短** | 窗口短，但窗口之内照样能搬空数据 | S16 的目标 |

> 📎 **拓展(超出 slides)：短期凭据也救不了权限过大** — 2019 年的 Capital One 泄露事件正好落在表格左下角。攻击者利用一个配置错误的 Web 应用防火墙发起 SSRF（服务端请求伪造），从云主机的元数据服务拿到了一个 IAM 角色的**临时凭据**。凭据本身是短期的，可这个角色被授予了过宽的存储权限，能列出并读取大量存储桶，结果约一亿名美国用户的申请资料被下载。服务商的日志里，这些请求全部来自一个"合法"的角色。缩短寿命和缩小权力是两个独立的旋钮，S16 的标题要求两个都拧。

<details>
<summary>自测：同学把含有云存储访问密钥的代码推到了公开的 GitHub 仓库，十分钟后发现，马上删掉了那次提交。这样够不够？还要做什么？</summary>

不够。十分钟足够扫描器复制走密钥，提交历史和 fork 里也可能还留着。要按 S15 第 5 步做：立刻**撤销**这把密钥；**调查**日志，看推送之后它被用来列出、读取、共享或删除了什么；给应用**换发**新凭据，而且新凭据放进秘密管理服务，不再写进代码。长期看，应该改用工作负载身份和短期令牌，并把权限缩到最小。

</details>

### 2.8 云勒索软件攻击的是身份和恢复路径 (S18–S20)

把 §2.7 的被盗凭据和 §2.3 的自动同步放在一起，就得到了云上的勒索软件。S18 的标题说，**云勒索软件攻击的是身份和恢复路径**。老师强调，云上的勒索**不一定需要在存储服务器里运行恶意软件**：攻击者拿着被盗的身份、令牌或 API key，用你的 API 就能下载、加密或覆盖、删除你的数据。S18 的五条：

- **被盗的会话可以通过合法的 API 修改或删除数据**；
- **同步会把被加密或被删除的文件扩散出去**（§2.3）；
- **攻击者可能删掉快照、旧版本或加密密钥**：先断你的退路，再动你的数据；
- **备份如果和数据共用同一个身份和控制平面，就会一起失效**：能删数据的管理员身份，往往也能删备份；
- **恢复需要不可变性 (immutability)、隔离 (separation) 和经过测试的流程。**

> 📎 **拓展(超出 slides)：用云自己的加密功能来勒索** — 2025 年初，有安全公司报告了一种针对 Amazon S3 的勒索手法：攻击者用窃取的访问密钥，调用 S3 支持的"客户自带密钥的服务端加密"，用**攻击者自己的密钥**重新加密受害者的对象，再设置生命周期规则让数据几天后自动删除，以此逼迫受害者付款。全程没有一行恶意代码，用的全是合法的 API 和加密功能，正是 S18 第 1 条描述的情形。

S20 接着回答怎么办，标题是：**韧性 (resilience) 需要独立的恢复路径**。老师先澄清了一个常见的误解：**复制和备份不是同一种控制**。

- **副本 (replica) 应对的是硬件故障，不是所有的安全事件。** 复制保持几份**当前**的拷贝，一块磁盘或一台机器坏了，服务不受影响。可如果数据被恶意加密或删除，复制会忠实地把这个有害的状态也复制过去，所有副本一起被加密。
- **版本 (version) 有助于从覆盖和删除中恢复**：它保留了较早的状态。可攻击者如果有足够的权限，也能把旧版本删掉（S18 第 3 条）。
- **不可变备份 (immutable backup) 能抵抗攻击者发起的修改**：在规定的保留期内，谁也改不了、删不掉，包括管理员。
- **独立的区域或服务商应对更大的故障域 (failure domain)**：整个区域停电，或者整个账号被封禁。
- **恢复目标必须经过测试、能够度量，并且有明确的负责人。** 没演练过的恢复流程，到真出事时往往走不通。

图 5 把 S18 和 S20 合在一起：被盗的管理员身份能碰到的东西，会一起出事。

```d2 图 5 · 被盗的管理员身份能碰到的一切（橙色）会一起出事；只有身份和控制平面都独立的不可变备份（蓝色）能幸免
direction: right
atk: "攻击者\n被盗的管理员会话" {class: warn}
acct: 同一个云账号 {
  grid-columns: 1
  p: 主数据：被加密 {class: warn}
  r: 副本：同步成密文 {class: warn}
  v: 旧版本和快照：被删 {class: warn}
  k: 加密密钥：被停用 {class: warn}
}
bk: "另一个账号的不可变备份\n保留期内谁也改不了" {class: good}

```

把几种机制和几类故障对照起来，可以看清它们各自管什么：

| 机制 | 硬件故障 | 误删或覆盖 | 被盗管理员身份发起的勒索 | 整个区域故障 |
|---|---|---|---|---|
| 副本 | ✅ | ❌ 删除也被复制过去 | ❌ 加密也被复制过去 | 只有跨区域副本 ✅ |
| 版本 | — | ✅ | ⚠️ 同一个身份能删掉旧版本 | 取决于存在哪里 |
| 同账号的普通备份 | ✅ | ✅ | ⚠️ 同一个身份能删掉备份 | 取决于存在哪里 |
| 独立账号的不可变备份 | ✅ | ✅ | ✅ 保留期内删不掉 | 存在另一区域时 ✅ |

表里的 ⚠️ 正是 S18 第 4 条的意思：备份的价值不在于"有一份拷贝"，而在于这份拷贝**不和数据共用同一个身份和控制平面**。

> 📎 **拓展(超出 slides)** — 不可变备份的一个具体实现是对象存储的"对象锁定"，比如 Amazon S3 Object Lock 的合规模式 (compliance mode)：保留期内，任何用户都不能覆盖或删除被保护的对象版本，连账号的 root 用户也不行。S20 说的**恢复目标**通常用两个指标度量：**RPO**（recovery point objective，恢复点目标），最多能接受丢失多长时间的数据，比如"最多丢 1 小时"；**RTO**（recovery time objective，恢复时间目标），最多能接受停机多久，比如"4 小时内恢复服务"。"经过测试"的意思是真的从备份恢复一遍，量一量实际的 RPO 和 RTO 能不能达标。

<details>
<summary>自测：一家公司把所有数据实时复制到另一个区域，管理员说："这下我们不怕勒索软件了。"哪里不对？</summary>

复制应对的是硬件和区域故障。数据被恶意加密或删除时，复制会把有害的状态也同步过去，两个区域的数据一起被加密。而且两份数据由同一个账号、同一个管理员身份控制，攻击者拿到这个身份就能同时处理两边。还需要保留旧版本，并在另一个账号里保存不可变备份，并且实际演练过恢复。

</details>

### 2.9 数据位置和元数据仍然重要 (S21)

最后一类风险不来自攻击者，而来自数据"在哪里"和"露出了什么"。老师说，云上的数据**逻辑上是全球的，物理上和法律上却连着某个具体的地方**。

S21 前两条讲位置。**区域 (region) 的选择影响司法管辖、延迟，以及哪些托管服务可用。** 而且，副本、备份、日志和技术支持流程**可能遵循和主数据不同的位置规则**：主数据在悉尼，备份可能在新加坡，查看日志的支持人员可能在另一个国家。老师说，数据驻留 (data residency) 的规定必须覆盖**整个生命周期**（回想 §2.4），而不只是主数据。

课上同学们举了两个"同一个服务、不同地方不同规则"的例子。Netflix 在不同国家显示不同的片库，取决于你的位置和 IP。iPhone 在欧盟可以从 App Store 以外的网站安装应用，在澳大利亚和美国只能从 App Store 下载。数据也是一样：同一份数据，放在不同的地方，适用的法律就不同。

> 📎 **拓展(超出 slides)** — 两个常被提到的例子：欧盟的 GDPR 限制把个人数据传出欧盟，除非接收方所在地有足够的保护；美国的 CLOUD Act 允许美国执法机构要求美国的服务商交出其控制的数据，即使数据存放在美国境外。"选哪个区域"有时也就是在选"哪国法律能要求访问这份数据"。

S21 后三条讲**元数据**。**加密保护的是内容，不是全部元数据。** 文件名、大小、时间戳、相关的身份和访问模式都会透露上下文。设想一份加密的文件叫 `2026-裁员名单-终版.xlsx`；或者财务总监的账号连续一周深夜访问一个名为 `acquisition` 的文件夹。内容一个字都没泄露，可知道这些的人已经能猜出很多事。S21 的最后一条把位置和元数据串了起来：**数据分类应当决定驻留地、保留期限和共享策略**。这又回到了 §2.4 的第一步：分类做好了，后面的决定才有依据。

<details>
<summary>自测：一家医院把病历加密后存到云上，文件按"患者姓名-诊断.pdf"命名。加密保护了什么，没保护什么？怎么改进？</summary>

加密保护了病历的内容，没保护文件名这个元数据：只要能看到文件列表，就能知道谁得了什么病。改进办法：用不含敏感信息的随机编号命名文件，把对应关系存在受保护的数据库里；按分类限制谁能列出桶里的文件；并确认备份和日志所在的区域也符合驻留要求。

</details>

到这里，云存储的风险地图已经很清楚了：大多数风险来自配置和身份，而不是算法。可密码学仍然是工具箱里最重要的工具之一：它能让"存储服务被攻破"不等于"数据被读走"。下一节只讲做安全决策时用得上的那部分密码学（S5 第 2 条）。

## 3. 密码学基础：只留做安全决策用得上的部分

S5 第 2 条说，本章只保留**做安全决策所需的那些密码学概念**。老师说得很坦白：这门课不推公式、不教怎么算，可这些概念是基础，至少要知道它们**能做什么、什么时候用、怎么用**。本节从安全目标出发（§3.1），先看加密这一族：对称加密（§3.2）、公钥加密（§3.3）和两者的组合（§3.4）；再看其他几种原语各回答什么问题（§3.5）；然后拆开"已加密"这句话（§3.6）；最后讲云上最常用的结构，信封加密（§3.7），它直接通向 §4 的密钥管理。

### 3.1 四个安全目标指导密码学选择 (S23)

讲安全，老师先回到 **CIA**：机密性、完整性、可用性，再加上第四个，真实性。S23 的定义：

- **机密性 (confidentiality)**：未经授权的人读不到内容。老师的说法是"我允许你读，你就能读；不允许，你就读不了"。
- **完整性 (integrity)**：未经授权的修改**可以被发现**。注意措辞是"可以被发现"，而不是"不可能发生"。老师的例子：我写下"明天给你 10 块钱"并签上名，你没法悄悄把 10 改成 100 而不被发现。
- **真实性 (authenticity)**：可以核实数据的来源，或者核实谁控制着某把密钥。
- **可用性 (availability)**：获得授权的用户在需要时能拿到数据和服务。

S23 最后一行是本节的核心：**没有哪一种密码学原语能同时提供所有这些目标** (*No single cryptographic primitive provides every goal*)。老师说，这几个目标彼此相关，但**不能互相替代**。他举了几个例子：

- **加密保护机密性，但挡不住删除。** 我把一个文件加密后放在电脑上。你拿去复制，我不在乎，因为你读不懂；可你要是把它删了，加密一点忙也帮不上。机密性保住了，可用性没了。
- **校验和 (checksum)** 能发现数据被损坏，却**不能证明是谁创建了数据**（§3.5）。
- **数字签名**能证明某个密钥持有者签了一条消息，却**不让消息保密**。Lab 里发的区块链交易就是这样：签了名，可人人都看得到内容（第 3 周 §1.4）。
- **可用性**主要靠架构、冗余、恢复流程和运维能力，而不是密码学（回想 §2.8）。

| 目标 | 防的是什么 | 典型的工具 |
|---|---|---|
| 机密性 | 未授权的人读到内容 | 加密 |
| 完整性 | 内容被改了却没人发现 | 哈希、MAC、签名、认证加密 |
| 真实性 | 有人冒充数据的来源 | MAC（在共享密钥的双方之间）、数字签名（任何人都能验证） |
| 可用性 | 需要的时候拿不到 | 冗余、备份、恢复流程，主要不靠密码学 |

好的设计要**先写明每项资产需要哪些目标，再挑选密码学控制和运维控制的组合**。老师说，这样才能避免那句常见又误导人的话："数据是安全的，因为它加密了。"

<details>
<summary>自测：一个加密过的备份文件被攻击者删除了。哪个安全目标受损了？加密为什么没帮上忙？</summary>

**可用性**受损。加密只保护机密性：攻击者读不懂内容，却照样能删除文件。要保护可用性，得靠另一个账号里的不可变备份这类架构和运维手段（§2.8）。

</details>

### 3.2 对称加密：快，但要先把钥匙送到 (S24)

S24 的图是密码学里最基本的一张图：明文 **M** 进入加密算法 **E**，变成**密文 (ciphertext)** **C**；**C** 进入解密算法 **D**，还原成 **M**。两端各有一把**秘密密钥 (secret key)**，而且是**同一把**。这就是**对称加密 (symmetric encryption)**：

$$C = E(K, M), \qquad M = D(K, C)$$

S24 的标题说明了它的长处：**对称加密能高效地保护大量数据**。老师说，大文件、数据库记录、备份、网络流量，都靠它加密。你在浏览器里看 Netflix，电影在传输过程中就是加密的，浏览器收到后先解密再播放。最常用的对称加密算法是 **AES**（Advanced Encryption Standard），老师说它用了很多年，今天仍然是标准选择。

对称加密的难处有三个。

**第一，密钥分发 (key distribution)。** 老师的问题是：我生成一把密钥，用它加密一条消息发给你，你怎么解密？你必须先拿到这把密钥。可如果我把密钥从同一条信道发过去，偷听的人也拿到了。**每一个需要解密的人，都必须安全地拿到这把秘密密钥。**

**第二，一把密钥该保护多少数据。** 老师用 1000 个文件举例。最省事的办法是 1000 个文件共用一把密钥，可这把密钥一旦泄露，1000 个文件全部能被解密，**波及范围 (blast radius)** 很大。反过来，每个文件一把密钥，泄露一把只影响一个文件，可你就得安全地存储、分发 1000 把密钥。这个两难正是 §3.7 的信封加密和 §4 的 KMS 要解决的。

**第三，加密不等于防篡改。** 老师提到，现代系统还需要**认证加密 (authenticated encryption)**，这样未经授权的修改**会被发现，而不是悄悄地解出一段错误的明文**。下面这个例子说明了"悄悄地"是什么意思。

> 🔑 **例：不带认证的加密会"顺从地"解出被篡改的明文** — 用 AES-256 的 CTR 模式加密一条 11 字节的消息 `PAY BOB $10`（在本机用 openssl 实际跑过）。CTR 模式用密钥生成一串看上去随机的**密钥流**，和明文逐字节做异或 (XOR)。这次运行得到的密文是 `41 c0 b1 0e cb 56 d1 82 fe 70 54`。
>
> 攻击者没有密钥，但他猜得到消息的格式，知道第 10 个字节是字符 `1`（十六进制 `0x31`），他想把它改成 `9`（`0x39`）。两者只差 `0x08` 这一位，于是他把密文的第 10 个字节 `0x70` 和 `0x08` 异或，变成 `0x78`，别的什么都不动。接收方用正确的密钥解密，得到的是 `PAY BOB $90`，**没有任何报错**。
>
> 这正是老师说的"10 块改成 100 块"的风险：密文保住了机密性，攻击者自始至终不知道密钥，可完整性完全没有保护。**认证加密**（比如 AES-GCM）在加密的同时算出一个 16 字节的**认证标签 (authentication tag)**；密文哪怕只改一位，解密时标签就对不上，算法直接拒绝输出明文。

> 📎 **拓展(超出 slides)：和 Assignment 2 的联系** — 你们的 Secure File Share 用 AES-256-GCM 加密文件，每个文件一把新的 256 位密钥。README 里的 Security demo 可以"翻转密文的一位"：翻转之后，先是 V1（和链上记录的哈希比对）报错；如果在演示模式里坚持解密，V5（GCM 标签）也会拒绝输出明文。后一步做的正是上面这个实验的另一半。

<details>
<summary>自测：1000 个文件，"全部用同一把 AES 密钥"和"每个文件一把密钥"，各有什么问题？</summary>

共用一把密钥：管理简单，但这把密钥一旦泄露，1000 个文件全部暴露，波及范围最大。每个文件一把：泄露一把只影响一个文件，但要安全地存储、分发和轮换 1000 把密钥，管理负担很重。信封加密（§3.7）让你同时拿到两边的好处。

</details>

### 3.3 公钥密码学：解决分发和身份问题 (S25)

对称加密卡在"钥匙怎么送过去"。**公钥密码学 (public-key cryptography)** 的思路是把一把钥匙拆成两把：

- **公钥 (public key)** 可以公开，随便给谁；
- **私钥 (private key)** 自己保密（S25 第 1 条）。

它也叫**非对称 (asymmetric)** 密码学，老师解释说，加密和解密用的不是同一把钥匙。第 3 周讲过，从私钥算出公钥很容易，从公钥反推私钥做不到，这是整套体系安全的基础。

它有两种用法（S25 第 2、3 条）：

- **用公钥加密，只有私钥持有者能解开。** Bob 把公钥公开出去（老师说可以发在 WhatsApp 上、贴在论坛上），任何人都可以用它给 Bob 加密消息。老师强调，100 个发送者可以用**同一个**公钥，可只有 Bob 能用私钥解开。
- **用私钥签名，任何人都能用公钥验证。** 这就是第 3 周讲的数字签名。

这样，分发问题就绕开了：公钥本来就是公开的，不怕被偷听。

> 📎 **拓展(超出 slides)：要管理多少把钥匙** — 如果 $n$ 个人两两之间都要用对称加密通信，每一对都需要一把只有这两人知道的密钥，一共要 $\frac{n(n-1)}{2}$ 把：100 个人就是 4,950 把，1,000 个人是 499,500 把，而且每一把都得通过某个安全的渠道送到。用公钥加密，每人只需要一对密钥，100 个人就是 100 对，公钥还可以公开发布。

公钥密码学有两个代价。

**它比对称加密慢得多**（S25 第 4 条）。§3.4 会用实测的数字说明慢多少。

**信任依然取决于把公钥和正确的身份绑在一起**（S25 第 5 条）。分离公钥和私钥，解决了分发和认证的一部分问题，但**没有消除信任**：发送者必须确认，手里这把公钥确实属于想要的那个接收者。老师举了一个例子：如果 Moodle 上出现一条匿名公告，"我是 Yudi，这是我的公钥，要给我发秘密消息就用它"，你怎么确认这把公钥真的是我的？没法确认。可如果我们在同一间教室，我当面把公钥写给你，你就能确定它是我的。如果攻击者把自己的公钥冒充成 Bob 的，发送者就会用攻击者的公钥加密，秘密直接送到攻击者手里。老师说，**证书 (certificates)**、**指纹 (fingerprints)** 和可信的应用程序负责提供这种绑定，后面的课会讲到。

### 3.4 混合加密：用公钥送钥匙，用对称密钥搬数据 (S26)

对称加密快，但要先送钥匙；公钥加密不用送钥匙，但慢。S26 的标题给出了实际系统的做法：**把两者组合起来**，这叫**混合加密 (hybrid encryption)**。S26 的五步：

1. **随机生成一把对称的数据密钥 (data key)**；
2. **用这把数据密钥高效地加密文件**；
3. **为每个获得授权的接收者（或者为 KMS）各保护一份数据密钥**：用接收者的公钥，或者用云上密钥服务管理的一把**密钥加密密钥 (key-encryption key, KEK)**，把数据密钥加密起来；
4. **把密文和被保护的密钥材料一起存储或发送**；
5. **只在获得授权的环境里恢复数据密钥**：解密时，先解出数据密钥，再用它解密文件。

课上有位同学把它总结得很准确：**用对称密钥加密大文件，再用公钥加密这把对称密钥。** 老师接着解释了它为什么是两条消息：我生成一把 AES 密钥，用它加密消息；再用你的 RSA 公钥加密这把 AES 密钥，两样一起发给你。你先用自己的 RSA 私钥解开第一条，拿到 AES 密钥，再用它解密第二条。同学追问 RSA 的私钥从哪来，老师说是接收者自己生成的：先生成私钥，再由私钥算出公钥，这一对叫**密钥对 (key pair)**，接收者只把公钥交出去。老师最后说，**HTTPS 就是这么工作的**：第一轮交换密钥，之后整个会话都用同一把 AES 密钥。

> 📎 **拓展(超出 slides)** — 老师描述的"用 RSA 公钥加密 AES 密钥"是 TLS 1.2 及以前的一种做法 (RSA key transport)。现在的 TLS 1.3 改用临时的 Diffie–Hellman 密钥交换来**协商**出会话密钥，服务器的证书和签名负责证明身份，这样即使服务器的长期私钥日后泄露，过去录下的流量也解不开。思路没变：公钥密码学负责建立一把对称的会话密钥，大量数据交给对称加密。

图 7 画的是 S26 的五步。注意第 ③ 步：同一份密文 C 可以配好几份被保护的数据密钥，每个接收者一份。老师说，这就是混合加密**支持共享**的方式，§6.5 会回到这一点。

> 🔑 **例：为什么不直接用 RSA 加密整个文件？** — 要加密一段 1 GB 的视频。在一台 Apple M3 笔记本上用 `openssl speed` 实测：RSA-2048 的公钥运算约每秒 82,700 次，私钥运算约每秒 2,270 次（每次约 0.44 毫秒）；AES-256-GCM 每秒能处理约 7.9 GB。
>
> - **只用 RSA**：RSA-2048 加 OAEP 填充（SHA-256）一次最多只能加密 190 字节，1 GB 要切成约 526 万块，每块各做一次 RSA。加密约 64 秒，**解密约 2,300 秒，接近 39 分钟**；而且每 190 字节的明文变成 256 字节的密文，1 GB 的文件变成约 1.35 GB。
> - **只用 AES-GCM**：约 0.13 秒，密文只比原文多 28 字节（12 字节的 nonce 和 16 字节的认证标签）。可钥匙怎么送过去的问题没解决。
> - **混合加密**：AES 加密整个文件（0.13 秒），RSA 只加密那把 32 字节的 AES 密钥（解密一次 0.44 毫秒）。
>
> 解密时，只用 RSA 比用 AES 慢了约一万八千倍。混合加密让每种算法只做自己擅长的事：公钥算法负责"送钥匙"这件小事，对称算法负责"搬数据"这件大事。

老师最后提醒，这个模式看上去简单，难的是围绕它的那些决定：**谁可以解出数据密钥、怎样增加或移除接收者、密钥怎样轮换、恢复用的副本放在哪里**。§4 和 §6 讲的就是这些。

<details>
<summary>自测：Alice 用混合加密把一份 500 MB 的报告同时发给 Bob、Carol 和 Dave。她一共要做几次 AES 加密、几次公钥加密？如果改成每人单独完整加密一份，又是多少？</summary>

混合加密：1 次 AES 加密（整个文件只加密一次），3 次公钥加密（数据密钥给每人各包一份），发出去的是 1 份密文加 3 份包装后的密钥。每人单独加密：3 次 AES 加密，产生 3 份 500 MB 的密文（每份还要各配一把密钥送过去）。接收者越多，混合加密省得越多，这也是它适合共享的原因。

</details>

### 3.5 哈希、MAC、签名、加密：各回答一个问题 (S27)

§3.1 说没有哪个原语能包办所有目标。S27 把常用的四种原语和它们回答的问题列在一起，最后一行是选用原则：**按安全问题选原语，而不是按熟悉程度** (*Choose the primitive by the security question—not by familiarity*)。

| 原语 | 回答的问题（S27） | 需要什么秘密 | 谁能检查 | 提供的目标 |
|---|---|---|---|---|
| **哈希 HASH** | 字节变了没有？ | 不需要 | 任何人 | 完整性（防意外损坏，或配合可信的渠道） |
| **MAC** | 是不是持有共享秘密的人认证了这份数据？ | 双方共享的一把密钥 | 只有持有同一把密钥的人 | 完整性 + 真实性（在共享密钥的双方之间） |
| **签名 SIGNATURE** | 是不是某把私钥的持有者签了这些字节？ | 签名者的私钥 | 任何有公钥的人 | 完整性 + 真实性（还能向第三方证明） |
| **加密 ENCRYPTION** | 未授权的人能不能读到内容？ | 解密密钥 | — | 机密性 |

几点说明：

**哈希不需要秘密，这既是优点也是边界。** 老师的例子：我给你一份 Word 文件，写着"明天给你 10 块钱"，同时给你它的哈希值。你把 10 改成 100，文件的哈希就变了，改动也就能被发现。这就是**校验和**。可哈希不涉及任何秘密，谁都能算：如果攻击者能同时改文件**和**旁边那个哈希值，检查就形同虚设。哈希能防的只是意外损坏，除非哈希值本身来自一个可信的地方（官方网站、签过名的记录、区块链）。老师说的"不在乎是谁创建的数据"也是这个意思：哈希只回答"变没变"，不回答"谁写的"。

> 📎 **拓展(超出 slides)：MAC 是什么** — **MAC**（message authentication code，消息认证码）可以理解成"加了密钥的哈希"，常用的是 HMAC-SHA256：把共享密钥和消息一起算出一个标签。没有密钥的人算不出正确的标签，攻击者改了消息，也就没法把标签改对。它的边界在于双方持有**同一把**密钥：Bob 收到一个合法的 MAC，只知道"是 Alice 或者我自己算的"，却没法向第三方证明是 Alice。签名没有这个问题，只有私钥持有者能签，任何人都能验证。§3.2 的认证加密 (AES-GCM) 可以看成加密和 MAC 的合体。

**签名不保密，加密不防篡改。** 前者是第 3 周的结论，后者是 §3.2 那个例子的结论。

老师说，真实的系统很少只用一种原语，而是通过认证加密和协议把几种性质组合起来。比如 HTTPS 里，哈希、签名、加密都有。最重要的技能是**先弄清楚要回答的问题**：要防止被读？要发现被改？要证明是谁发的？先有需求，再选原语、定组合。

> 🔑 **例：Assignment 2 的检查各用了哪种原语** — 你们的 Secure File Share 在解密之前和之后，按 README 做了一组检查，每一项回答一个不同的问题：
>
> | 检查 | 用了什么 | 回答的问题 |
> |---|---|---|
> | V1：下载的密文的 SHA-256 与链上的 ctHash 比对 | 哈希 + 可信的来源（区块链） | 存储里的密文被改过、换过、删过吗？ |
> | V4：用链上登记的签名公钥验证 manifest 的 ECDSA 签名 | 数字签名 | 这份 manifest 真是文件主人签的吗？ |
> | 解包：用请求者的私钥解开 ECIES 包装的文件密钥 | 公钥加密 | 这把文件密钥是包给我的吗？ |
> | V5：AES-256-GCM 的认证标签 | 认证加密 | 密文在解密前被动过吗？ |
> | V6：解密结果的 SHA-256 与主人签过名的摘要比对 | 哈希 + 签名 | 解出来的内容是主人签名认可的那份吗？ |
>
> 注意 V1 能起作用，靠的是哈希值来自链上，而不是和密文放在同一个不可信的存储里。这正是"哈希要配合可信的来源"那条边界。

<details>
<summary>自测：下面四个需求各该用哪种原语？① 下载一个 Linux 镜像后，核对它是否和官网（HTTPS）上公布的一致，防止下载出错；② 两个后端服务共享一把密钥，要确认对方发来的请求没被篡改；③ 软件厂商发布更新，要让全世界的用户都能确认更新确实来自厂商；④ 一份备份要保证即使存储被偷也读不出内容。</summary>

</details>

### 3.6 "已加密"三个字不完整：要说清保护范围 (S28)

经常听到这样的说法："放心，我们的数据是加密的。"S28 的标题指出，这句话**少了一半**：不说清**保护范围 (protection scope)**，"已加密"三个字什么也说明不了。S28 列出五种范围：

- **静态加密 AT REST**：存储介质或服务内部的拷贝是加密的。它防的是磁盘被偷、硬件报废时数据外流。可老师提醒，服务会在收到经过授权的请求时**自动解密**：能发出授权请求的人（或者攻破了服务的人）看到的是明文。
- **传输加密 IN TRANSIT**：网络连接保护数据在两个端点之间的传输，比如 HTTPS。可连接的两个**端点**照样能读到明文，而云服务器正是其中一个端点。老师的例子：你在学校的网络上把文件传到云盘，用的是 HTTPS，学校的 IT 部门看不到内容；可云服务商看得到，你上传的照片、论文都在它那里以明文出现。
- **使用中 IN USE**：应用处理数据时，通常要在内存里用明文。这一条不是"加密"，而是提醒你：总有一个时刻，数据是明文。
- **客户端加密 CLIENT-SIDE**：上传之前，在你自己的设备上加密，服务商从头到尾只拿到密文。
- **端到端加密 END-TO-END**：只有通信的两个端点持有解密能力，中间的服务从不拥有密钥。

### 3.7 信封加密让密钥管理可以扩展 (S29)

回到 §3.2 的两难：一把密钥保护所有数据，波及范围太大；每个对象一把密钥，又多得管不过来。云上的标准答案是**信封加密 (envelope encryption)**，它把混合加密（§3.4）的结构用到了存储上。S29 的前两条：

- **每个对象（或一小组对象）用一把独立的数据加密密钥 (data-encryption key, DEK)**；
- **一把密钥加密密钥 (KEK) 保护许多把 DEK。**

具体做法是：用 DEK 加密数据（对称加密，快）；再用 KEK 把 DEK 加密起来，这一步叫**包装 (wrap)**，反过来叫**解包 (unwrap)**。KEK 通常放在云上的**密钥管理服务 (Key Management Service, KMS)** 里，**从不离开 KMS**。包装后的 DEK 很小，可以直接和密文放在一起。老师说，包装后的 DEK 放在密文旁边并不危险，因为没有更上层的那把密钥、没有解包的权限，它毫无用处。这就是"信封"这个名字的由来：数据锁在 DEK 里，DEK 又被装进一个由 KEK 封口的信封，信封和数据放在一起。图 9 画出了这个结构。

```d2 图 9 · 信封加密：每个对象有自己的 DEK，包装后的 DEK 和密文存在一起；KEK 留在 KMS 里
direction: down
kms: 云 KMS {
  kek: "KEK\n从不离开 KMS" {class: key}
}
bucket: 存储桶 {
  o3: "对象 3 的密文\n+ 包装后的 DEK₃"
  o2: "对象 2 的密文\n+ 包装后的 DEK₂"
  o1: "对象 1 的密文\n+ 包装后的 DEK₁"
}
kms.kek -> bucket.o3
kms.kek -> bucket.o2: 包装 / 解包
kms.kek -> bucket.o1
```

这个两层结构同时拿到了两边的好处：每个对象一把 DEK，泄露一把只影响一个对象；需要严密保护和管理的，却只有 KMS 里的一把 KEK。S29 的后三条说明了它还带来什么：

- **大块的密文不必因为每一次策略变化而重新加密。** 要换 KEK、要调整谁能访问，只需要重新包装那些很小的 DEK，数据本身原封不动（§4.5 会细讲）。
- **能不能解包 DEK，变成了一个集中的安全决定。** 谁能让 KMS 解包，谁就能读数据。所有的访问最后都汇聚到 KMS 这一个点上，策略和审计也就集中在这里（§4.2）。
- **密钥层级限制了暴露范围，也便于审计和轮换**（§4.3）。

> 🔑 **例：一次策略变化要动多少数据** — 一个桶里有 10,000 个对象，平均每个 500 MB，共 5 TB。公司决定轮换 KEK。
>
> - **信封加密**：用新的 KEK 重新包装 10,000 把 DEK。每把包装后的 DEK 只有几百字节，总共几 MB；5 TB 的密文一个字节都不用碰。
> - **如果所有对象直接用同一把主密钥加密**：换密钥就意味着把 5 TB 数据全部读出来、解密、用新密钥加密、再写回去。
>
> 这就是 S29 标题里"可扩展"的意思：密钥管理的工作量取决于密钥的数量，而不取决于数据的大小。

<details>
<summary>自测：把包装后的 DEK 和密文放在同一个桶里，不就等于把钥匙和锁放在一起了吗？</summary>

不是。放在桶里的是**包装后**的 DEK，它本身是用 KEK 加密过的。要用它，必须请 KMS 解包，而 KEK 从不离开 KMS，KMS 解包前还要检查调用者的权限并记录审计日志。真正需要保护的是 KEK 和"解包权限"，而不是包装后的 DEK。

</details>

信封加密把整个系统的安全收拢到了一个地方：KEK，以及谁有权解包。可以说，到这里加密已经不是难题了，难的是管好密钥。这就是下一节的主题。

## 4. 密钥管理：加密的安全最后落在密钥上

S5 第 3 条说，要**把密钥当作高价值的云身份来管理**。老师给的理由很简单：**再强的加密，一旦密钥被暴露、不可用、被滥用或被销毁，就变弱了**。第 3 周讲钱包时我们已经见过这个道理：丢了私钥，就丢了资产；在云上，丢了密钥，可能就丢了数据。密钥管理覆盖密钥的完整一生：生成、存储、分发、使用、轮换、撤销、备份和恢复。本节先看密钥通常从哪里出事（§4.1），再看云上集中管理密钥的服务（§4.2）、密钥怎样分层（§4.3）、密钥的生命周期（§4.4）和轮换（§4.5），最后是两个治理问题：恢复时的职责分离（§4.6）和密钥归谁所有（§4.7）。

### 4.1 算法很少是密钥管理里最弱的一环 (S31)

老师说，**现代的加密通常不是靠猜密钥攻破的**。AES-256 的密钥有 $2^{256}$ 种可能，就算是 AES-128，$2^{128} \approx 3.4 \times 10^{38}$ 种，也没有人能穷举完。这和第 3 周的结论一样：助记词被泄露的可能，远大于被暴力破解。系统出事，是因为密钥材料出现在了不该出现的地方：源代码、环境变量文件、日志、备份、内存转储、技术支持工单，或者没人管理的设备。S31 列出了五种失效方式：

1. **密钥可能通过代码、日志、备份、内存或支持工具泄露。** 写死在代码里（§2.7 的老问题）；调试时打印进了日志；整个配置目录被备份，密钥文件也在里面；程序崩溃产生的内存转储被附在工单里发给了外部的技术支持。
2. **权限过宽，会把一个应用的身份变成一台解密机。** 老师说，密钥本身可能**在技术上一直是保密的**，可如果一个权限过大的应用身份能对**任何**对象请求解密，攻击者只要攻破这个应用，就能借它的身份解密一切，而他从头到尾没见过密钥。密钥没被"偷"，数据却被读走了。
3. **密钥不可用或被删除，好端端的密文就成了废数据。** 老师强调，**可用性和保密性同样重要**：如果我把你的密钥服务关了，你能怎么办？加密的数据还在，却谁也读不出来了。
4. **长期使用的密钥会不断积累暴露和被遗忘的依赖。** 一把用了五年的密钥，被复制过多少次、有多少系统依赖它、当年是谁配置的，往往已经说不清，想换都不敢换。
5. **安全取决于人、流程、软件和恢复能力**，而不只是算法。

> 📎 **拓展(超出 slides)：把"密钥被删"变成工具** — 第 3 条是一把双刃剑。意外删掉密钥会让数据永远丢失，**有意**销毁密钥却可以用来彻底删除数据，这叫**密码学擦除 (crypto-shredding)**。回想 §2.4 的难题：一份数据散落在旧版本、副本、备份里，很难一份不落地全部删掉。如果它们全都用同一把密钥加密，只要可靠地销毁这把密钥（以及它的所有备份），所有拷贝就同时变成了无法解读的数据。S10 说删除阶段要"核实处置"，销毁密钥就是一种便于核实的处置方式。

<details>
<summary>自测：攻击者攻破了一台 Web 服务器，没拿到任何密钥，却解密了数据库里所有客户的数据。这对应 S31 的哪一条？该怎么改进？</summary>

第 2 条：权限过宽，应用身份成了解密机。这台服务器的身份能对所有数据请求解密，攻击者借用这个身份就行。改进：按最小权限只允许它解密自己需要的那部分数据（比如按租户分开的密钥，§4.3）；监控解密请求的数量和来源，异常激增时告警（§4.2 的审计日志）。

</details>

### 4.2 云 KMS 把密钥策略和审计集中起来 (S32)

§3.7 的信封加密里，KEK 放在 **KMS** 里，从不离开。S32 说明了 KMS 具体做什么：

- **生成并保护 KEK**；
- **授权各种操作**：加密、解密、包装、解包，以及管理操作（建密钥、改策略、轮换、禁用、删除）。应用不拿密钥，而是把请求发给 KMS，KMS 在内部完成运算后返回结果；
- **把每一次密钥使用记进集中的审计日志**：老师说，服务会记录**每个操作是谁请求的**；
- **可以和硬件安全模块 (HSM) 集成**，获得更强的隔离；
- **减少了直接接触原始密钥的场合，但也造就了一个高价值的控制平面。**

图 10 画出了应用和 KMS 之间的一来一回。

```d2 图 10 · 应用从不接触 KEK：写入时向 KMS 要数据密钥，读取时请 KMS 解包；每次请求都要过策略检查、留下审计记录

```

> 📎 **拓展(超出 slides)：一个真实的 KMS 接口** — 以 AWS KMS 为例，`GenerateDataKey` 一次返回两样东西：明文的数据密钥（应用用它加密，用完立即从内存里丢掉）和用 KEK 加密过的同一把密钥（和密文存在一起）；读取时调用 `Decrypt`，把包装后的密钥交给 KMS 解开。KEK 本身始终留在 KMS 的 HSM 里。删除一把 KEK 也不能立即生效，必须先进入 7 到 30 天的等待期，给"误删"或"恶意删除"留出发现和撤回的时间。

> 📎 **拓展(超出 slides)：HSM 是什么** — **硬件安全模块 (hardware security module, HSM)** 是专门保管和使用密钥的防篡改硬件：密钥在里面生成、在里面使用，不能以明文形式导出；不少 HSM 在检测到外壳被撬开时会自动清除密钥，通常还要通过 FIPS 140 之类的认证。它和第 3 周的硬件钱包是同一个思路：私钥从不离开设备，你把要签名或解密的东西送进去，只拿回结果。

S32 的最后一条值得反复体会。KMS 让真正接触长期密钥的应用变少了，这是好事；可它也把所有加密数据的命运集中到了一个地方。老师点出了这件事的两个推论：

- **调用 Decrypt 的权限，可能就等于读取受保护数据的权限。** 给一个应用 Decrypt 权限，和直接把明文给它没有本质区别。
- **修改密钥策略或安排删除密钥的管理权限，可能更强大。** 能改策略，就能给自己加上 Decrypt 权限；能删密钥，就能让所有数据无法恢复（§4.1 第 3 条，也是 §2.8 勒索手法的一环）。

这和 §2.1 的控制平面是同一个道理：在 KMS 这里，"能管密钥"比"能用密钥"更危险。

<details>
<summary>自测：审计时发现，一个开发者账号拥有某把 KEK 的 Decrypt 权限。他说："我从来没见过这把密钥长什么样，所以没关系。"他说得对吗？</summary>

不对。在信封加密下，他根本不需要见到 KEK：只要能调用 Decrypt，就能解包这把 KEK 保护的每一把 DEK，进而读到所有对应的数据。Decrypt 权限就等于读取这些数据的权限，应当按最小权限收回，只留给确实需要的工作负载。

</details>

### 4.3 密钥层级限制了被攻破时的波及范围 (S33)

信封加密是两层：KEK 保护 DEK。实际系统往往再往上加一层，形成一个**密钥层级 (key hierarchy)**（S33）：

- **根密钥 (root key) 或主密钥 (master key)** 保护下一层的 KEK；
- **KEK** 保护许多把短期使用的 DEK；
- **DEK** 保护单个对象、会话或一小组数据。

S33 的标题说，层级的作用是**限制被攻破时的波及范围**。规律是：**层级越高，被攻破时影响的范围越大**（第 4 条）。泄露一把 DEK，只影响一个对象；泄露一把 KEK，影响它下面所有的 DEK；泄露根密钥，就是全部。老师把它和第 3 周的 HD 钱包联系起来：拿到你的根密钥，就拿到了一切。这也是为什么根密钥通常放在 HSM 里，极少使用，只用来包装 KEK。

层级的另一个作用在第 5 条：**按租户、工作负载、区域或敏感程度分开，可以把损失控制住。** 每个租户（或每个区域、每类敏感数据）用自己的 KEK，一把 KEK 出事，只波及那一个分支。图 11 画出了这种隔离。

```d2 图 11 · 按租户分开 KEK：KEK-A 出事时，只有租户 A 的分支（橙色）受影响
direction: down
root: "根密钥\n放在 HSM 里，极少使用" {class: key}
kb: "KEK：租户 B"
ka: "KEK：租户 A\n（出事了）" {class: warn}
d4: "DEK₄\nB 的文件 2"
d3: "DEK₃\nB 的文件 1"
d2: "DEK₂\nA 的文件 2" {class: warn}
d1: "DEK₁\nA 的文件 1" {class: warn}
root -> kb
root -> ka
kb -> d4
kb -> d3
ka -> d2
ka -> d1
```

> 🔑 **例：分开 KEK 能少损失多少** — 一个 SaaS 服务有 3 个企业客户（租户），每个租户 1,000 个文件，每个文件一把 DEK。
>
> - **所有租户共用一把 KEK**：这把 KEK 出事（比如它的解包权限被盗用），3,000 个文件全部暴露，三个客户都要通知。
> - **每个租户一把 KEK**（图 11）：同样的事故只波及一个租户的 1,000 个文件。
> - **一把 DEK 泄露**：只有 1 个文件。
>
> 层级里每往上一层，单个密钥出事的代价就大一个数量级。越高层的密钥，越要少用、少给权限、多加保护。

<details>
<summary>自测：第 3 周的 HD 钱包里，主种子泄露意味着什么？它和 S33 的根密钥有什么相同之处？</summary>

主种子泄露，就能推出钱包里的每一把私钥，所有资产都失守。相同之处在于两者都位于层级的顶端：越高层的密钥，泄露时波及的范围越大，都要放在最受保护的地方（硬件钱包、HSM），尽量少用。

</details>

### 4.4 密钥的一生：从生成到销毁 (S34)

和数据一样（§2.4），密钥也有生命周期。S34 的五个阶段和老师的补充：

| 阶段 | 要做到 | 常见的失误 |
|---|---|---|
| **生成 GENERATE** | 用经过认可的随机源，在受保护的服务（KMS、HSM）里生成 | 自己写随机数生成（第 3 周 §1.5 的 PS3 事故）；在开发者的电脑上生成再上传 |
| **激活 ACTIVATE** | 激活之前先明确负责人、允许的用途、管理员、审计设置和恢复要求 | "先用起来再说"，出事时没人知道这把密钥归谁、谁能恢复 |
| **使用 USE** | 只让经过认证的工作负载做它需要的那几种操作；不导出长期密钥；监控异常的地点、身份、用量和使用时间 | 把长期密钥导出给应用自己保管；一律授予"所有操作"权限 |
| **轮换 / 撤销 ROTATE** | 因为年限、策略或事故需要时，启用新版本；权力该结束时及时撤销 | 从不轮换；第一次撤销发生在事故当天 |
| **归档 / 销毁 ARCHIVE** | 按保留期和恢复需求，保存旧版本或彻底销毁 | 过早销毁，历史数据读不出来；忘了销毁，旧密钥一直暴露 |

表里有两个动作容易混淆。**轮换 (rotation)** 是给密钥换一个新版本，供以后的操作使用；**撤销 (revocation)** 是停止或限制进一步的使用，在某份权力应当结束时用。老师还提到，**归档的密钥可能还要用来解密留存的历史数据**，"销毁"之前必须确认没有数据还依赖它。下一节专门讲轮换。

<details>
<summary>自测：为什么 S34 要求"所有权和策略确立之后才能激活"，而不是先用起来、以后再补？</summary>

一把密钥一旦开始使用，就会有数据依赖它、有应用调用它。如果事先没写明负责人、允许的用途、谁能管理、怎么审计、丢了怎么恢复，出事时就没人能做决定，也没有日志可查；事后再补，往往已经弄不清这把密钥被谁、在哪里用过。

</details>

### 4.5 轮换不等于把一切重新加密 (S35)

"轮换密钥"听上去像是"把所有数据换一把新钥匙重新锁一遍"。S35 的标题纠正了这个印象：**轮换不等于把一切重新加密**。要分清三种操作：

- **轮换 (rotation)：让一个新的密钥版本对以后的操作生效。** 新写入的数据用新版本；已有的密文**可能还依赖旧版本**，这样历史数据仍然读得出来。老师说，这降低了运维成本，代价是**旧的密钥材料仍然必须受到保护**。
- **重新包装 (re-wrapping)：改变 DEK 的保护方式，不改变文件。** 在信封加密下，系统可以用新的 KEK 把 DEK 重新包装一遍，老师强调，这**不需要解密、再加密那个大文件**。
- **完全重新加密 (full re-encryption)：改变数据本身的密文，开销更大。** 换一把新的 DEK，把整份数据解密再加密。老师说，当一把数据密钥暴露时，可能就必须这么做（录音在这句话中间断了）。

S35 的最后一条是：**事故响应可能需要比例行轮换更快的行动。** 例行轮换按计划进行（比如每年一次），而且只管以后；出了事，要根据**哪一把密钥**出了问题，马上采取对应的操作。

> 🔑 **例：哪把钥匙出事，就做哪种操作** — 沿用 §3.7 的设定：每个对象一把 DEK，DEK 由 KMS 里的 KEK 包装。
>
> | 出了什么事 | 攻击者能做什么 | 该怎么办 |
> |---|---|---|
> | 一把 DEK 出现在了公开的日志里 | 解密这个对象 | **完全重新加密**这个对象，换一把新 DEK。重新包装没用：攻击者手里拿的就是 DEK 本身，换信封挡不住他 |
> | 某个身份的 Decrypt 权限被盗用 | 解包它够得着的所有 DEK | 先**撤销**这个身份的权限；查审计日志，确认它解包过哪些 DEK；这些对象都要**完全重新加密** |
> | KEK 的材料本身外流（比如曾被导出的一份拷贝） | 解包任何拿得到的包装后的 DEK | 立即启用新 KEK，**重新包装**所有 DEK，停用旧 KEK；如果攻击者可能也拿到了包装后的 DEK，就要假定那些 DEK 已经泄露，对应的数据**完全重新加密** |
>
> 规律是：**重新包装只能保护"还没被解开"的 DEK**。一旦有理由相信攻击者已经拿到了某把 DEK 本身，唯一的办法就是换掉这把 DEK，也就是把数据完全重新加密。

> 📎 **拓展(超出 slides)** — 云 KMS 的"自动轮换"通常就是 S35 第 1 条描述的那种轮换。以 AWS KMS 为例：打开自动轮换后，KMS 定期生成新的密钥材料用于以后的加密，而**保留所有旧的密钥材料**用来解密以前的数据，密钥的 ID 保持不变，应用无需任何改动。它不会自动重新加密你的任何数据。

<details>
<summary>自测：公司的 KEK 每年自动轮换一次。某天发现一把 DEK 被写进了公开的日志。等到明年的自动轮换可以吗？立即重新包装这把 DEK 呢？</summary>

都不行。轮换只影响以后的操作，重新包装只是给同一把 DEK 换个信封，泄露出去的 DEK 照样能解密这个对象。必须马上换一把新 DEK，把这个对象完全重新加密，并废弃旧 DEK（以及旧密文）。

</details>

### 4.6 恢复需要职责分离 (S36)

> 📚 S36 和 S37 两段录音里都没有，以下按 slides 展开。

§4.1 说，密钥被删和密钥被偷一样致命；§4.2 说，管理密钥的权限比使用密钥的权限更危险。那么，谁来行使这些最危险的权限？S36 的回答是**职责分离 (separation of duties)**：

- **没有任何一个操作员能悄悄地导出或销毁关键密钥。** 导出威胁机密性（拿走就能解密一切），销毁威胁可用性（删掉就谁也读不出）。"悄悄地"是关键：这类操作必须留下记录，并且需要别人的批准。
- **恢复材料要和日常运维分开保护。** 用来在灾难后恢复密钥的备份，不应该放在日常管理员一个人就能碰到的地方。这和 §2.8 对备份的要求一样：恢复路径要独立于日常的身份和控制平面。
- **法定人数审批 (quorum approval) 可以保护高影响的操作。** 比如规定 5 位密钥保管人中至少 3 位同意，才能导出或删除根密钥（"M-of-N"）。
- **备份要经过测试，但测试不能让不必要的密钥暴露变成常态。** 恢复演练要定期做（§2.8），可不能每次演练都把主密钥导出到某台笔记本上"试一试"。
- **紧急访问要记录、限时、事后复查。** 出了紧急情况，可以启用一个平时封存的高权限账号（俗称"破窗 (break-glass)"访问），但它要留下完整的日志、过一段时间自动失效、事后有人逐项复查。

> 📎 **拓展(超出 slides)** — 法定人数审批和多签钱包是同一个思路：一笔高风险的操作需要 N 个人里的 M 个人同时签字，任何一个人被盗、被收买或犯错，都不足以单独造成损失。密码学上还有一种更进一步的做法，**Shamir 秘密共享 (Shamir's secret sharing)**：把一把恢复密钥拆成 N 份，任意 M 份能拼回原密钥，少于 M 份则得不到关于密钥的任何信息。KMS 的密钥策略里也常见类似的分工：**密钥管理员**能管理密钥，却不能用它解密；**密钥使用者**能用它加解密，却不能修改策略。

<details>
<summary>自测：一家公司只有一位管理员掌握 KMS 的全部权限，他既能修改密钥策略，也能安排删除密钥。按 S36，这有什么风险？至少给出两条改进。</summary>

风险：这一个人（或者盗用了他账号的攻击者）可以悄悄给自己加上解密权限、导出密钥，或者删除密钥让全部数据无法恢复，没有人能及时阻止。改进：把"管理密钥"和"使用密钥"的权限分给不同的人；删除、导出等高影响操作要求多人批准（M-of-N）并设等待期；恢复材料由另一组人在另一个地方保管；紧急访问账号平时封存，启用时限时、留日志、事后复查。

</details>

### 4.7 密钥归属模型：用易用性换控制权 (S37)

最后一个问题：密钥到底归谁？S37 列出四种**密钥归属模型 (key ownership models)**，从左到右，客户的控制越来越多，负担也越来越重：

| 模型 | 密钥从哪来、放在哪 | 谁管策略和生命周期 | 客户的控制 | 客户的负担 |
|---|---|---|---|---|
| **服务商管理 PROVIDER-MANAGED** | 服务商生成，放在服务商的 KMS 里 | 服务商，全自动 | 最少：看不到，也管不了 | 最轻 |
| **客户管理 CUSTOMER-MANAGED** | 在服务商的 KMS 里生成 | 客户：谁能用、何时轮换、能否禁用或删除 | 能设策略、看审计日志、随时禁用 | 要自己配置和监控策略 |
| **自带密钥 BYOK** | 客户在自己的环境（比如自己的 HSM）生成，**导入**云服务 | 客户 | 能证明密钥的来源；可以删除后重新导入 | 要安全地生成、导入、备份原始密钥材料 |
| **自持密钥 HYOK / 外部密钥** | **始终留在客户控制的外部系统里**，云服务每次要用都得向它请求 | 客户 | 最多：可以随时切断云服务的访问 | 最重：外部系统一旦宕机，云上的数据也就用不了了 |

S37 的最后一条是总结：**更多的控制，意味着更重的集成、可用性和恢复负担**。选哪种模型，取决于监管要求和你愿意承担多少运维工作，没有一种对所有人都最好。

这张表里有一个常见的误解要澄清。BYOK 的"自带"听起来像是服务商就碰不到了，其实不然：密钥一旦导入，就存放在服务商的 KMS 里，由服务商的系统替你使用。BYOK 控制的是**密钥从哪里来、什么时候删**，而不是让服务商**接触不到**密钥。只有 HYOK 让密钥始终留在外面。即便如此，云服务处理数据时，解密后的明文仍会出现在服务商的系统里（§3.6 的"使用中"）。要让服务商从头到尾看不到明文，就得走到 §6 的客户端加密。

> 📎 **拓展(超出 slides)** — 几大云服务商都提供了 HYOK 式的选项，比如 AWS KMS 的外部密钥存储 (External Key Store, XKS) 和 Google Cloud 的外部密钥管理器 (External Key Manager, EKM)：KMS 每次需要加解密时，都去调用客户自己运营的外部密钥管理器。

<details>
<summary>自测：一家银行要求"云服务商在任何情况下都不能单方面解密我们的数据"，也愿意承担额外的运维负担。四种模型里哪种最接近？它还留下了什么风险？</summary>

**HYOK / 外部密钥**最接近：密钥始终在银行自己的系统里，银行可以随时切断访问。遗留风险有两类：一是可用性，外部密钥系统宕机，云上的数据就用不了；二是"使用中"的明文，云服务处理数据时仍要在自己的系统里解密，服务商在那一刻看得到明文，元数据也照样可见。要彻底不让服务商看到内容，需要客户端加密（§6.1）。

</details>

密钥管理回答了"钥匙放在哪里、由谁保管"。可每一处都绕不开另一个问题：**谁有权使用它**？KMS 的 Decrypt 权限、存储桶的读取权限、管理员能不能删备份，都是访问控制的决定。下一节就讲访问控制。

## 5. 访问控制：谁能做什么，由谁来决定

S5 第 4 条要求比较三种访问控制：**RBAC、ABAC 和基于密码学的访问控制**。老师说，访问控制本身是个很大的话题，更多细节放到下周网络安全的第二部分去讲。本节先分清认证和授权（§5.1），再讲贯穿所有授权决定的原则，最小权限（§5.2），然后是两种主流的授权模型，RBAC（§5.3）和 ABAC（§5.4），最后看它们通常在哪里执行，也就是服务器居中的访问控制（§5.5）。§5.5 的局限会把我们带到 §6 的"基于密码学的访问控制"。

### 5.1 认证和授权解决的是两个不同的问题 (S39)

这两个词常被混着用，S39 第一件事就是把它们分开：

- **认证 (authentication)** 确定一个身份，或者一个工作负载的**主体 (principal)**。老师说，它回答"**是谁，或者是什么**在发请求"，手段有密码、多因素认证、证书、设备身份和工作负载凭据。
- **授权 (authorization)** 决定**这个主体能不能对某个资源执行某个动作**。

住酒店是个好例子。前台核对你的证件，这是认证；给你一张房卡，只能在入住期间打开你那一间房，这是授权。两道关各管一件事：证件对了，不代表你能进所有房间；房卡被别人捡到，酒店的门锁也分不出拿卡的是不是你。

| | 认证 authentication | 授权 authorization |
|---|---|---|
| 回答 | 你是谁？ | 你能做这件事吗？ |
| 依据 | 密码、多因素认证、证书、设备身份、工作负载凭据 | 策略：主体 + 动作 + 资源 + 上下文 |
| 只靠它会怎样 | 身份对了，权限却可能过大 | 策略写对了，却可能被偷来的凭据骗过 |

表格最后一行就是 S39 中间两条：

- **一个合法的身份，照样可能拥有过多的权限。** 认证通过了，授权却给得太宽：§4.1 那台能解密一切的 Web 服务器就是这样。
- **一条正确的策略，在凭据被盗时照样会失效。** 授权写得再好，认证一旦接受了错误的主体（攻击者拿着偷来的凭据），策略就会忠实地把权限交给攻击者：§2.7 的泄露凭据就是这样。老师的原话是：**如果认证接受了错误的主体，写得再好的策略也帮不上忙。**

S39 的最后一条给出了强系统的做法：**同时核实身份、上下文、动作、资源和时间**。老师补充，云上的访问决定常常还要看额外的上下文：设备状态、网络、时间、风险评分、资源的敏感程度。一个请求应当作为一个**组合**来评估：主体、动作、资源、上下文，再对照策略。

> 🔑 **例：把一个请求拆开来评估** — 凌晨 3 点，存储服务收到一个请求：
>
> - **主体**：`backup-svc`（备份服务的工作负载身份），凭据有效；
> - **动作**：删除对象；
> - **资源**：`finance/2026/` 下的全部对象；
> - **上下文**：来自一个从未出现过的 IP 地址，不在公司的网络里。
>
> 只看认证，这个请求毫无问题：凭据是真的。可策略规定 `backup-svc` 只能读数据、写快照，不能删除业务对象，授权这一关拒绝了它。即使策略碰巧允许删除，"凌晨、陌生 IP、批量删除"这个上下文组合也应当触发额外的检查或告警。这正是 §2.7 第 ③ 步的反面：只认凭据的系统看不出异常，把上下文纳入评估的系统才看得出。

<details>
<summary>自测：攻击者用钓鱼网站骗到了财务经理的密码和一次性验证码，登录后下载了全部财务报表。这是认证出了问题，还是授权出了问题？</summary>

认证出了问题：它接受了错误的主体（攻击者冒充成财务经理）。授权其实在"正常工作"，财务经理本来就有权读报表，这正是 S39 说的"正确的策略在凭据被盗时会失效"。改进方向：用抗钓鱼的认证方式，把设备、地点等上下文纳入评估，并限制和监控批量下载。

</details>

### 5.2 最小权限要扛得住云的规模和变化 (S40)

授权该给多少？安全领域的基本答案是**最小权限 (least privilege)**：**只授予完成当前任务所需的权限** (S40 第 1 条)。

S40 第 2 条把"最小"说得更具体：在云上，权限不仅要按**动作**限制，还要按**资源、条件、时长和委托**限制。老师举了一个例子：一个只需要读取某个存储前缀的工作负载，不应该拿到删除整个账号的能力。

> 🔑 **例：把一条策略从"什么都行"收紧到"刚好够用"** — 一个每天生成报表的任务需要读取 `uow-reports` 桶里 2026 年的报告。下面用 AWS IAM 的策略写法演示（不同的云写法不同，思路一样）。收紧之前：
>
> ```json
> { "Effect": "Allow", "Action": "s3:*", "Resource": "*" }
> ```
>
> 它允许对**所有**存储资源做**任何**操作，包括删除数据、修改桶策略。收紧之后：
>
> ```json
> {
>   "Effect": "Allow",
>   "Action": "s3:GetObject",
>   "Resource": "arn:aws:s3:::uow-reports/2026/*",
>   "Condition": { "IpAddress": { "aws:SourceIp": "203.0.113.0/24" } }
> }
> ```
>
> 对照 S40 的几个维度：**动作**只剩"读对象"；**资源**只剩一个桶里的一个前缀；**条件**要求请求来自公司的网段。另外两个维度不写在这条策略里：**时长**，这个任务通过工作负载身份换取 1 小时有效的临时凭据（S40 第 3 条，也是 §2.7 的建议）；**委托**，不授予它把权限转交给别人、或扮演其他角色的能力。即使这个任务被攻破，攻击者也只能读到 2026 年的报告，删不了数据，改不了策略。

S40 的后两条讲的是"变化"。老师强调，云环境变化很快，**最小权限不是做一次审查就完事的**：角色会不断累积权限，项目和服务会被替换，旧的身份却留了下来。

- **审查不再使用的权限，删除被遗弃的身份**（第 4 条）。用量分析能找出很少使用的权限，但老师提醒，**一项权限没被用过，不能自动证明它不需要**。比如灾难恢复用的权限，可能一年才用一次，删掉它，真出事时就恢复不了。
- **把策略变更当作特权级的安全操作来保护**（第 5 条）。老师说，策略变更本身就是特权操作，需要审批、监控和回滚能力。这呼应了 §2.1 的控制平面：能改策略的人，就能给自己任何权限。

<details>
<summary>自测：一个每天凌晨读取 reports/ 目录、生成报表的任务，被授予了整个账号的管理员权限，理由是"反正它只读数据"。按 S40，应当从哪几个维度收紧？</summary>

**动作**：只允许读取，不允许写入、删除、改策略。**资源**：只允许 reports/ 这个前缀所在的那个桶。**条件**：只允许从运行任务的那个环境发起。**时长**：用工作负载身份换取短期凭据，不给长期密钥。**委托**：不允许它转授权限或扮演其他角色。任务下线时还要删除这个身份，策略的修改要经过审批。"它只读数据"是现在的用法，不是它的权限上限，攻击者会用上它的全部权限。

</details>

### 5.3 RBAC：按岗位分配权限 (S41)

逐个用户分配权限，用户一多就管不过来。**基于角色的访问控制 (role-based access control, RBAC)** 在用户和权限之间加了一层**角色 (role)**（S41 前两条）：

- 用户和工作负载被分配到有名字的角色；
- 角色包含对特定资源、特定动作的权限。

S41 举的存储系统角色有：**reader**（读者）、**editor**（编辑）、**backup operator**（备份操作员）、**security auditor**（安全审计员）。老师说，这样管理起来容易得多，因为**权限跟着岗位走**，而不是为每个人单独维护：新员工入职，分配一个角色就行；换岗，换一个角色就行。S41 第 4 条说，**RBAC 在岗位稳定、职责分得清的时候效果很好**。

S41 的最后一条指出了它的两个毛病：**角色爆炸 (role explosion)** 和**过宽的角色**。

- **角色爆炸**：现实中的例外越来越多，"能读财务数据，但只在澳洲区域、只用公司设备"……每一种例外都要一个新角色。老师说，当组织建了太多特殊用途的角色，或者为了方便把太多权限塞进一个大角色时，问题就出现了。
- **角色叠加**：老师还提到，一个用户可以同时拥有好几个角色，**它们的权限合在一起，可能形成一条意料之外的路径**。

图 13 画的就是角色叠加。

```d2 图 13 · RBAC：用户 → 角色 → 权限。每个角色单看都合理，Bob 同时拿着两个角色，就既能覆盖数据、又能删掉快照（橙色）
direction: down
users: 用户 {
  bob: Bob {class: warn}
  alice: Alice
}
roles: 角色 {
  backup: backup operator
  editor: editor
  reader: reader
}
perms: 权限 {
  snap: 删除过期快照 {class: warn}
  write: 写入、覆盖对象 {class: warn}
  read: 读取对象
}
users.bob -> roles.backup
users.bob -> roles.editor
users.alice -> roles.reader
roles.backup -> perms.snap
roles.editor -> perms.write
roles.reader -> perms.read
```

editor 需要覆盖文件，这很正常；backup operator 要清理过期的快照，也很正常。可 Bob 同时拿着两个角色，他（或者偷了他账号的人）就能先删掉快照、再覆盖数据，正是 §2.8 勒索软件的路线。图 13 里没有任何一条"错误"的权限，危险来自组合。这也是 §4.6 职责分离的另一种表现：互相制衡的职责，不应该落在同一个人身上。

> 🔑 **例：角色是怎么"爆炸"的** — 一家公司起初按部门建角色，5 个部门，5 个角色。后来要求按数据敏感度（公开、内部、机密、绝密）区分，变成 5 × 4 = 20 个；再按区域（澳洲、欧洲、美国）区分，变成 60 个；再区分"公司设备 / 个人设备"，变成 120 个。每加一个维度，角色数就乘一次。到这一步，已经没人说得清某个用户为什么有某项权限。下一节的 ABAC 不再为每种组合建一个角色，而是直接用这些维度（属性）写规则。

<details>
<summary>自测：公司给每个项目建三个角色（只读、读写、管理）。现在有 40 个项目，每年新增 15 个，旧项目从不清理。三年后有多少个角色？这说明了什么？</summary>

$(40 + 3 \times 15) \times 3 = 85 \times 3 = 255$ 个角色。这就是角色爆炸：角色数量随项目和例外不断增长，审查和清理越来越难，过期的权限也就越积越多（S40 第 4 条）。改用"项目"这个属性写一条 ABAC 规则（§5.4），可以用一条策略替代这几百个角色。

</details>

### 5.4 ABAC：按属性和上下文做决定 (S42)

**基于属性的访问控制 (attribute-based access control, ABAC)** 不再问"你是什么角色"，而是看四类**属性 (attribute)**（S42）：

- **主体属性 SUBJECT**：部门、安全级别 (clearance)、在职状态；
- **资源属性 RESOURCE**：所有者、敏感度、所属项目、区域；
- **动作属性 ACTION**：读、写、共享、删除、管理；
- **上下文属性 CONTEXT**：时间、设备、地点、风险、网络。

策略把这些属性组合起来，做出比固定角色**更细的决定**。老师举的例子是：当用户的部门和资源所属的项目相匹配、设备是公司管理的、请求来自批准的区域时，才允许读取。这样就能表达固定角色很难简洁地表达的上下文。他还举了学校的例子：一个人可以带着"学生""来自 SCIT""年龄"之类的属性，只要这些属性满足策略，就能访问对应的内容。

> 🔑 **例：用一条 ABAC 策略评估四个请求** — 策略 P：允许**读取**，当且仅当
> ① 主体的部门 = 资源所属的部门，② 主体在职，③ 设备由公司管理，④ 请求来自澳洲区域。
>
> | 请求 | 部门 | 在职 | 公司设备 | 澳洲 | 结果 |
> |---|---|---|---|---|---|
> | Alice（财务部）用公司笔记本在悉尼读财务报告 | ✓ | ✓ | ✓ | ✓ | **允许** |
> | 同一个 Alice、同一份报告，改用自己的手机 | ✓ | ✓ | ✗ | ✓ | 拒绝 |
> | Bob（市场部）用公司笔记本在悉尼读财务报告 | ✗ | ✓ | ✓ | ✓ | 拒绝 |
> | Alice 离职后的第二天，用旧账号登录 | ✓ | ✗ | ✓ | ✓ | 拒绝 |
>
> 一条策略就覆盖了 §5.3 例子里那几十个角色：新增一个部门，不需要新建角色，只要资源和用户带上正确的部门属性。第二行和第四行是 RBAC 很难做到的：Alice 的**角色**没变，变的是上下文和在职状态。

RBAC 和 ABAC 的区别可以归纳成一张表：

| | RBAC | ABAC |
|---|---|---|
| 决定的依据 | 你属于哪个角色 | 主体、资源、动作、上下文的属性组合 |
| 适合 | 岗位稳定、职责分得清 | 需要按设备、地点、时间、敏感度细分 |
| 难点 | 角色爆炸、角色过宽、角色叠加 | 属性必须准确、及时（谁来维护"部门"和"在职状态"？）；策略更难读懂和审查 |

ABAC 的难点值得留意：它的每个决定都建立在属性上，属性错了，决定就错了。HR 系统里一个人的离职状态晚更新三天，他就多了三天的访问权。§6.8 讲 ABE 时会看到同样的问题。

<details>
<summary>自测：按上面的策略 P，Alice 出差到新加坡，用公司笔记本读财务报告，会被允许吗？如果公司希望出差时也能读，可以怎么改？代价是什么？</summary>

会被拒绝，因为不满足条件 ④（请求来自澳洲区域）。可以把条件改成"来自澳洲，**或者**通过公司 VPN 并完成多因素认证"，或者为出差人员增加批准的区域。代价是暴露面变大：条件越宽，被盗的凭据在更多地方都能用。这是安全和可用性之间的取舍。

</details>

### 5.5 服务器居中的访问控制：灵活，但高度可信 (S43)

RBAC 也好，ABAC 也好，策略总要有人来执行。在今天绝大多数的云存储里，执行者是**服务器**。S43 画了一个例子：Sarah 是 IT 部门的备份经理，她向存储服务器请求一个文件；这个文件的**访问控制列表 (access control list, ACL)** 写着"Kevin、Dave，以及 IT 部门的任何人"；服务器核对后发现 Sarah 在 IT 部门，于是把文件交给她。

老师说，在这种**服务器居中 (server-mediated)** 的模式下，客户端先向存储服务认证，再请求文件；服务用用户的身份、角色、属性和资源的元数据评估策略；允许，就返回数据。它的优点是**灵活**：策略可以集中修改，立即生效，还能用上当前的上下文（§5.4 的设备、地点）。

S43 标题的后半句是代价：**高度可信**。图下面那行字说得更直接：**策略很灵活，但服务器仍然被信任着保管明文。** 服务器手里有文件的明文（或者有能力把它解密，比如 §3.6 的静态加密），ACL 只在服务器**愿意执行**的时候才起作用。图 14 把这一点画了出来。

## 6. 客户端加密、端到端加密与安全共享

S5 的最后一条要求**评估客户端加密、E2EE、共享和 ABE**。§5.5 留下了一个问题：服务器居中的访问控制必须信任服务器保管明文。本节换一个思路：让服务器拿不到明文。先看客户端加密（§6.1）和端到端加密（§6.2），再看它们保护不了什么（§6.3）。明文离开了服务器，共享就变成了分发密钥的问题（§6.4），于是有了各种共享模式（§6.5）和撤销的极限（§6.6）。最后是把访问策略直接写进密文的 ABE（§6.7–6.9）。

### 6.1 客户端加密把明文从服务商那里移走 (S45)

**客户端加密 (client-side encryption)** 在文件到达云存储**之前**就把它加密。老师说，这样服务商存储的、在各处分发的都只是密文，它从头到尾不拥有数据密钥。好处有两个：存储服务被攻破，后果就小多了；服务商的管理员能读到的东西也少了（S45 的 *Benefit*：**存储服务收到的是密文**）。对普通用户来说，做法很简单：往 OneDrive 或 Google Drive 上传之前，先在自己的电脑上加密。回到图 14：右边那个能直接碰到服务器的人，现在只能拿到密文。

老师马上补了一句很关键的话：**信任并没有消失，它只是转移了** (*Trust does not disappear, it moves*)。原来要信任服务器，现在要信任三样东西：

- **客户端程序必须是正确的**：加密做错了（比如 §3.2 那种不带认证的加密），密文也保护不了什么；
- **终端设备必须是安全的**：明文和密钥现在都在你的设备上；
- **用户必须拿到正确的密钥**：拿错了公钥（§3.3），文件就加密给了别人。

S45 的 *Challenge* 写的是代价：**客户端必须自己分发、保护、恢复和撤销密钥**。这四件事原来都由服务商替你做，现在全落到了客户端。老师还提到密钥粒度的两难，和 §3.2 一样：每个文件一把新密钥，就需要一套可扩展的办法来分发它们；一把密钥保护许多文件，泄露时影响的范围就大，按文件细分的共享也更难做。

> 📎 **拓展(超出 slides)** — 客户端加密还有一个容易忽略的代价：服务器面对的只有密文，也就**帮不上忙**了。全文搜索、文件预览、服务端的病毒扫描、跨用户去重，都做不了。忘了密钥也没有"找回密码"可用，数据就真的没了。Cryptomator 这类开源工具就是专门给云盘做客户端加密的，用它之前要先想清楚这些取舍。你们的 Assignment 2 也是客户端加密：README 写明存储被**当作不可信的**，每个文件一把新的 256 位密钥，这就需要一套密钥分发机制，也就是链上合约加上 ECIES 包装（§6.5）。

<details>
<summary>自测：做了客户端加密以后，云服务商还能做什么、不能做什么？</summary>

**还能**：存储、复制、分发密文；看到元数据（谁上传、什么时候、多大、和谁共享）；删除数据或停止服务（可用性仍然依赖它）。**不能**：读取内容，在内容里搜索，生成预览，扫描内容里的恶意软件。客户端加密保护的是机密性，可用性和元数据仍然要另想办法。

</details>

### 6.2 端到端加密把服务器移出明文路径 (S46)

客户端加密说的是"在哪里加密"。**端到端加密 (end-to-end encryption, E2EE)** 说的是"谁能解密"：老师的定义是，发送方为**预定的接收端**加密内容，中间的服务器**没有读取内容所需的密钥**。服务器可以转发消息、存储密文、管理投递，但不应当在中途短暂地解密、再重新加密。S46 的标题概括为：**E2EE 把服务器从明文的路径上移走了。**

老师强调，E2EE 比传输加密**强**。安全的网络连接（比如 HTTPS）保护的是客户端到服务器这一段路，可服务器本身仍是一个能看到明文的端点。还是 §3.6 那个例子：你在 UOW 的网络上传文件，学校的 IT 部门看不到内容，因为有 HTTPS；可云服务商看得到，你的照片、论文都在它那里以明文出现。E2EE 改变了信任边界，让**只有通信的两端**能解密。即使 Alice 和 Bob 共享文件必须先传到服务器上，服务器也打不开。图 15 把两者对比着画出来。

### 6.3 E2EE 保护内容，不保护端点和全部元数据 (S47)

S47 的标题划出了 E2EE 的边界：**它保护内容，不保护端点，也不保护全部元数据。** 五条逐一看：

1. **恶意软件或者一台被偷的、已解锁的设备，可以读到明文。** E2EE 的"端"就是你的设备，加密在这里结束。设备上跑着的任何程序，看到的都和你看到的一样。
2. **接收者可以复制、截图或导出解密后的内容。** 老师又提到那个"笨"办法：你在屏幕上读一份机密文件，我拿手机拍一张，加密就管不到了。E2EE 防的是中间人，防不了一个不可信的接收者。
3. **服务器仍然可能看到身份、时间、大小和通信模式。** 老师以 Google 为例：你上传一个端到端加密的文件并分享给我，Google 解不开它，**仅此而已**。它照样知道你是谁（注册信息、手机号，可能还有信用卡），知道你用的是 MacBook 还是 Windows 笔记本，知道什么时候上传、文件多大，也知道你分享给了谁，而我的姓名、生日、住址它同样知道。对比一下：不用 E2EE，Google 既知道内容、又知道我们是谁；用了 E2EE，它不知道内容，但仍然知道我们是谁、和谁来往。这些就是 §2.9 说的**元数据**，很难保护。
4. **备份可能悄悄地削弱端到端的边界。** 消息在传输中是端到端加密的，可如果设备把聊天记录备份到云盘，而备份不是端到端加密的，服务商就能从备份里读到全部内容。"悄悄地"是因为用户往往不知道备份在哪、由谁的密钥保护。
5. **密钥验证和设备变更需要好用的安全设计。** 老师说，**添加设备和恢复账号是敏感的时刻**，因为新设备需要拿到解密能力：密钥怎么转到新手机上？如果服务器可以悄悄地替你"添加一台设备"，它就能给自己加一个端点，端到端加密也就名存实亡。这就需要用户能看懂、愿意用的密钥验证方式。

> 📎 **拓展(超出 slides)** — 第 4、5 条都有真实的例子。WhatsApp 的消息早就是端到端加密的，可聊天备份存到 Google Drive 或 iCloud 时，直到 2021 年才提供可选的端到端加密备份；没打开这个选项，备份就由云服务商的密钥保护。第 5 条对应的设计是 Signal 的"安全码" (safety number) 和 WhatsApp 的"安全代码"：两人当面扫码或比对一串数字，确认对方的公钥没被调包，这也是 §3.3 那个"把公钥和身份绑定"问题的一种解法。

<details>
<summary>自测：一款 E2EE 聊天应用每天把聊天记录备份到云盘，备份没有端到端加密。攻击者攻破了云盘的服务器，能拿到什么？哪一条 S47 说的就是这种情况？</summary>

能拿到备份里的全部聊天内容（或者能被服务商密钥解开的备份），尽管每一条消息在传输时都是端到端加密的。这就是 S47 第 4 条：备份悄悄地削弱了端到端的边界。攻击者本来就能看到元数据（谁和谁、什么时候、消息多大），这是第 3 条。

</details>

### 6.4 安全共享本质上是密钥分发问题 (S48)

在服务器居中的模式下，共享只是改一下 ACL。数据在客户端加密以后，事情变了。老师说：**共享意味着分发解密能力，而不只是分发密文。** 我把密文发给你，你没有密钥，这不叫共享；你拿到密文、又能解开，才叫共享。S48 的标题由此而来：**安全共享从根本上说是一个密钥分发问题。** 它列出了五条要求：

- **发送者必须确认预定的接收者或群组。** 老师补充，还要拿到可信的公钥、属性，或者另一条安全的投递渠道。这又是 §3.3 的绑定问题：加密给了错误的公钥，就是共享给了错误的人。
- **接收者需要解密能力，但不能因此暴露主密钥。** 老师说，系统不应该给每个接收者一把长期的主密钥。给你一份文件，你应当只拿到这份文件的 DEK，而不是能打开一切的 KEK（回想 §4.3）。
- **成员变化时，要能高效地更新以后的访问权。** 老师说，增加一个接收者，不应该要求把每个大文件重新加密一遍；移除一个接收者，应当尽可能有效地停止他以后的访问。
- **系统需要审计、过期、恢复和应对密钥泄露的能力。**
- **好不好用的失败，可以让技术上正确的密码学失效。** 共享流程太麻烦，用户就会退回到用邮件发明文、在群里贴共享密码。

课上有同学问"membership 是什么"。老师解释，**成员 (membership)** 就是有权访问这份数据的那一群人，比如一个部门。它是动态的：今天有人加入，明天有人离开，共享的设计必须能应付这种变化。

<details>
<summary>自测：为什么说"把密文发给对方"不算共享？真正的共享要解决哪两个问题？</summary>

没有密钥，密文毫无用处。共享要解决的是：① 把解密能力**安全地**交给**正确的**人（确认身份、拿到可信的公钥，又不暴露主密钥）；② 成员变化时，能**高效地**增加新成员、停止离开者以后的访问。

</details>

### 6.5 五种共享模式，五种取舍 (S49)

S49 列出了五种常见的共享模式，课上只念了名字。它们的区别在于解密能力**由谁、以什么形式**持有：

- **服务器策略 SERVER POLICY：灵活、简单，但服务器仍然被信任。** 就是 §5.5 的模式，服务器手里有明文或能解密，按 ACL 决定给谁。
- **共享秘密 SHARED SECRET：适合小群体，但问责和撤销都弱。** 一个群里所有人都知道同一个密码或密钥。出了事分不清是谁干的、谁泄露的；要踢掉一个人，就得换一个新秘密、重新告诉其他所有人。
- **逐个接收者包装 PER-RECIPIENT WRAPPING：身份明确，但密钥管理工作更多。** 就是 §3.4 混合加密的第 ③ 步：同一个 DEK，用每个接收者的公钥各包一份。谁能解密一清二楚，代价是每个文件、每个接收者都要包一次。
- **组密钥 GROUP KEY：高效，但成员变化时要更新密钥。** DEK 只用一把组密钥包装，组密钥再分发给所有成员。加一个文件只包一次，加一个人只要把组密钥交给他；可每当有人离开，就要换新的组密钥并分发给剩下的人。
- **公开链接 PUBLIC LINK：方便，但常常变成一张不记名凭据。** 回想 §2.7 的不记名令牌和 §2.6 的 Google Drive 例子：谁拿到链接谁就能打开，链接被转发到哪里，访问权就跟到哪里。

> 🔑 **例：同一件事在五种模式下各要做多少工作** — 一个 10 人小组共享 1,000 个文件。某天 Carol 离开小组，Dave 加入。
>
> | 模式 | Dave 加入 | Carol 离开 | 谁能解密、能否问责 |
> |---|---|---|---|
> | 服务器策略 | 把 Dave 加进 ACL | 把 Carol 移出 ACL，立即生效 | 服务器能读一切；访问由服务器记日志 |
> | 共享秘密 | 把秘密告诉 Dave | 换新秘密，通知其余 9 人；以后的文件用新秘密加密 | 10 个人用同一个秘密，分不清是谁 |
> | 逐个接收者包装 | 把 1,000 个 DEK 各包一份给 Dave：1,000 次公钥运算 | 删掉给 Carol 的 1,000 份包装；以后的新版本不再包给她 | 每份包装对应一个人，清清楚楚 |
> | 组密钥 | 把组密钥包一份给 Dave：1 次运算，但他也能读以前的所有文件 | 生成新组密钥，分发给 9 人；新文件用新组密钥 | 只知道是"组里的某个人" |
> | 公开链接 | 把链接发给 Dave | 只能作废整个链接，再给 9 人发新链接 | 谁拿到链接谁就能打开，无从问责 |
>
> 注意"Carol 离开"那一列里，没有一种模式能让 Carol 忘掉她**已经**拿到的东西。这正是下一节的主题。

**组密钥**：每次有人离开，都要生成新组密钥、分发给剩下的 199 人，频繁的人员变动让这件事几乎不停。**逐个接收者包装**：每来一个人，就要把成千上万个 DEK 逐个包给他；每走一个人，要找出并删掉他名下的所有包装。人多、文件多、变化快时，两种模式都很吃力。这正是 S51 说的"大型、多变的群组让逐个接收者的密钥管理开销很大"，ABE 就是为此设计的（§6.7）。

</details>

### 6.6 撤销收不回已经拿到的明文 (S50)

老师说，**撤销 (revocation) 有一个根本的限制**。他用课堂举例：我把一批文件共享给你们 10 个人，第二天要把其中一个人移出去。可在移出之前，他已经下载了全部文件，而且当时他是合法用户，下载也是合法的。移出之后，他确实再也访问不了云端，可他电脑上的那些文件，**我们没有办法阻止他继续读**。S50 的标题就是这句话：**撤销无法抹掉已经被拿到的明文。**

S50 的五条把"撤销能做到什么"说得很精确：

- **移除服务器上的权限，能阻止以后的授权下载。** 这是服务器策略那一层（§5.5）。
- **轮换或重新包装密钥，能保护以后加密的版本。** 这是密码学那一层：新版本用他没有的新密钥。
- **以前的接收者可能还保留着密文和旧密钥。** 他之前拿到的版本，照样能解开。
- **水印和审计提高的是问责，而不是用密码学收回。** 你能查出是谁泄露的，却不能让泄露的东西消失。
- **访问的过期和成员变化，要在部署之前就设计好。** 事后才想到"怎么撤销"，往往为时已晚。

### 6.7 ABE：把策略放进密文 (S51, S53)

§6.5 的自测留下了一个难题：人多、变化快的群组，逐个包装和组密钥都很吃力。S51 说，**属性基加密 (attribute-based encryption, ABE)** 正是为此设计的，它的思路是**把策略放进加密的数据里**：

- 传统的加密共享，针对的是**具名的**接收者或密钥；
- 大型的、不断变化的群组，让逐个接收者的密钥管理开销很大；
- 而一条策略可以用**属性**来描述接收者，而不是列出一个个具体的身份，比如"IT 部门的任何人"；
- ABE 只允许密钥里的属性**满足策略**的人解密；
- 于是，**存储服务器在机密性上可以不被信任。**

老师用 §5.4 的 ABAC 来类比。ABAC 是：你的属性符合我的策略，你就能**访问**这个文件，由服务器来判断。ABE 是：一切都加了密，你的属性符合我的策略，你就能**解密**，由数学来判断，服务器插不上手。他说，**策略本身就像一把钥匙**：你用这条策略把文件加密；以后，谁的属性能满足这条策略，谁就能解开，因为每个人的属性已经被转换成了他的私钥。他算了一笔账：IT 部门有 50 个人，如果逐个分享，要把解密密钥一个一个地发给 50 个人；用 ABE，只要用"IT 部门"这条策略加密**一次**，50 个人都能解开，以后新来的 IT 员工也能。

S53 讲的是最常见的一种，**密文策略 ABE (ciphertext-policy ABE, CP-ABE)**：策略写在密文上，属性写在用户的密钥里。它涉及四个角色：

1. **属性授权机构 (attribute authority)** 持有**主密钥 MSK** (master secret key)，并公布**公钥 PK**；
2. 授权机构给每个用户签发一把带属性的私钥：Sarah 的 $SK_{Sarah}$ 带着 "manager" 和 "IT dept."，Kevin 的 $SK_{Kevin}$ 带着 "manager" 和 "sales"；
3. 数据所有者用 PK 和一条策略加密文件，策略是一棵树：**OR(IT dept., AND(manager, marketing))**，读作"IT 部门的任何人，**或者**市场部的经理"；
4. 解密时，算法拿用户密钥里的属性去满足这棵策略树：满足，就能解开；不满足，就解不开。

老师的解读是：只要你来自 IT 部门，我不管你是经理还是普通员工，都能解开；如果不是 IT 部门，你就必须是市场部的经理。图 17 把两个人的评估过程画了出来。

direction: right

> 📎 **拓展(超出 slides)** — ABE 有一个关键性质叫**抗合谋 (collusion resistance)**：几个用户把各自的密钥凑在一起，也不能满足任何一个人单独满足不了的策略。比如 Kevin（manager、sales）和一位市场部的实习生（staff、marketing）合起来，凑得出 "manager" 和 "marketing"，可他们仍然解不开图 17 的文件，因为授权机构签发每把私钥时都混入了只属于这个用户的随机数，不同人的密钥部件拼不到一起。和 CP-ABE 相对的还有**密钥策略 ABE (key-policy ABE, KP-ABE)**：属性贴在密文上，策略写进用户的密钥。

<details>
<summary>自测：策略仍是 OR(IT dept., AND(manager, marketing))。下面三个人谁能解密？① Tom：staff、IT dept.；② Lily：manager、marketing；③ Kevin 和一位市场部实习生（staff、marketing）把密钥凑在一起。</summary>

① **能**：IT dept. 满足 OR 的第一支，职位无关紧要。② **能**：manager 和 marketing 同时满足 AND，OR 的第二支成立。③ **不能**：单看属性，两人合起来有 manager 和 marketing，可 ABE 抗合谋，不同用户的密钥部件不能拼在一起使用。

</details>

### 6.8 ABE 带来强大的策略，也带来难办的运维 (S54)

> 📚 S54 课上没有讲，以下按 slides 展开。

S54 的标题说得很平衡：ABE 带来了强大的策略表达能力，也带来了难办的运维。五条代价：

- **属性授权机构必须核实并签发可信的属性。** 存储服务器不用信任了，信任转移到了授权机构身上：它把 "IT dept." 发给了不该发的人，策略就形同虚设。更进一步，授权机构持有 MSK，**能生成任何属性组合的私钥**，也就能解密一切。
- **撤销和属性变化可能需要重新发密钥，或者划分时间段。** Sarah 周一调离了 IT 部门，可她的私钥里仍然写着 "IT dept."，密钥发出去就收不回来。常见的折中是让属性带上有效期（比如 "IT dept., 2026 年第 4 季度"），到期重新签发；或者用新策略重新加密数据。和 §5.5 那种改一下 ACL 就立即生效的方式相比，这慢得多，也重得多。
- **策略本身可能泄露组织里的敏感信息。** 策略通常以明文附在密文上。一条 "board OR merger-team-Falcon" 的策略，就告诉了所有能看到密文的人：公司有一个代号 Falcon 的并购项目，谁在里面。这又是一种元数据泄露（§2.9、§6.3）。
- **计算开销和密文的额外长度都高于普通加密。** 策略越复杂，密文越大，解密越慢。
- **终端被攻破、明文被复制，仍然在 ABE 管辖之外。** 和 §6.3、§6.6 一样：解密之后的事，密码学管不到。

> 📎 **拓展(超出 slides)** — 正因为开销大，实际系统一般不直接用 ABE 加密整个文件，而是又一次用上 §3.4 的混合加密思路：用 AES 加密文件，再用 ABE 加密那把很小的 DEK。ABE 负责"按策略送钥匙"，AES 负责"搬数据"。

<details>
<summary>自测：Sarah 周一调离了 IT 部门。在 ABE 下，她还能解密那些按 "IT dept." 策略加密的文件吗？和 §5.5 的服务器居中模式相比，撤销有什么不同？</summary>

还能，直到她的密钥过期（如果属性带有效期），或者数据用新策略、新密钥重新加密为止，因为她的私钥里仍然写着 "IT dept."，发出去就收不回。服务器居中模式下，只要改一下她的属性或 ACL，下一个请求就被拒绝，立即生效。这就是 S52 和 S54 说的：ABE 减少了对存储的信任，但让撤销变得复杂。

</details>

### 6.9 RBAC 和 ABE 在不同的边界上执行策略 (S52)

最后把 §5 和 §6 放在一起比较。S52 的标题指出，两者的根本区别是**在哪个边界上执行策略**：

| | RBAC（服务器居中） | ABE（由密码学执行） |
|---|---|---|
| 谁执行策略 | 一个**可信的服务**，在交出数据之前检查角色 | **密文本身**：只有属性匹配的密钥才解得开 |
| 信任谁 | 服务器，它看得到明文 | 属性授权机构，它签发密钥；存储服务器可以不被信任 |
| 策略变化 | **立即生效**，还能用丰富的运行时上下文（设备、地点、时间） | 要重新发密钥或重新加密；运行时上下文很难写进密钥 |
| 撤销 | 容易：改策略即可（已下载的除外） | 难：密钥发出去就收不回，要靠有效期或重新加密 |
| 服务器被攻破时 | 明文泄露 | 只泄露密文和策略 |

S52 的最后一条是结论：**两者可以互补，而不是互相竞争。** 一个合理的设计是两层都用：文件用 ABE（或者 §6.5 的任何一种客户端加密）保护，服务器被攻破也只丢密文；服务器那一层再用 RBAC 或 ABAC 决定谁能**下载**密文，做到立即撤销、按上下文判断、记录审计日志。攻击者想拿到明文，必须同时骗过两层：既要有一个能通过服务器检查的会话，又要有一把属性匹配的密钥。

<details>
<summary>自测：一家医院要在云上共享病历。它希望服务商读不到病历，又希望医生离职当天就再也下载不到新的病历。只用 RBAC 或只用 ABE 各缺什么？怎么组合？</summary>

只用 RBAC：撤销能立即生效，但服务器（服务商）看得到明文。只用 ABE：服务商读不到明文，但离职医生的密钥里仍带着原来的属性，撤销慢。组合：病历用 ABE（比如策略 "cardiology AND doctor"）加密，服务商只存密文；服务器端再用 RBAC/ABAC 控制谁能下载密文，医生离职当天移除他的账号和角色，他就下载不到新的病历。已经下载过的，仍然收不回（§6.6）。

</details>

## 本章小结 (Key takeaways)

S55 用一句话收尾：**安全的云存储要让五个控制平面对齐** (*Secure cloud storage aligns five control planes*)。这一页课上只匆匆看了一眼，它正好是本章五节的目录：

| 控制平面 | S55 的说法 | 本章 |
|---|---|---|
| 存储 STORAGE | 生命周期、韧性、位置和可见性 | §2 |
| 密码学 CRYPTOGRAPHY | 在正确的边界上提供正确的性质 | §3 |
| 密钥 KEYS | 受约束的使用、审计、轮换、恢复和销毁 | §4 |
| 访问 ACCESS | 强身份、最小权限、RBAC 或属性 | §5 |
| 共享 SHARING | 可信的接收者、好用的分发、现实的撤销预期 | §6 |

"对齐"的意思是：任何一个平面出了漏洞，其他平面做得再好也会被拖垮。数据用最强的算法加了密，可桶策略被改成了公开，而解密由服务端自动完成（密码学对、访问错）；访问控制滴水不漏，可一把能解密一切的密钥写在代码里（访问对、密钥错）；什么都做对了，可备份和数据共用一个管理员身份（其余都对、存储韧性错）。

- **云安全的主要风险在配置和身份，不在算法。** 云改变了风险的位置、规模、速度、可见性和依赖；责任共担模型是一张边界图，从 IaaS 到 SaaS 服务商管得越来越多，但**数据和身份永远归客户**。
- **云存储是一道服务边界。** 数据平面读写内容，控制平面决定"怎么存、谁能读"，能改策略的权限往往比能读数据更危险。一份数据在一生中会长出很多副本：对可用性是保障，对保密和删除是负担，分享出去的那份收不回来。
- **合法的功能是最常见的攻击路径。** 一条策略就能暴露整批数据；泄露的 API 凭据在服务商看来是合法调用，防御要同时缩短秘密的寿命、缩小它的权力。云勒索攻击的是身份和恢复路径：**复制不是备份**，备份要不可变、独立于数据的身份和控制平面，并且演练过。
- **没有一个密码学原语能包办所有安全目标。** 按问题选原语：哈希问"变没变"，MAC 问"是不是共享秘密的持有者"，签名问"是不是这把私钥签的"，加密问"别人能不能读"；不带认证的加密挡不住篡改。"已加密"要说清范围：静态、传输、客户端还是端到端，以及**谁持有密钥**。
- **对称密钥搬数据，公钥或 KEK 送钥匙。** 混合加密和信封加密都用一把随机的数据密钥加密数据，再把这把小密钥保护起来；包装后的 DEK 可以和密文放在一起。能解包就能读：KMS 的 Decrypt 权限和管理权限是最高价值的控制平面。
- **密钥管理的失败多在人和流程。** 密钥层级越高，泄露时波及越广，按租户、区域、敏感度分开 KEK 可以控制损失；轮换只管以后，重新包装只换信封，DEK 本身泄露就必须完全重新加密；导出和销毁关键密钥要职责分离、多人批准；四种归属模型用易用性换控制权，BYOK 并不让服务商碰不到密钥。
- **认证确认"是谁"，授权决定"能做什么"，两道关缺一不可。** 最小权限要按动作、资源、条件、时长和委托收紧，并持续复查。RBAC 按岗位分配，怕角色爆炸和角色叠加；ABAC 按属性和上下文判断，依赖属性准确及时。
- **不想信任服务器，就让服务器拿不到明文。** 服务器居中的访问控制灵活，但服务器被信任保管明文；客户端加密和 E2EE 把明文移出服务器，信任随之转移到客户端、终端和密钥，而终端、接收者和元数据仍不受保护。共享就是分发解密能力，撤销只能保护以后；ABE 把策略写进密文，让存储不必被信任，代价是授权机构、撤销和开销，它和 RBAC 互补而不是竞争。
